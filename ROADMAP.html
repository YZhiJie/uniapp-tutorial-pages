uni-app 系统教程 · 精通级演进路线图 ​

基于项目现状（VitePress 1.5 + Vue 3 + Pinia 3 + TS 5.6，11 模块 33 篇教程，自研中文搜索引擎）， 从 地基自动化 → 核心壁垒 → 闭环演练 → 平台化 → 单端专精 → 混合栈协同 → 工程质量 → 社区生态 八个阶段， 按依赖关系从底向上推进。每个阶段内的任务可并行，阶段间存在硬依赖。

现状速览 ​

维度已具备待补充
内容11 跨端模块 × 3 阶段 = 33 篇 md；nav.ts 为单一数据源0 篇单端专精（H5/小程序/App 特有技术全空白）、版本标注、实战案例深度、图示/图解
检索自研 search.ts（bigram + AND 语义 + 加权评分 + 高亮）倒排索引、BM25、拼音、md 全文
演练CodePlayground iframe + 6 个 HTML 演练场；uniapp-demo 独立 HBuilderX 工程H5 产物自动发布、双向链接、代码自动注入
个人化收藏夹（Pinia + IndexedDB）、最近阅读学习进度、知识图谱、笔记、计划生成
工程化vitest 4 个测试（taxonomy/search/storage/favorites）、sw.jsCI 全链路、md ↔ nav 校验、代码片段可执行
生态—Discussions、RSS、PR 模板、i18n、插件化

关键诊断：现有 33 篇教程视角 100% 是"一份代码覆盖四端"的跨端统一策略， 但 uni-app 用户真实上线前卡壳的 20% 恰恰是单端特有技术（微信支付、SSR 部署、原生插件、推送、审核发布等）。 官方文档只讲 API，不讲"怎么接入微信支付上线"——这正是单端专精模块的差异化价值。

Phase 0 · 地基自动化（Foundation Automation） ​

目标：让维护者做一件事（写 nav.ts）就能驱动全站，消除手工同步风险。 为什么先做：后续 Phase 的 build 脚本、CI 校验、内容扩展，全部依赖这里打好的地基。 估算：2~3 天 · 可立即启动

0.1 nav.ts ↔ md frontmatter 自动同步 ​

  • 现状：nav.ts 是 sidebar/catalog/crumbs/allTags 的单一数据源，但 33 个 md 文件的 frontmatter（title/description/tags）需手工维护，容易出现"nav 改了但 md 没更"
  • 方案：
    1. 扩展 modules 里的 CourseItem，把 summary 字段拆成 summary（一句话）+ description（2~3 句用于 frontmatter）
    2. 写 scripts/sync-frontmatter.mjs：读取 nav.ts → 用 gray-matter 解析对应 md → 自动注入/覆盖 frontmatter → 保留 md 正文不动
    3. 支持 --check 模式（CI 用），检测 diff 后返回非零退出码
  • 影响文件：.vitepress/theme/nav.ts（加 description）、新增 scripts/sync-frontmatter.mjs、所有 guide/**/*.md 的 frontmatter
  • 依赖：无
  • 成功标准：运行 pnpm run sync:fm 即可完成全站 frontmatter 同步；CI 拦截手工修改

0.2 nav.ts ↔ md 完整性 CI 校验 ​

  • 现状：tests/taxonomy.test.ts 校验 catalog 长度、sidebarGroups 结构，但不校验 md 文件是否真实存在、frontmatter 是否与 nav 一致
  • 方案：
    1. 扩展 vitest 套件：校验 nav.ts 每个 link 指向的 md 文件必须存在
    2. 校验 md 的 frontmatter.title 必须包含 nav 里的 phaseLabel（如"基础入门"/"进阶应用"/"实战案例"）
    3. 校验 nav 里的 tags 必须非空、allTags 去重后数量一致
    4. 新增 .github/workflows/quality.yml，push 时自动跑 pnpm test
  • 影响文件：tests/taxonomy.test.ts（扩展）、新增 .github/workflows/quality.yml、可能新增 scripts/check-consistency.mjs
  • 依赖：0.1 完成（否则 frontmatter 永远对不上）
  • 成功标准：缺失 md 或 frontmatter 不一致时 CI 红

0.3 md 代码片段可执行校验 ​

  • 现状：md 里的 js` / ts / ````vue 代码块无法保证能跑通
  • 方案：
    1. 新增 scripts/validate-snippets.mjs，用 markdown-it 提取 md 中所有 fenced code block
    2. 对 JS/TS 块用 tsx + Node 跑一遍（允许 mock uni / wx 全局）
    3. 对 Vue SFC 块做 template 语法检查（用 @vue/compiler-sfc）
    4. 输出报告：哪些 md 的哪些代码块在哪一行报错
  • 影响文件：新增 scripts/validate-snippets.mjs、可能需要给 uniapp-demo 里的 uni API 写 mock
  • 依赖：无（可与 0.1/0.2 并行）
  • 成功标准：pnpm run check:snippets 扫描完 33 篇 md，报告零错误

0.4 Frontmatter 扩展：版本与难度 ​

  • 方案：在 nav.ts 的 CourseItem 里加两个字段：
    • uniVersion: '3.2.0' — 该教程基于哪个 uni-app 版本
    • difficulty: 1|2|3 — 1=入门 / 2=进阶 / 3=实战
  • 由 0.1 的 sync 脚本自动注入到 md frontmatter
  • 在首页卡片、sidebar 上可选显示版本号（v3.2 小徽章）
  • 成功标准：每个 md 顶部都有版本号 + 难度星级

Phase 1 · 搜索引擎升级（The Core Differentiator） ​

目标：把现有全量扫描的 search.ts → 预构建倒排索引 + BM25 + 拼音 + 全文搜索。 这是本教程站最独特的技术壁垒——VitePress 官方 local search 是 minisearch 封装，社区没有面向中文 uni-app 生态的自建搜索引擎。 估算：5~7 天 · 核心亮点

1.1 miniindex 预构建倒排索引 ​

  • 现状：每次搜索都对 catalog（33 项）做全量扫描。如果扩展到 200+ 篇就慢了，且搜不到 md 正文
  • 方案：
    1. vitepress buildEnd 钩子（或独立的 scripts/build-index.mjs）读取 nav.ts + 所有 md 前 3 段正文
    2. 用 miniindex（轻量倒排索引库，~5KB gzip）构建倒排列表 + posting list
    3. 生成 public/index.json（或 public/index.js，VitePress 的搜索可以直接用）
    4. 运行时 search.ts 改为 O(log N) 查询，不再全量遍历
  • 影响文件：package.json（加 miniindex 依赖）、.vitepress/theme/utils/search.ts（重写）、可能加 .vitepress/theme/index.ts 的 buildEnd 钩子
  • 依赖：0.1（需要从 nav.ts + md 正文取完整语料）
  • 成功标准：pnpm run docs:build 后产物里有 index.json；搜索响应 < 50ms

1.2 BM25 排序替换手写加权 ​

  • 现状：search.ts 里 scoreDoc 是手写加权（标题×6，标签×4，摘要×1），调着调着就不准
  • 方案：引入 BM25 公式（k1=1.2, b=0.75），保留 title/tags/moduleTitle/summary 四个 field 的权重因子
  • 成功标准：同一查询"拦截器"，BM25 排序结果比手写加权更合理（企业级请求层排在 request.beforeRequest 之前）

1.3 拼音模糊匹配 ​

  • 方案：
    1. 构建索引时给每个词额外存一份拼音（用 pinyin-pro，~15KB gzip）
    2. 查询时如果 token 里全是英文/拼音字母（无中文），先走拼音匹配再走中文匹配
    3. 例："jiajuzuo" → 命中"脚手架"、"request" → 命中所有含 request 的标题/代码
  • 成功标准：输入"jiajuzuo"能召回"脚手架"；输入"pinia"召回状态管理相关全部

1.4 md 全文索引（含代码片段） ​

  • 方案：索引语料从"title + tags + summary"扩展为：
    • md 正文全部段落（除去 fenced code block）
    • fenced code block 里的变量名/API 名（如 addInterceptor、navigateTo）作为额外 boost 词
  • 成功标准：搜"addInterceptor"能命中"5.2 进阶应用：路由拦截、鉴权守卫"

1.5 搜索历史 + 热门推荐 ​

  • 方案：
    1. CatalogExplorer.vue 顶部加一个"大家都在搜"横条：从 nav.ts 的 allTags 里取 top 10（或 IndexedDB 记录 hits 排序）
    2. IndexedDB 存用户搜索历史（最近 10 条），下拉输入框时可见
  • 成功标准：检索页打开即显示"大家都在搜：拦截器 / Pinia / 分包 / 虚拟列表"

Phase 2 · Demo 深度集成（Close the Tutorial-Code Loop） ​

目标：消除 uniapp-demo（独立 HBuilderX 工程）与 VitePress 教程之间的墙，让读者"点一下就能看到跨端代码跑起来"。 估算：4~6 天

2.1 uniapp-demo H5 自动构建发布 ​

  • 方案：
    1. CI 里加 uni build -p h5 步骤（需要 DCloud 官方 CLI 或 npx @dcloudio/uvm 安装）
    2. 产物发布到 public/demo/<module>/<page>/ 目录
    3. CodePlayground 组件改为 iframe 嵌入真实构建产物（不是 source HTML）
  • 影响文件：uniapp-demo/（可能调整目录结构以支持 CLI 构建）、新增 .github/workflows/build-demo.yml
  • 依赖：0.1（教程和 demo 路径需要对齐）
  • 成功标准：CI push 后 public/demo/04-api/basics-request/ 下有真实可访问的 H5 产物

2.2 md ↔ demo 源码双向链接 ​

  • 方案：
    1. 扩展 nav.ts 的 CourseItem 加 demoPath?: string 字段（如 'pages/request/request.vue'）
    2. sync-frontmatter 脚本把 demoPath 注入 md frontmatter
    3. 写 VitePress 自定义组件 DemoLink.vue：在每个 practice.md 底部渲染"查看对应源码 → GitHub 跳转链接"
  • 成功标准：每篇 practice.md 末尾有一个链接，指向 uniapp-demo 仓库里对应源码的具体文件 + 具体行号

2.3 自动代码示例注入 ​

  • 方案：
    1. 在 uniapp-demo 的 .vue 文件里加注释标记：// tutorial:04-api-basics-request-start 和 // tutorial:04-api-basics-request-end
    2. 写 build 脚本扫描这些标记，提取片段，注入到 md 的对应位置（Frontmatter 里加 demoSnippet: '04-api-basics-request'）
    3. VitePress 自定义容器 :::demo-snippet 渲染提取的代码
  • 依赖：2.1、2.2
  • 成功标准：改了 uniapp-demo 里的代码 → 教程里的代码示例自动同步，不复制粘贴

2.4 在线 uni-app 编译器（进阶 · 可选） ​

  • 方案：
    1. 接入 DCloud uniCloud 编译 API（需要后端 serverless 函数）
    2. CodePlayground 升级为：左侧编辑 uni-app .vue，右侧实时预览编译后的 H5 产物
  • 依赖：2.1 必须先跑通、后端能力
  • 成功标准（如果做）：用户在浏览器里写 uni-app 代码，点"运行"就能看到效果

Phase 3 · 学习平台化（From Docs to Learning Platform） ​

目标：让用户"用"教程而不是"看"教程——有进度管理、依赖导航、个人笔记。 估算：5~7 天 · 与 Phase 1/2 可部分并行

3.1 学习进度持久化 ​

  • 现状：ReadTracker 只记录"读过哪些"；没有"完成哪些"
  • 方案：
    1. IndexedDB 里加一个 progress store，记录每个 link 的状态：'reading' | 'done' | 'skipped' + 完成时间戳
    2. DocToolbar.vue 加一个"标记已完成 ✅"按钮（就在现有收藏按钮旁边）
    3. 首页 learning-path.md 渲染模块进度条（"模块一 3/3 完成"）
  • 依赖：无（可与 Phase 1 并行）
  • 成功标准：切换浏览器后进度仍在；首页学习路径有可视化进度

3.2 知识图谱 / 模块依赖图 ​

  • 方案：
    1. 写 build 脚本扫描 nav.ts 的 tags，用标签交叉出现频率构造模块间有向图（08-perf 的"分包加载"标签 ↔ 07-adapt 的"平台分支"标签 → 连一条边）
    2. 自动生成 Mermaid graph，嵌入 learning-path.md
    3. 效果：读者一眼看到"模块七 ← 模块三 ← 模块二 ← 模块一"的前置关系
  • 成功标准：learning-path.md 顶部有一个 Mermaid 依赖图，能看出学习顺序建议

3.3 学习计划生成器 ​

  • 方案：
    1. 前端交互：勾选"我想 3 周内掌握跨端实战" → 选择每天可投入时间（15/30/60 分钟）
    2. 算法：根据 3.2 依赖图做拓扑排序 + 按模块难度加权分配天数
    3. 输出：21 天甘特式计划，每天几篇 + 对应 demo + 预计时长 + 完成打勾
  • 依赖：3.1（进度要持久化）、3.2（依赖图）
  • 成功标准：用户勾选项后 3 秒内生成一份个性化学习计划，可导出 Markdown

3.4 段落级笔记 / 高亮 ​

  • 方案：
    1. 用户选中正文段落 → 右键菜单"添加笔记"
    2. IndexedDB 存笔记数组（pageLink + 段落锚点 + 用户笔记文本 + 时间戳）
    3. 新页面 notes.md 汇总所有笔记，支持按模块筛选 + 导出 Markdown
  • 成功标准：选中一段文字加笔记后，下次回到该页段落有虚线标记 + hover 显示笔记内容

Phase 4 · 工程质量体系（Engineering Quality） ​

目标：从"个人维护"到"学术级严谨"——每篇教程有版本、代码可跑、多语言可达。 估算：3~5 天

4.1 内容版本矩阵 ​

  • 方案：
    1. 0.4 已经在每个 md frontmatter 加了 uniVersion，现在扩展：
      • 教程首页底部显示"本教程基于 uni-app 3.2.0 + Vue 3.5 + Vite 5"
      • 新增 versions.json 维护多版本文档入口（如 uni-app 3.0 / 3.2 差异对照）
      • 升级时：每篇 md 加 deprecatedFrom / supersededBy 字段
    2. 侧边栏顶部 badge 显示当前站点覆盖的 uni-app 版本
  • 成功标准：首页明确标注 uni-app 版本号，版本升级时有迁移对照页

4.2 CI 全链路校验矩阵 ​

  • 现状：.github 目录还不存在，没有 CI
  • 方案：
    1. .github/workflows/quality.yml（push 触发）：
      • pnpm install + test + typecheck
      • Phase 0 的 pnpm run sync:fm --check + pnpm run check:snippets
      • Phase 1 的 pnpm run docs:build（确保构建成功）
    2. .github/workflows/deploy.yml（main 分支 push 触发）：
      • docs:build → 产物发布到 GitHub Pages
      • 同时跑 uniapp-demo H5 构建 → 发布到 Pages 的 /demo/ 子路径
  • 依赖：Phase 0（脚本都得先写好）、Phase 2（如果同时部署 demo）
  • 成功标准：PR 打开后自动跑全链路，红/绿一目了然

4.3 i18n 国际化（英文骨架） ​

  • 方案：
    1. 用 VitePress 内置 locale 机制，新建 en-US/ 目录（每个 md 一份英文骨架，先翻标题和摘要，正文后续补）
    2. nav.ts 拆成 nav.zh.ts / nav.en.ts，或用 frontmatter 的 title_en 字段
    3. 导航栏加语言切换按钮（已有 --vp-locales 支持）
  • 成功标准：站点右下角有 🌐 切换按钮，点一下看到英文标题 + 英文摘要

4.4 Lighthouse CI + 性能基线 ​

  • 方案：

Phase 6 · 单端专精补全（Single-Platform Expertise） ​

目标：填补 H5 / 微信小程序 / App 三端独有技术的知识空白——这是上线前卡壳的"最后一公里"，也是官方文档不覆盖的差异化价值。 现状诊断：33 篇已有教程 100% 是"跨端统一"视角，单端独有技术（SSR、微信支付、原生插件、审核发布等）零覆盖。 核心产出：新增 模块十二（H5 专精） + 模块十三（微信小程序专精） + 模块十四（App 专精），共 9 篇 md（每模块 3 阶段）。 估算：10~14 天 · 内容重写为主、脚本少量补充

6.1 模块十二 · H5 端专精（guide/12-h5/） ​

  • 为什么新增：uni-app H5 端独有 SSR/PWA/SEO/CORS/Web API 等，在小程序/App 上完全不存在
  • 子任务：
    1. 12.1 基础入门：uni-app H5 渲染原理与 SPA 路由
      • 渲染后的 DOM 结构（<uni-app> 根节点 / 虚拟列表 / 与小程序/App 的本质差异）
      • hash vs history 路由模式切换 + nginx/宝塔回退配置
      • 浏览器 BOM/DOM API（window/document/fetch/IntersectionObserver）在 uni-app 里的使用边界
      • H5 端专属条件编译 #ifdef H5 实战
    2. 12.2 进阶应用：SSR、PWA 与 SEO
      • uni-app SSR 配置 + 动态 meta（<title>/og:image/canonical）
      • PWA 三件套：manifest.json + Service Worker + 桌面图标 + 安装提示
      • SEO checklist：sitemap.xml、robots.txt、结构化数据、AMP 适配
    3. 12.3 实战案例：企业级 H5 发布（Nginx + CDN + CI/CD）
      • CORS 跨域解决 + Cookie SameSite=None 处理 + HTTPS 证书
      • HSTS + CSP + Permissions Policy 安全头
      • SSR 首屏 < 1s 优化演练（关键 CSS 内联、图片 lazy、HTTP/2 push）
  • 影响文件：新增 guide/12-h5/{basics,advanced,practice}.md、nav.ts 新增 1 个模块条目
  • 依赖：Phase 0（nav.ts ↔ frontmatter 同步、md 完整性校验）
  • 成功标准：12.3 提供可运行的 Nginx 配置片段 + CDN 回源策略 + 完整的 CI/CD YAML

6.2 模块十三 · 微信小程序端专精（guide/13-mp-weixin/） ​

  • 为什么新增：微信小程序是 uni-app 用户量最大的目标端，但官方文档从不教"怎么上线一个合规的小程序"
  • 子任务：
    1. 13.1 基础入门：uni-app 小程序编译产物与原生差异
      • dist/dev/mp-weixin/ 目录结构解读（app.json/pages.json/组件映射表）
      • 原生小程序组件 / API / 配置 与 uni 封装的映射关系对照表
      • 微信开发者工具 + 真机调试 + 模拟器差异
    2. 13.2 进阶应用：微信能力深度集成
      • wx.login + code2session + openid/unionid 鉴权体系（uni.login 四端差异）
      • 微信支付 wx.requestPayment（uni.requestPayment 参数差异、签名、回调）
      • 订阅消息（一次性/长期）+ 模板 ID 配置 + 后端发送模板
      • getPhoneNumber 手机号一键登录（2023 年后授权 API 变化）
      • 小程序分包（微信后台配置 vs uni-app 编译分包，两者同时存在）
    3. 13.3 实战案例：从 0 发布一个上线版小程序
      • 微信公众平台注册 → AppID → 小程序后台配置（服务器域名、业务域名、隐私协议）
      • 体验版上传 + 灰度发布 + 全量发布
      • 隐私合规弹窗 __usePrivacyCheck__ + 审核必备清单
      • url scheme / 分享跳转（小程序 → H5 → 小程序）
  • 影响文件：新增 guide/13-mp-weixin/{basics,advanced,practice}.md、nav.ts 新增 1 个模块条目
  • 依赖：Phase 0、6.1（H5 历史路由知识可复用）
  • 成功标准：13.3 给出一份"上线前 checklist"，按清单走完不会因审核被拒

6.3 模块十四 · App 端专精（iOS + Android，guide/14-app/） ​

  • 为什么新增：原生插件、推送、热更新、应用市场上架是 uni-app 变现的最后一公里，社区里没人系统性讲
  • 子任务：
    1. 14.1 基础入门：uni-app App 构建原理
      • 云打包 vs 离线打包 vs 原生工程（HBuilderX / Android Studio / Xcode）三种路线对比

Phase 7 · 混合栈与跨应用协同（Hybrid Stack & Cross-App Collab） ​

目标：填补"跨容器、跨应用、跨技术栈"协同的知识空白——这是 uni-app 用户从"单项目跨端"走向"多项目/多端混合"时必然遇到的架构问题。 现状诊断：现有 33 篇教程 + Phase 6 单端专精，全部是"单一 uni-app 工程内的跨端策略"。但真实生产中大量场景涉及：

  • uni-app 内嵌原生 SDK（极光/高德/微信）→ requireNativePlugin
  • 小程序 <web-view> 嵌独立 H5 编辑器 → postMessage 双向通信
  • 原生 Android/iOS 壳嵌 uni-app 页面 → plus.webview + JSBridge
  • H5 拉起小程序、小程序拉起 App → url scheme + 微信开放标签
  • 小程序 ↔ App 账号体系打通 → unionid + JWT 官方文档只讲 web-view / requireNativePlugin API 签名，不讲怎么搭混合栈架构。 核心产出：新增 模块十五 · 混合栈与跨应用协同（3 篇 md）。 估算：5~7 天 · 偏架构与集成实战

7.1 模块十五 · 混合栈与跨应用协同（guide/15-hybrid/） ​

  • 为什么新增：uni-app 的"混合"场景远比"条件编译"更广义——它是跨技术栈、跨容器、跨进程的协同，不是编译期分支
  • 与现有模块七的边界：
    • 模块七 = "同一份代码，编译期物理剪枝"（单工程、编译时）
    • 模块十五 = "多来源代码在运行时协同"（跨工程、运行时）
  • 子任务：
    1. 15.1 基础入门：混合开发全景与三条武器
      • 混合开发 vs 跨端统一 vs 原生混编：三者边界与决策树（何时用哪种）
      • 三条武器清单：
        • web-view 组件（跨 H5 ↔ 小程序/App 容器，运行时 HTML）
        • plus.webview（原生级 webview 管理，App 端独占）
        • uni.requireNativePlugin（原生 SDK 桥接，App 端独占）
      • JSBridge 基础：window.webkit.messageHandlers（iOS）/ plus.webview.evalJS（App）/ wx.miniProgram.postMessage（H5 内嵌小程序）
    2. 15.2 进阶应用：跨容器通信与跨端拉起
      • H5 ↔ 小程序：web-view postMessage + wx-open-launch-weapp 标签拉起 + 小程序跳转其他小程序
      • H5 ↔ App：uni.postMessage + plus.webview.currentWebview() + H5 调原生 plus.android.invoke / plus.ios
      • App ↔ 原生 SDK：requireNativePlugin 写一个极光推送完整示例（Android/iOS 双端 plugin 实现 + uni-app 调用端）
      • 小程序 ↔ App 账号打通：unionid 体系 + H5 中转登录 + JWT 双端共享
      • 原生 App ↔ uni-app 页面互跳：plus.webview.create 从原生壳拉起 uni 页面 + uni 调回原生 Activity/ViewController
    3. 15.3 实战案例：三种典型混合栈架构落地
      • 方案 A · uni-app App + 原生 SDK：完整演示 requireNativePlugin 调用高德地图 3D SDK（含 plugin 目录结构、Android .aar 集成、iOS .framework、HBuilderX 打包配置）
      • 方案 B · 小程序 + 独立 H5 编辑器：小程序 <web-view> 加载独立 Vue3 编辑器，用户编辑完 postMessage 同步回小程序页面
      • 方案 C · H5 + 小程序 + App 三端统一登录态：H5 写 cookie → 小程序 web-view 读取 → App plus.webview 同步，附 JWT + 刷新策略
  • 影响文件：新增 guide/15-hybrid/{basics,advanced,practice}.md、nav.ts 新增 1 个模块条目
  • 依赖：Phase 0（nav.ts ↔ frontmatter 同步）、Phase 6（H5/小程序/App 单端知识已具备，混合是在此之上做协同）
  • 成功标准：7.3 三个方案每个都给出完整可运行的 demo 代码（含 requireNativePlugin 的 Android/iOS 原生端代码片段）

7.2 nav.ts 扩展（新增模块十五） ​
