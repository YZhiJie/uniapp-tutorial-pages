架构方案（阶段一交付） ​

项目：ecommerce-mini-program/ 目标：uni-app + Vue3 + TypeScript（strict）+ Vite，六端（微信 / 支付宝 / 抖音 / QQ / 百度 / H5）平权适配，Mock 先行、可插拔转接真实后端。 本文只描述「怎么搭、为什么这么搭」，业务实现从阶段二开始。

1. 架构总览 ​

┌─────────────────────────────────────────────────────────────┐
│  pages / pages-sub            页面层：只编排，不写数据逻辑        │
├─────────────────────────────────────────────────────────────┤
│  components/common|business   基础组件 + 业务组件（SkuPopup 等） │
│  composables                  组合式逻辑（usePagination/useFlag）│

│  stores (Pinia)               按业务域拆分：config/user/cart/... │
├─────────────────────────────────────────────────────────────┤
│  api                          按业务域拆文件，只依赖 Transport   │
├─────────────────────────────────────────────────────────────┤
│  transport                    Msw / LocalMock / Http 三套实现    │
│  providers                    Payment/Live/Sms/Login 抽象        │
│  config                       env + flag 注册表                 │
├─────────────────────────────────────────────────────────────┤

依赖方向严格单向：pages → composables/stores → api → transport，providers → platform。反向依赖（如 api 依赖 store）禁止。

2. 技术选型与结论 ​

2.1 UI 基座：uni-ui vs uview-plus ​

维度uni-uiuview-plus
维护方DCloud 官方社区
六端一致性官方按端适配，风险低组件丰富，但支付宝/百度差异需逐项验证
体积按需引入，体积小全量较重，需要手动裁剪
业务契合组件偏基础，需二次封装现成业务组件多，但定制成本转移到覆盖样式

结论：uni-ui 作为基座，业务组件（SkuPopup / WaterfallFlow / LiveProductBar 等）在基座之上二次封装。理由：六端平权是硬指标，官方组件的跨端一致性优先于组件数量；业务组件的可控性也更强。

2.2 请求层：luch-request vs 自研薄封装 ​

维度luch-request自研薄封装
能力完整度拦截器、取消、上传下载齐全需自行实现重试/去重/取消（代码量小）
与 Transport 抽象契合需二次改造，存在两套取消逻辑直接注入 Transport，Mock/Http 同一入口
包体积中等极小
可观测性需扩展埋点、traceId、桶号透传可内建

结论：自研薄封装（api/core + 拦截器链），取消能力下沉到 platform/request.ts：小程序用 RequestTask.abort，H5 用 AbortController。

2.3 Mock 方案 ​

方案适用范围结论
msw（Service Worker）H5 开发 / 单测（msw/node）采用，仅 H5
LocalMockTransport全端小程序开发采用，直接调用 handler
json-server / 独立 Mock 服务跨端联调不采用，增加外部依赖且无法覆盖错误码分支

**结论：VITE_MOCK_MODE 三选一（msw / local / http），小程序端强制回落 local。

2.4 状态管理与持久化 ​

Pinia 按域拆分；pinia-plugin-persistedstate 自定义 uni storage 适配器，字段白名单 + 版本迁移。选择理由：多端 storage API 差异被适配器收敛，避免每端写一套持久化。

2.5 构建 ​

@dcloudio/vite-plugin-uni + Vite 5 + Vue 3.4。六端构建命令统一收口到 package.json，CI 后续只调用 build:<platform>。

4. 分包规划（按端可裁剪） ​

微信主包上限 2MB，首屏只保留 4 个 tabBar 页面。

6. 接口契约 ​

唯一事实来源：src/types/api.d.ts；错误码：src/types/error-code.ts。

ts
interface ApiResponse<T> { code: number; msg: string; data: T; serverTime?: number; traceId?: string }
interface PageResult<T> { list: T[]; total: number; page: number; pageSize: number }

约定：

  • 金额统一「分」（integer），展示层用 formatPrice 转换，禁止浮点运算。
  • 时间统一「毫秒时间戳」，倒计时必须使用服务端 serverTime 校准后的时间。
  • 枚举值全大写，新增只追加；删除字段需保留一个版本并标注 @deprecated。
  • 每域一个文件，请求/响应均有类型；Mock 数据复用同一套类型，禁止另写一份。
  • 异常分支必须覆盖：网络失败、超时、库存不足、未登录、支付失败、重复提交、团单已满。

7. Mock 与真实后端转接 ​

7.1 传输层 ​

实现环境说明
MswTransportH5 开发msw 拦截 XHR/fetch；单测用 msw/node
LocalMockTransport全端小程序开发直接调用 handler，返回统一响应；无 Service Worker 依赖
HttpTransport真机 / 生产真实接口，带签名、重试、去重、traceId

装配逻辑集中在 transport/index.ts：根据 MOCK_MODE + 运行期 grayApis 选择实现；msw 在小程序端强制回落 local。

7.2 Provider 抽象 ​

Provider业务签名Mock 实现真实实现（按端）
PaymentProvidercreatePayment(orderId) → 调起 → PayResult模拟收银台（成功/失败/取消可配置）+ 轮询微信/QQ uni.requestPayment、支付宝 my.tradePay、抖音 tt.pay、百度收银台；H5 仅 Mock
LiveProviderenterRoom(roomId) → 播放器能力占位视频 + 定时推进讲解商品微信/QQ/支付宝 live-player；抖音/百度/H5 video
SmsProvidersend(mobile) / verify(mobile, code)固定 123456 + 频控后端下发
LoginProvidersilentLogin() → LoginResult固定 userId/openidwx.login / my.getAuthCode / tt.login / qq.login / swan.login 换 sessionToken

工厂函数按 flag 装配（如 createPaymentProvider(flags)），业务代码零分支。参数差异全部收敛在 Provider 内部。

7.3 灰度转接 ​

  • 构建期：VITE_MOCK_MODE 只决定默认 Transport，不做运行时切换。
  • 运行期：grayApis.<domain>（如 gray.api.goods）按域切换 Mock/真实，两者不得混用。
  • 每次切换交付：受影响接口列表、差异点、回归路径、回滚开关。

8. 配置中心与灰度 ​

8.1 启动时序 ​

onLaunch
  ├─ 同步读本地缓存配置 → 立即得到可用默认值（不阻塞首屏）
  ├─ 并行请求 RemoteConfig（800ms 超时）
  └─ 合并远程 + 缓存 + 默认值 → 写入 store → 通知订阅者
       └─ Provider 工厂读取最新 flag，惰性装配

失败策略：超时/网络失败/缓存损坏 → 使用缓存 + 代码默认值，展示非阻断提示，禁止白屏。

8.2 分桶 ​

  • 登录后：hash(userId + flagKey) % 100，保证同一用户多端一致。
  • 未登录：首次启动写入本地持久化 UUID（ec:anonymousId），后续不再变更。
  • 白名单优先于百分比；percent=0 全关，percent=100 全量。

8.3 flag 治理 ​

注册表：src/config/flags.ts，每个 flag 必须有 owner、defaultValue、scope、expiresAt、description。判定入口统一 useFlag(key)，页面禁止直接读配置对象。

当前登记的 flag：

key默认作用
feature.livefalse直播入口与直播间
feature.groupfalse拼团
feature.seckillfalse秒杀
feature.distributionfalse分销
gray.api.goodsfalse商品域接口转接
gray.api.orderfalse订单域接口转接
ui.darkModetrue暗黑模式能力

8.4 三层灰度 ​

  1. 代码发布灰度：微信分阶段发布；支付宝/抖音按比例灰度；QQ/百度以体验版内测 + 全量两步走。全部记录在发版 runbook（阶段五）。
  2. 接口转接灰度：环境变量（构建期）+ gray.api.<domain>（运行期）。
  3. 业务功能灰度：远程 flag，秒级生效与回滚。

放量顺序：内测白名单 → 5% → 20% → 50% → 100%，每档独立可回滚。

8.5 一致性约束 ​

  • 双实现期数据结构向后兼容；flag 关闭后老数据仍可读。
  • 秒杀、拼团等强时序业务不做半开灰度，只能全量或全关。
  • 未开放功能的入口随 flag 隐藏或置灰，不做「点击后提示未开放」。
  • 埋点必须携带 flag_key + bucket + config_version；请求层自动透传桶号与配置版本。
  • 监控熔断：错误率/支付失败率超阈值自动关闭对应 flag。

9. 平台差异收敛 ​

详见 matrix.md。硬约束：

  • 条件编译只允许在 src/platform/ 与 NavBar、CanvasPoster 等极少数基础组件中。
  • src/pages/、src/components/business/、src/stores/、src/api/ 禁止 #ifdef，CI grep 校验。
  • 能力探测优先：API 存在性 → uni.canIUse → 平台兜底；不可用能力必须有可见降级 UI。
  • openid 各端不同，登录后统一换服务端 userId，分桶与业务主键只用 userId。
