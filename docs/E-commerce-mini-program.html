角色 ​

你是一名资深 uni-app 跨端开发工程师，具备大型电商小程序（日活百万级）的多端架构经验，熟悉 Vue3 Composition API、TypeScript 严格模式、微信/支付宝/抖音/QQ/百度等主流小程序平台底层机制、平台差异治理与性能优化，并有丰富的前端 Mock、灰度发布与真实后端交接经验。

目标 ​

使用 uni-app 从零构建一个可运行的多端电商小程序项目（微信 / 支付宝 / 抖音 / QQ / 百度小程序 + H5，六端平权全量适配）：

  1. 覆盖「浏览商品 → 加购 → 结算 → 支付 → 订单 → 售后」完整业务闭环，并延伸到直播、分销/拼团、秒杀三类高复杂度营销场景；
  2. 关键模块落地企业级工程实践（高阶组件封装、复杂交互、方案选型对比、主流 npm 库进阶用法）；
  3. 所有依赖后端的模块采用「契约先行 + 可插拔 Transport + Provider 抽象」的设计，先用 Mock 跑通完整链路，后端就绪后按接口灰度转接，业务代码零改动；
  4. 建立运行期远程配置与 feature flag 体系，使业务功能与接口转接都能按用户分桶灰度放量，并支持秒级回滚，不依赖发版。

技术栈（强制） ​

  • uni-app + Vue3 <script setup> + TypeScript（strict）+ Vite
  • 状态管理：Pinia（按业务域拆分 store，持久化用 pinia-plugin-persistedstate 并适配 uni storage）
  • UI 基座：uni-ui 或 uview-plus，业务组件在基座之上二次封装，不重复造基础轮子
  • 样式：rpx + 750 设计稿，设计变量（色板/字号/圆角/间距）集中定义
  • 请求层：luch-request 或自研封装，支持拦截器链、取消、重试、去重、埋点
  • Mock：H5 开发与单测用 msw（含 msw/node）；小程序开发用自研 LocalMockTransport
  • 配置与灰度：远程配置中心（Mock 接口或微信云开发配置）+ feature flag 判定体系
  • 测试：Vitest（工具函数、SKU 矩阵、状态机、flag 降级、核心 store）
  • 多端：微信 / 支付宝 / 抖音 / QQ / 百度小程序 + H5，六端平权全量适配
  • 平台差异收敛到 platform/ 适配层；条件编译只允许出现在适配层与极少量基础组件中，业务代码与页面禁止 #ifdef
  • 能力探测优先于平台判断：运行期检测 API 可用性（uni.canIUse / API 存在性），不支持的能力按能力矩阵降级

多端适配策略（强制） ​

目标平台 ​

  • 微信（MP-WEIXIN）、支付宝（MP-ALIPAY）、抖音（MP-TOUTIAO）、QQ（MP-QQ）、百度（MP-BAIDU）小程序 + H5，六端平权全量适配
  • 平台能力缺失不砍功能，按能力矩阵做定制降级方案，降级 UI 必须可见、可演示

平台适配层 ​

  • 所有平台差异收敛到 platform/ 目录，按能力域拆文件：login.ts / pay.ts / live.ts / share.ts / canvas.ts / system.ts（状态栏与胶囊）/ theme.ts / storage.ts / upload.ts，每端一个实现，构建期按条件编译选入
  • 条件编译只允许出现在 platform/ 与极少量基础组件（如 NavBar、CanvasPoster）中；pages/、components/business/、stores/、api/ 中禁止 #ifdef，CI grep 校验
  • 差异 API 一律封装后使用：如 uni.login、uni.requestPayment 各端参数结构差异，业务层只面对统一签名

身份与分桶一致性 ​

  • openid 各端不同，登录后统一换取服务端 userId；分桶用 hash(userId + flagKey) % 100，保证同一用户多端一致
  • 未登录场景用本地持久化 UUID（首次启动 uni.setStorage 写入后不再变更）作为分桶输入

A. 常见需求的主流工程方案 ​

  1. 登录态与路由守卫：LoginProvider 统一各端静默登录（wx.login / my.getAuthCode / tt.login / qq.login / swan.login）换取 sessionToken，token 持久化、静默续期、401/403 统一拦截、白名单、登录后跳回原页面
  2. 列表分页抽象：封装 usePagination（loading / finished / error / reset / loadMore），统一处理快速切 Tab 的竞态与重复请求
  3. 请求竞态与取消：过期请求打标丢弃；小程序用 RequestTask.abort，H5 用 AbortController
  4. 购物车数据一致性：跨页面同步、本地乐观更新 + 失败回滚、同 SKU 合并加购
  5. SKU 规格选择器：规格矩阵构建、不可选组合置灰、选中路径回溯、价格与库存区间计算
  6. 订单超时与倒计时：服务端时间校准（本地时钟偏移）、页面隐藏后恢复、超时自动刷新状态
  7. 支付结果确认：主动查询 + 轮询兜底 + 失败重试，防止“已支付但状态未同步”
  8. 表单与校验：Schema 驱动表单（配置 → 渲染 + 校验），支持动态增删地址项与联动显隐
  9. 图片上传：uni.compressImage 压缩、并发上限、失败重试、上传进度、裁剪入口
  10. 拼团状态机：状态流转定义、定时器推进成团、并发参团与超时退款分支
  11. 秒杀状态机：未开始/排队中/成功/售罄/失败五态，轮询与退避策略
  12. 权限与埋点：统一权限判断，曝光埋点按可见性触发而非 mounted 触发

B. 高阶组件封装（每个必须给出 props / emit / slot / 使用示例） ​

  • SkuPopup：规格选择弹层，内置矩阵逻辑，confirm 返回选中 SKU 与数量
  • VirtualList：长列表虚拟滚动，定高与动态高两种模式，暴露 scrollTo
  • WaterfallFlow：双列瀑布流，按列高最少插入，图片占位防跳动
  • PopupManager：弹层管理器，统一 z-index 栈、遮罩、滚动锁定、多弹层叠加与返回键处理
  • NavBar：自定义导航栏，适配各端状态栏高度；微信/QQ/抖音/百度按胶囊按钮位置避让，支付宝与 H5 按安全区兜底
  • CountDown：支持服务端时间校准与页面隐藏恢复
  • CanvasPoster：分享海报生成，绘制图片/文字/二维码，导出并保存相册
  • Skeleton / EmptyState / LoadMore：骨架屏与全站统一状态组件
  • FormSchema：配置化表单渲染器
  • LiveProductBar：直播间底部讲解商品条 + 抢购弹窗，支持商品切换推进
  • SeckillBar：秒杀价条与倒计时、库存进度条、三态按钮

C. 复杂交互与动效 ​

  • 加购抛物线飞入动画（贝塞尔曲线 + createAnimation，计算起止点与缩放）
  • 商品主图双指缩放与滑动切换手势
  • 购物车侧滑删除，含阈值判断与回弹
  • Tab 吸顶联动：导航吸顶 + 分类锚点联动高亮
  • 沉浸式导航栏：滚动渐变透明度、返回顶部、下拉放大头图
  • 富文本详情渲染：rich-text 节点解析、图片宽度自适应、视频占位
  • 直播间弹幕滚动与讲解商品切换动画
  • 多弹层叠加：规格弹层内打开优惠券弹层，验证层级与关闭顺序
  • 暗黑模式：主题变量切换 + 系统主题监听；微信/QQ 用 theme.json + CSS 变量双写，支付宝/抖音/百度/H5 用 CSS 变量 + prefers-color-scheme，全端保留手动开关兜底

D. 主流 npm 库的进阶用法（必须说明选型理由与踩坑规避） ​

  • dayjs：按需加载插件（relativeTime / utc / timezone / customParseFormat），处理订单时间与时区
  • lodash-es：按需导入与打包体积控制
  • @vueuse/core：useDebounceFn / useThrottleFn / useStorage 在小程序端的可用性边界与替代方案
  • pinia-plugin-persistedstate：自定义 uni storage 适配器、版本迁移、字段白名单
  • z-paging：与自研 usePagination 的取舍说明
  • echarts + lime-echart：小程序端图表渲染（用于 P1 数据看板）
  • uQRCode / qrcode：小程序端二维码生成与 Canvas 结合；微信/抖音/QQ 用 type="2d" 新接口，支付宝/百度走旧版 CanvasContext API，差异收敛在 platform/canvas.ts
  • crypto-js：接口签名与防重放（nonce + timestamp）
  • html2canvas：仅 H5 端海报生成，与小程序 Canvas 方案差异说明
  • pinyin-pro：搜索联想的中文拼音首字母匹配
  • msw / msw/node：H5 开发与单测的请求拦截，明确小程序端不可用及替代方案

E. 工程化与质量保障 ​

  • 多环境变量（dev/test/prod）+ Mock 开关，业务代码零侵入
  • 目录分层：pages/、components/（common / business）、composables/、stores/、api/、transport/、providers/、platform/、config/、mock/、utils/、types/、styles/
  • 分包：tabBar 页面留主包，详情/订单/售后/直播进分包；preloadRule 按端支持度配置，不支持的端构建期剔除
  • 性能：onReachBottom 分页、图片懒加载、setData 合并与最小化、长列表虚拟化、首屏骨架屏
  • 代码规范：ESLint + Prettier + husky + lint-staged + commitlint
  • 错误监控：onError / onUnhandledRejection / 接口异常统一上报，封装 track() 埋点 SDK
  • 配置治理：每个 flag 有 owner、默认值、生效范围、过期时间，到期强制清理
  • 打包上传：各端 CI 上传脚本统一封装（微信 miniprogram-ci、支付宝 minidev、抖音/QQ/百度对应官方 CLI），npm run upload:<platform> 一键执行，密钥通过环境变量注入，禁止硬编码

Mock 与真实后端转接策略（必须遵守） ​

分层原则 ​

  • 契约层：OpenAPI（或 types/api.d.ts）为唯一事实来源，字段、分页结构、错误码枚举与后端一致
  • 传输层：请求模块只依赖 Transport 接口，实现三套
    • MswTransport：H5 开发环境，基于 msw 拦截 XHR
    • LocalMockTransport：全端小程序开发环境，直接调用 handler 返回数据（小程序无 Service Worker，MSW 不可用）
    • HttpTransport：真机与生产，真实接口
  • 平台能力层：支付、直播、短信、分享统一抽象为 Provider 接口
    • PaymentProvider：Mock 实现走模拟支付弹窗 + 结果轮询；真实实现按端调起支付（微信/QQ uni.requestPayment、支付宝 my.tradePay、抖音 tt.pay、百度收银台），参数差异收敛在 Provider 内部，H5 无真实支付走 Mock 收银台演示
    • LiveProvider：Mock 实现用 video 组件播占位流；真实实现按端接入（微信/QQ/支付宝 live-player，抖音/百度/H5 降级 video 或第三方播放器）
    • SmsProvider：Mock 固定验证码 + 频控；真实实现走后端下发
    • LoginProvider：Mock 实现返回固定 openid；真实实现统一封装各端静默登录票据（wx.login / my.getAuthCode / tt.login / qq.login / swan.login）换取 sessionToken
  • 切换方式：构建期用环境变量 VITE_MOCK_MODE（msw / local / http）选择 Transport；运行期用接口级白名单 gray.api.<domain> 控制单个接口的 Mock 与真实切换，业务代码零改动

各模块要求 ​

  • 分销/拼团：Mock 侧实现完整关系链与团单状态机，定时器推进成团，必须覆盖成团失败与超时退款分支
  • 秒杀：Mock 侧实现活动时间、库存、排队 token、结果轮询与五态 UI；文档中明确标注「并发与防超卖能力不可通过 Mock 验证」
  • 直播：直播间列表、讲解商品上下架联动、购买弹窗、点赞弹幕均需 Mock；音视频经 Provider 降级为占位视频
  • 支付：下单、参数下发、结果查询、失败重试、重复提交拦截全部 Mock；禁止在前端实现签名逻辑
  • 短信：发送、频控、倒计时、校验 Mock，Mock 验证码统一 123456 并在 UI 明确提示
  • 时间：所有倒计时使用服务端 serverTime + 本地时钟偏移校准，禁止直接用本地时间
  • 幂等：重复下单/重复参团/重复提交必须在 Mock 阶段返回真实错误码并驱动 UI 分支

灰度转接 ​

  • 维护接口白名单，后端交付一个模块就切换一个，不做一次性全量切换
  • 每次切换需给出：受影响的接口列表、Mock 与真实的差异点、回归验证路径

灰度发布与配置下发（必须实现） ​

三层灰度 ​

  • 代码发布灰度：按端使用平台能力（微信「分阶段发布」、支付宝/抖音灰度发布按比例放量；QQ/百度不支持按比例时以体验版内测 + 全量两步走替代），不依赖热更新，各端放量动作统一记录在发版 runbook
  • 接口转接灰度：VITE_MOCK_MODE 为构建期环境开关；gray.api.<domain> 为运行期接口级白名单，两者不得混用
  • 业务功能灰度：远程配置 feature flag，运行期秒级生效与回滚

集成点 ​

  • RemoteConfig：onLaunch 先读本地缓存 → 并行拉远程（800ms 超时）→ 合并并通知订阅者；失败走缓存 + 默认值，禁止阻塞启动或导致白屏
  • 分桶：hash(userId + flagKey) % 100（openid 各端不同，统一用服务端 userId；未登录用本地持久化 UUID），稳定分桶，禁止随机；多端一致
  • 判定入口：统一 useFlag(key)，页面不得直接读配置对象
  • Provider 装配：createPaymentProvider(flags) 等工厂函数按 flag 选择实现，业务代码零分支
  • 请求层自动透传桶号与配置版本；埋点必须携带 flag_key + bucket + config_version
  • 监控熔断：错误率、支付失败率超阈值自动关闭对应 flag，不依赖人工

放量流程 ​

内测白名单 → 5% → 20% → 50% → 100%，每档独立可回滚且不依赖发版；每档记录观察指标与回滚动作

一致性约束 ​

  • 双实现期数据结构保持向后兼容，flag 关闭后老数据必须可读
  • 秒杀、拼团等强时序业务不做半开灰度，只能全量或全关
  • 未开放功能的入口随 flag 同步隐藏或置灰，不采用「点击后提示未开放」
  • 每个 flag 必须有 owner、默认值、生效范围、过期时间，到期强制清理
  • 多实验分层正交，避免组合爆炸与相互干扰

接口与数据契约 ​

  • Mock 数据放 /mock，与 handler 共用同一套类型定义
  • 统一响应 { code: number, msg: string, data: T }，分页 { list, total, page, pageSize }
  • 错误码使用后端真实枚举，集中定义在 types/error-code.ts，禁止自造
  • 接口按业务域拆文件，请求与响应均有 TS 类型
  • 必须覆盖异常分支：网络失败、超时、库存不足、未登录、支付失败、重复提交、团单已满

交付方式（分阶段，每阶段结束暂停等我确认） ​

  1. 阶段一：架构方案 + 目录结构 + 分包规划 + 设计变量 + 契约定义 + 企业级场景清单（列出要落地的 8+ 个场景及选型结论，不写业务代码）
