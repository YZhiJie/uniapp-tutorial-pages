24.2 进阶应用：符号表、Trace 串联与告警分级 ​

有了事件还不够：错误要能还原到源码行、一次用户操作要能串起多个服务、告警要能分级到人。这三件事决定可观测性是否真正可用。

一、符号表自动上传 ​

符号表缺失时，堆栈只剩地址与混淆后的类名，等于没有日志。四类产物与上传方式在 14.3 崩溃监控 已给出完整命令，这里补上「与发布流程绑定」的部分：

yaml
- name: 上传 H5 sourcemap
  run: |
    npx @sentry/cli releases new "shop-h5@${VERSION}"
    npx @sentry/cli releases files "shop-h5@${VERSION}" \
      upload-sourcemaps ./dist/build/h5 --url-prefix '~/assets' --ext js --ext map
    npx @sentry/cli releases finalize "shop-h5@${VERSION}"
  env:
    SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}

三条硬约束：

约束说明
release 名一致运行时 Sentry.init({ release }) 必须与上传时完全相同
上传失败即阻断sentry-cli 非零退出码直接让 job 失败，避免发出无法定位的版本
产物不公开.map 不能随 CDN 发布，否则源码泄露

App 端同理：Android 传 mapping.txt，iOS 传 .dSYM；wgt 热更新要为每个 wgt 版本单独建 release。

二、Trace 串联：一次操作贯穿前后端 ​

2.1 客户端生成 traceId ​

ts
// src/services/trace.ts
export function newTraceId() {
  const rand = Math.random().toString(16).slice(2, 10)
  return `${Date.now().toString(16)}${rand}`.slice(0, 24)
}

export const traceId = newTraceId()

请求头带上，服务端日志与链路追踪系统继续传递：

ts
uni.request({
  url: '/api/orders',
  method: 'POST',
  data: payload,
  header: {
    'X-Trace-Id': traceId,
    'X-Request-Id': `${traceId}-${Date.now()}`
  },
  success: (res) => {
    // 服务端回传 requestId，便于精确检索
    telemetry.track('api_order_create_success', {
      traceId,
      requestId: res.header['X-Request-Id'],
      durationMs: Date.now() - startedAt
    })
  }
})

2.2 服务端返回并记录同一个 traceId ​

ts
// server/middleware/trace.ts
import { randomUUID } from 'node:crypto'

export function trace(req, res, next) {
  const traceId = req.headers['x-trace-id'] ?? randomUUID()
  const requestId = req.headers['x-request-id'] ?? randomUUID()
  req.trace = { traceId, requestId }
  res.setHeader('X-Trace-Id', traceId)
  res.setHeader('X-Request-Id', requestId)
  logger.info({ traceId, requestId, path: req.path }, 'request_start')
  next()
}

一条链路的最小信息集：

text
客户端点击 → traceId
  ├─ API 请求（url / status / duration）
  ├─ 服务端日志（traceId / requestId / service）
  ├─ 下游调用（DB / 支付渠道）
  └─ 客户端结果事件（成功 / 失败 / 重试）

排查时用 traceId 一次串起全部日志，而不是靠时间戳猜。

三、告警分级：不是所有错误都值得叫醒人 ​

级别触发条件通知方式响应时限
P0支付全链路失败、登录不可用、崩溃率突增 > 1%电话 + 群 @所有人5 分钟
P1核心接口错误率 > 5%、某渠道支付成功率骤降群机器人 + 值班人30 分钟
P2单个页面错误率升高、慢请求占比上升日报 / 看板次工作日
P3长尾错误、低频机型兼容问题周报排期处理

避免告警疲劳的三条规则：

  1. 按影响面聚合，不按单条错误报警（例如「同一错误 5 分钟内 > 100 次」）。
  2. 告警必须带上下文：版本、页面、机型、traceId、最近一次发布。
  3. 每条告警有归属人，无人认领的告警 24 小时后自动升级。

3.1 基于错误预算的发布门禁 ​

text
SLO：支付成功率 ≥ 99.5%（滚动 7 天）
错误预算 = 0.5% × 总支付请求数
当 7 天错误预算消耗 > 50%：暂停非紧急发布
当消耗 > 100%：冻结发布，直到恢复

四、采样与数据治理 ​

数据类型采样保留说明
错误100%180 天必须全量
支付 / 订单结果100%365 天对账与审计
页面行为10–50%90 天按用户稳定分桶
性能指标20%90 天分位数聚合
调试日志仅开发/灰度7 天生产关闭 debug

采样要按用户稳定分桶，否则同一用户的漏斗数据会断裂：

ts
function isSampled(userId: string, rate: number) {
  let hash = 0
  for (const ch of userId) hash = (hash * 31 + ch.charCodeAt(0)) | 0
  return Math.abs(hash) % 100 < rate * 100
}

五、看板的最小集合 ​

看板核心图表
稳定性崩溃率（JS/Native/ANR）、Top 10 崩溃、版本对比
可用性核心接口成功率、P95 延迟、支付渠道成功率
体验冷启动分位、首屏时长、setData 峰值、页面错误率
发布版本分布、灰度比例、回滚事件

每张图都要能下钻到「版本 → 页面 → 机型 → traceId」。

六、验收标准 ​

bash
# 1. 用 traceId 串联
curl -H "X-Trace-Id: test-trace-001" https://api.example.com/health -i
# 期望：响应头回传同一个 X-Trace-Id

# 2. 符号表 release 对齐
npx @sentry/cli releases list | grep "shop-h5@${VERSION}"

自查：

  • 任取一个线上错误，能在 5 分钟内定位到源码文件与行号。
  • 任取一次支付失败，能用 traceId 串起客户端、服务端、渠道三方日志。
  • P0 告警 5 分钟内有人响应，且告警内容包含版本与影响面。
  • 采样后的漏斗数据仍能还原单个用户路径（按用户稳定分桶）。
