10.1 基础入门：社交应用架构与消息模型 ​

社交应用与电商的本质差异是实时性：消息推送、会话排序、未读数、在线状态都要求数据在变化时尽快到达。

页面地图 ​

text
pages/
├─ index/index            Feed 流（tabBar）
├─ feed/
│  ├─ detail              动态详情（评论楼中楼）
│  └─ publish             发布动态（图片/视频）
├─ message/
│  ├─ list                会话列表（tabBar）
│  └─ chat                聊天页
├─ contact/list           通讯录/好友
├─ mine/index             我的（tabBar）
└─ login/index
subPackages:
└─ pages/profile/         他人主页、设置、黑名单等低频页

三个核心模型 ​

Feed（动态） ​

ts
export interface Feed {
  id: string
  author: { id: string; nickname: string; avatar: string }
  type: 'text' | 'image' | 'video'
  content: string
  media: MediaAsset[]
  likeCount: number
  commentCount: number
  liked: boolean
  createdAt: string
}

Feed 列表的关键技术是**游标分页（cursor-based）**而不是页码：

ts
export interface FeedQuery {
  cursor?: string   // 上一页最后一条的 id/时间戳
  size: number
  tab: 'recommend' | 'follow'
}
export interface FeedPage {
  list: Feed[]
  nextCursor: string | null
}

原因：Feed 会不断插入新内容，页码分页会出现重复/跳过；游标分页以「某条内容」为锚点，结果稳定。

会话（Conversation） ​

ts
export interface Conversation {
  id: string                 // 会话 id（单聊通常由双方 id 派生）
  type: 'single' | 'group'
  peerName: string
  peerAvatar: string
  lastMessage?: MessageBrief
  unread: number
  updatedAt: string
  muted: boolean             // 免打扰
}

会话列表始终按 updatedAt 倒序——每收到一条消息就要重排，所以它本质是一个有序集合，不是普通数组翻页。

消息（Message） ​

ts
export type MessageType = 'text' | 'image' | 'system' | 'recall'

export interface Message {
  id: string                 // 客户端生成 uuid（临时 id）
  serverId?: string          // 服务端确认后回填
  conversationId: string
  fromId: string
  type: MessageType
  content: string
  createdAt: number
  status: 'sending' | 'sent' | 'delivered' | 'read' | 'failed'
}

设计要点：

  • 发送即上屏：先插入 sending 状态消息，不等待服务端；失败显示重发。
  • 客户端 id 用于去重（ack 回来按 clientId 匹配），服务端 id 用于撤回等操作。
  • 撤回消息是独立类型（recall）而不是删除，保证双方历史一致。

实时性方案选型 ​

方案实时性电量/成本适用
HTTP 轮询秒级，差高（大量空请求）兼容性兜底
长轮询（long polling）近实时中WebSocket 不可用时降级
WebSocket毫秒级低IM 主链路
小程序订阅消息事件触发低离线通知（需用户订阅）
App 推送（UniPush）事件触发低App 离线/后台通知

结论：在线走 WebSocket，离线走平台通知（订阅消息/UniPush），两者配合。

各端 WebSocket 能力差异 ​

  • uni-app 提供统一 API：uni.connectSocket 返回 SocketTask，或直接 new WebSocket()（H5/部分端支持情况不同，跨端统一用 uni API）。
  • 小程序同时存在的 Socket 连接数量有限（微信端通常 5 个），所以全局只维护一条连接，消息中带通道字段复用。
  • App 退到后台后连接会被系统挂起，消息到达依赖厂商推送；回前台需要重连 + 拉取断连期间消息。
  • H5 受浏览器生命周期限制，标签页不可见时可降低心跳频率。

整体架构 ​

text
                    ┌──────────────────────┐
                    │   IM Gateway (WSS)   │
                    └──────────┬───────────┘
               鉴权握手(token)  │  消息帧(JSON)
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
  stores/im.ts          platforms/push         pages/message/chat
  连接/心跳/重连/         订阅消息/UniPush       会话视图（订阅 store）
  消息分发/未读聚合        离线通知适配

分层原则：

  • 页面只渲染 store，不直接操作 Socket。
  • Socket 客户端封装为单例模块（连接管理 + 事件订阅）。
  • 平台通知（小程序订阅消息、App UniPush）走适配层，接口统一为 requestNotifyPermission()。

未读数的三级模型 ​

  1. 消息级未读：聊天页内当前会话的已读位置。
  2. 会话级未读：每个 conversation 的 unread 计数。
  3. 全局未读：免打扰会话不计数（红点 vs 数字的产品策略要明确）。

更新路径：收到消息 → IM store 更新消息列表 → 更新会话 unread → 聚合全局未读 → 更新 tabBar 角标。任何一级都不要让页面自己计数。

数据存储策略 ​

  • 近期会话与消息：内存 store；聊天记录持久化用本地数据库（App SQLite、H5 IndexedDB、小程序可用本地存储分片或插件）。
  • 分页拉取历史消息：进入聊天页先加载本地最近 20 条，再向服务端增量同步。
  • 图片视频：消息只存 URL/尺寸，不入库二进制。

练习 ​

  1. 画出「A 给 B 发消息」完整时序：发送方上屏、服务端存储、推送 B、B 在线/离线两条路径、回执。
  2. 用本文模型设计群聊：哪些字段需要增加（at 列表、群成员版本），会话列表排序逻辑是否变化？
  3. 调研微信小程序「一次性订阅消息」与「长期订阅消息」的类目限制，列出你的产品需要申请哪些模板。
