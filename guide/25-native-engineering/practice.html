25.3 实战案例：插件体积、初始化耗时与产物校验 ​

插件上线前最容易被忽略的两个指标是体积和初始化耗时：前者拖慢首包下载，后者拖慢冷启动。本篇把它们和产物完整性一起做成可执行门禁。

一、体积预算：先定上限，再谈优化 ​

仓库根目录的 native-budget.json 定义单插件产物上限：

json
{
  "android": {
    "maxKb": 800
  },
  "ios": {
    "maxKb": 4096
  }
}

scripts/native-check.mjs 在发现产物后会逐项比对，超出即失败：

bash
pnpm native:check
# 有产物时的输出示例：
#  • UniNativeDemo android uniapp-demo/nativeplugins/UniNativeDemo/android/UniNativeDemo.aar  612.4 KB  sha256=3f2a9c1d8e4b…
#  • UniNativeDemo ios     uniapp-demo/nativeplugins/UniNativeDemo/ios/UniNativeDemo.framework  2048.7 KB  sha256=n/a
# ❌ UniNativeDemo aar 体积 912.0 KB 超过预算 800 KB

预算怎么定：

依据做法
宿主主包上限小程序 2MB / App 安装包预算倒推
同类插件基线取成熟插件体积的 80% 作为首版预算
增长规则每季度评审一次，只允许在评审后上调

Android 体积排查顺序：

bash
# 1. 查看 aar 内各条目大小（解压后按体积排序）
unzip -l UniNativeDemo.aar | sort -k1 -n -r | head -20

# 2. 确认依赖没有被打进 aar（compileOnly 才是正解）
./gradlew :dependencies --configuration releaseRuntimeClasspath

# 3. 检查是否误带 so / 资源
unzip -l UniNativeDemo.aar | grep -E '\.so$|res/'

iOS 侧关注 framework 是否误带调试符号与多余架构：

bash
# 只允许 arm64（模拟器架构不应进发布包）
lipo -info UniNativeDemo.framework/UniNativeDemo

# 去掉调试符号后再看体积
dsymutil --strip UniNativeDemo.framework/UniNativeDemo 2>/dev/null || true
du -sh UniNativeDemo.framework

二、初始化耗时：埋点而不是猜 ​

插件初始化通常发生在基座加载阶段，必须用原生时钟测量，不能用 JS Date.now() 推断。

Android 侧：

java
// NativeDemoModule.java（片段）
private static final String TAG = "UniNativeDemo";

public NativeDemoModule() {
    long start = SystemClock.elapsedRealtimeNanos();
    // 初始化逻辑：注册监听、创建线程池、加载配置
    long costMs = (SystemClock.elapsedRealtimeNanos() - start) / 1_000_000;
    Log.i(TAG, "init_cost_ms=" + costMs);
}

iOS 侧：

objc
// NativeDemoModule.m（片段）
- (instancetype)init {
    CFAbsoluteTime start = CFAbsoluteTimeGetCurrent();
    self = [super init];
    if (self) {
        // 初始化逻辑
    }
    NSLog(@"UniNativeDemo init_cost_ms=%.2f", (CFAbsoluteTimeGetCurrent() - start) * 1000);
    return self;
}

采集命令（需真机）：

bash
# Android：过滤插件日志并记录冷启动总耗时
adb logcat -c
adb shell am force-stop com.example.uniappdemo
adb shell am start -W -n com.example.uniappdemo/.MainActivity
adb logcat -d | grep -E "init_cost_ms|Displayed"
bash
# iOS：用 Instruments 的 Time Profiler / App Launch 模板
xcrun xctrace record --template 'App Launch' \
  --device <UDID> --launch com.example.uniappdemo \
  --output native-launch.trace

验收口径：

指标建议阈值说明
单插件 init≤ 20ms超过则把同步初始化改为懒加载
插件总 init 增量≤ 50ms多插件叠加后的冷启动增量
首次调用耗时≤ 100ms不含网络与权限弹窗

优化顺序：懒加载 → 合并初始化 → 异步预热。不要一上来就开线程，线程创建本身也有成本。

三、产物完整性：基线 + SHA-256 ​

二进制产物无法 code review，必须靠哈希锁定。流程：

bash
# 1. 构建 Android aar 并放入插件目录
cd uniapp-demo/nativeplugins/UniNativeDemo/android
./gradlew assembleRelease
cp build/outputs/aar/UniNativeDemo-release.aar ../UniNativeDemo.aar

# 2. 构建 iOS framework（macOS + Xcode）
cd ../ios
xcodebuild -project UniNativeDemo.xcodeproj -scheme UniNativeDemo \
  -configuration Release -sdk iphoneos -derivedDataPath ./build build
cp -R build/Build/Products/Release-iphoneos/UniNativeDemo.framework ./

# 3. 生成基线（提交 native-artifacts.json，不提交二进制）
cd -
pnpm native:check -- --write

# 4. 之后每次发布校验
pnpm native:check:strict

native-artifacts.json 记录每个产物的路径、大小与 SHA-256。任何人替换了 aar/framework，native:check:strict 都会失败：

text
❌ .../UniNativeDemo.aar SHA-256 与基线不一致，产物疑似被替换

更新基线的唯一合法场景：有意的版本发布，且同一次提交里包含版本号变更与构建日志。

四、CI 模板（需构建环境） ​

以下流水线在具备 Android SDK / Xcode 的 runner 上才能执行，本仓库未启用：

yaml
name: native-plugin

on:
  push:
    paths:
      - 'uniapp-demo/nativeplugins/**'
      - 'native-sdk.lock.json'
      - 'native-budget.json'

jobs:
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - run: pnpm install --frozen-lockfile
      - run: pnpm exec vitest run tests/native-contract.test.ts
      - run: pnpm native:check

  android:
    runs-on: ubuntu-latest
    needs: contract
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
      - uses: android-actions/setup-android@v3
      - name: Build aar
        working-directory: uniapp-demo/nativeplugins/UniNativeDemo/android
        run: |
          gradle wrapper --gradle-version 8.9
          ./gradlew assembleRelease
          cp build/outputs/aar/UniNativeDemo-release.aar ../UniNativeDemo.aar
      - run: pnpm native:check:strict

  ios:
    runs-on: macos-14
    needs: contract
    steps:
      - uses: actions/checkout@v4
      - name: Build framework
        working-directory: uniapp-demo/nativeplugins/UniNativeDemo/ios
        run: |
          xcodebuild -project UniNativeDemo.xcodeproj -scheme UniNativeDemo \
            -configuration Release -sdk iphoneos -derivedDataPath ./build build
          cp -R build/Build/Products/Release-iphoneos/UniNativeDemo.framework ./
      - run: pnpm native:check:strict

三个注意点：

  1. iOS job 必须用 macOS runner，且需安装对应 Xcode 版本（与 native-sdk.lock.json 一致）。
  2. native-artifacts.json 在 CI 中只校验不生成；生成基线必须在本地发布流程完成。
  3. Android 构建依赖 HBuilderX 离线 SDK 的 weex_core.jar，CI 需提前准备该文件或改用私有 Maven。

五、受限项与验证边界 ​

项目当前状态原因需要谁 / 什么
aar 构建❌ 缺离线 SDKGradle 9.7.1 + JDK 17 已执行到 extractReleaseAnnotations，因 android/libs/weex_core.jar 不存在而失败（10m49s）HBuilderX 离线 SDK 的 weex_core.jar（放入 android/libs/）
framework 构建⛔ 未产出源码可用 DCUniBase 头文件通过 clang -fsyntax-only；但插件目录没有 .xcodeproj，无法 Archive补齐 Xcode 工程与签名配置
真机加载插件未验证需要 HBuilderX 自定义基座与设备HBuilderX + 真机
初始化耗时未采集依赖真机日志真机 + adb / Instruments
体积数值未采集无 aar/framework 产物双端构建完成后由 native:check 输出
iOS 上架未验证需要 Apple 账号与证书Apple Developer 账号

实际验证记录（2026-11-04）：

bash
# iOS 源码语法验证（真实执行，退出码 0）
mkdir -p /tmp/ios-include
ln -sfn "$HBuilderX/.../DCUniBase.framework/Headers" /tmp/ios-include/WeexSDK
clang -fsyntax-only -fobjc-arc -target arm64-apple-ios13.0-simulator \
  -isysroot "$(xcrun --sdk iphonesimulator --show-sdk-path)" \
  -I /tmp/ios-include \
  uniapp-demo/nativeplugins/UniNativeDemo/ios/NativeDemoModule.m
# 结果：仅 1 条 deprecated 警告，无错误

Android 构建的阻塞证据：首次构建被本机 ~/.gradle/init.gradle 的仓库模式拦截；改用隔离 GRADLE_USER_HOME=/tmp/gradle-home-verify 与 JDK 17 后，Gradle 自动安装 SDK 34，执行到 :extractReleaseAnnotations 时明确报错：

text
File/directory does not exist: .../android/libs/weex_core.jar
BUILD FAILED in 10m 49s

这不是脚本问题，而是缺少 HBuilderX 离线 SDK 提供 weex_core.jar。日志：/tmp/gate-evidence/android-build2.log。

明确标注「需真机验证」的项目，验证步骤已在上文给出，不应以「CI 绿了」替代。

七、自查 ​

  • 插件体积有明确预算，且超出会让流水线失败。
  • 基线文件随版本提交，二进制不进 Git。
  • 初始化耗时来自原生时钟与真机日志，不是估算。
  • 所有「需真机」项都有执行人与证据记录。
  • 升级 SDK 后重新生成基线，并解释体积变化。
