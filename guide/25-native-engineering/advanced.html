25.2 进阶应用：宿主 SDK 对齐、双端契约与升级回归 ​

插件能编译，不代表能在宿主里跑。真正导致线上事故的，通常是三件事：宿主 SDK 版本变了、双端契约漂移了、升级后没人回归。

一、版本对齐：把「兼容」写成锁文件 ​

原生插件同时受四层版本约束：

层关键版本不对齐的后果
uni-app 宿主HBuilderX 版本、uni-app 运行时离线打包基座与插件 ABI 不匹配
Android 构建compileSdk / minSdk / targetSdk、AGP、JDKaar 能编过，基座加载失败
iOS 构建Xcode、deploymentTarget、架构framework 缺 arm64 切片，真机无法加载
插件自身version、versionCode、ABI灰度与回滚无法按版本定位

仓库根目录用 native-sdk.lock.json 锁定这些值：

json
{
  "schemaVersion": 1,
  "uniapp": "3.2.0",
  "android": {
    "compileSdk": 34,
    "minSdk": 21,
    "targetSdk": 34,
    "agp": "8.6.1",
    "jdk": 17
  },
  "ios": {
    "deploymentTarget": "13.0",
    "arch": "arm64",
    "xcode": "15.4"
  }
}

scripts/native-check.mjs 会读取它并逐项比对 android/build.gradle 与插件声明：

bash
pnpm native:check
# 若 gradle 写 compileSdk 33，而锁文件是 34：
# ❌ UniNativeDemo compileSdk=33 与 native-sdk.lock.json 的 34 不一致

升级宿主 SDK 时，正确顺序是：

  1. 先改 native-sdk.lock.json（评审一次）；
  2. 再改各插件 build.gradle / xcconfig；
  3. 重新构建双端产物；
  4. 跑契约测试与真机回归；
  5. 最后才更新宿主 App 的基座。

反过来「先升宿主、再看插件报什么错」会让问题混在一起，无法定位。

二、契约：静态检查 + 运行期验证 ​

2.1 契约文件 ​

把「JS 能调什么」写成机器可读的契约，放在插件目录：

json
{
  "module": "UniNativeDemo",
  "methods": [
    { "name": "getDeviceInfo", "args": [], "returns": ["platform", "model", "brand"] },
    { "name": "showToast", "args": ["text"], "returns": [] }
  ],
  "component": {
    "name": "NativeDemoView",
    "events": ["onNativeClick"]
  }
}

契约文件是唯一事实来源：Android、iOS、教程示例、宿主调用页都应对齐它。

2.2 静态契约测试（本仓库可直接运行） ​

tests/native-contract.test.ts 不依赖真机，直接比对声明与源码：

bash
pnpm exec vitest run tests/native-contract.test.ts

核心断言（节选）：

ts
const androidMethods = [...androidModule.matchAll(/public\s+void\s+(\w+)\s*\(/g)].map((m) => m[1])
const iosSelectors = [...iosModule.matchAll(/WX_EXPORT_METHOD\(@selector\((\w+):/g)].map((m) => m[1])

expect(androidMethods.sort()).toEqual(iosSelectors.sort())
expect(androidMethods).toContain('getDeviceInfo')
expect(androidMethods).toContain('showToast')

这类测试能在 1 秒内发现「只改了一端」的低级错误，但它不能证明方法在真机上可用。

2.3 运行期契约测试（需自定义基座 + 真机） ​

运行期验证必须走 uni-automator，前置条件明确：

前置说明
HBuilderX已安装，且 CLI 可用
自定义调试基座已勾选 UniNativeDemo 并打包
Android/iOS 真机已连接，且与基座签名匹配
测试账号能进入原生插件演示页
js
// tests/e2e/native-contract.e2e.js（由 uni-automator 执行，需真机）
const assert = require('assert')

async function run() {
  const page = await program.currentPage()
  await page.waitFor(2000)

  const plugin = uni.requireNativePlugin('UniNativeDemo')
  assert.ok(plugin, '插件未注册，检查基座是否勾选 UniNativeDemo')

  const info = await new Promise((resolve, reject) => {
    plugin.getDeviceInfo({}, (res) => {
      if (res && res.platform) resolve(res)
      else reject(new Error('getDeviceInfo 返回结构不符合契约'))
    })
  })
  assert.ok(info.model, 'model 字段缺失')

  await page.callMethod('triggerToast')
  await page.waitFor(500)
}

run().catch((error) => {
  console.error(error)
  process.exit(1)
})

本仓库没有可用的真机与自定义基座，因此该用例未纳入 CI。执行方式见 20.3 实战案例 的 uni-automator 章节。

三、SDK 升级回归清单 ​

每次升级 HBuilderX / uni-app 离线 SDK，按下面矩阵执行。标注「需真机」的项目无法在纯 CI 中完成，必须人工确认：

检查项自动化命令 / 操作通过标准
锁文件与 Gradle 对齐✅pnpm native:check无版本不一致错误
双端声明一致✅pnpm exec vitest run tests/native-contract.test.ts5 项断言通过
aar/framework 可构建⚠ 需构建环境./gradlew assembleRelease、xcodebuild产物生成
产物未被替换✅pnpm native:check:strictSHA-256 与基线一致
基座加载插件❌ 需真机自定义基座运行JS 能拿到 plugin 对象
module 方法返回结构❌ 需真机运行期契约用例字段与契约一致
component 事件❌ 需真机点击原生区域onNativeClick 触发
权限与降级❌ 需真机拒绝权限后再调用返回明确错误码，不崩溃
冷启动耗时❌ 需真机adb shell am start -W增量在预算内
包体积✅pnpm native:check:strict不超过 native-budget.json

升级回归的最小证据包：锁文件 diff、契约测试输出、双端产物 SHA-256、真机截图/日志、版本号。缺任何一项都不算完成。

四、把「降级」写进契约 ​

原生能力不是永远可用。契约里要显式定义失败形态：

场景期望行为
插件未安装（H5/小程序）JS 侧走降级实现，不抛异常
权限被拒绝返回 { code: 'PERMISSION_DENIED' }，由业务层提示
宿主版本过低返回 { code: 'SDK_VERSION_UNSUPPORTED' }，引导升级
原生初始化失败返回 { code: 'INIT_FAILED', message }，上报但不崩溃
ts
// src/native/demo.ts
type NativeResult<T> = { code: 'OK'; data: T } | { code: string; message?: string }

export async function safeGetDeviceInfo(): Promise<NativeResult<{ model: string }>> {
  // #ifdef APP-PLUS
  const plugin = uni.requireNativePlugin('UniNativeDemo')
  if (!plugin) return { code: 'PLUGIN_NOT_FOUND' }
  return new Promise((resolve) => {
    plugin.getDeviceInfo({}, (res: { model?: string; code?: string }) => {
      if (res?.model) resolve({ code: 'OK', data: { model: res.model } })
      else resolve({ code: res?.code ?? 'INIT_FAILED' })
    })
  })
  // #endif
  // #ifndef APP-PLUS
  return { code: 'PLUGIN_NOT_FOUND' }
  // #endif
}

这样 H5 与小程序端不需要知道插件存在，App 端也不会因为原生异常直接白屏。

五、验收标准 ​

bash
# 1. 版本与声明
pnpm native:check

# 2. 静态契约
pnpm exec vitest run tests/native-contract.test.ts

# 3. 发布前（需先构建双端产物）
pnpm native:check:strict

# 4. 真机回归（需自定义基座）
# HBuilderX → 运行 → 运行到手机或模拟器 → 选择自定义调试基座

自查：

  • 升级 SDK 前先改锁文件，且锁文件变更单独评审。
  • 双端新增方法时，契约文件、两端源码、静态测试同时更新。
  • 任何「需真机」项都有明确的执行人与证据，不靠口头确认。
  • 降级路径在 H5/小程序端真实跑过，不只是写了条件编译。
