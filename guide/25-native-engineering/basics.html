25.1 基础入门：原生插件 monorepo 与版本单一来源 ​

一个插件写完后，真正难的是「三个月后还能不能重新构建出同一个包」。当插件开始变多（支付、地图、推送、扫码），每个都要维护 Android aar、iOS framework、双端声明和宿主版本，单仓库复制粘贴会迅速失控。

本篇用仓库内已有的 UniNativeDemo 作为真实样本，搭一个最小可用的插件 monorepo。

一、为什么是 monorepo，而不是「一个插件一个仓库」 ​

方案优点代价
单插件单仓库权限隔离清晰宿主版本、构建脚本、契约文件各存一份，升级要逐个改
插件 monorepo版本、脚本、契约、CI 模板共享需要目录规范与门禁，否则同样会乱

推荐把「宿主 App」与「插件源码」放在同一个工作区，二进制产物仍然按插件目录隔离：

text
native/
├── pnpm-workspace.yaml
├── package.json                    # 工作区脚本：native:check / native:contract
├── native-sdk.lock.json            # 宿主 SDK 版本锁
├── native-budget.json              # 插件产物体积预算
├── native-artifacts.json           # 产物 SHA-256 基线（构建后生成）
├── plugins/
│   └── uni-native-demo/
│       ├── package.json            # 插件声明（id / version / 双端 class）
│       ├── android/
│       │   ├── build.gradle
│       │   └── src/main/java/...
│       ├── ios/
│       │   ├── NativeDemoModule.h/.m
│       │   └── NativeDemoView.h/.m
│       └── contract/
│           └── plugin-contract.json
└── scripts/
    ├── native-check.mjs            # 元数据 + 产物校验
    └── sync-native-version.mjs     # 版本号单一来源（可选）

工作区声明：

yaml
# pnpm-workspace.yaml
packages:
  - 'plugins/*'
  - 'fixtures/*'

宿主工程不必搬进 monorepo：本地开发时把插件目录软链到宿主 nativeplugins/，CI 时复制构建产物即可。

bash
# 本地联调：宿主读取的仍是 nativeplugins/ 目录
ln -s ../../native/plugins/uni-native-demo uniapp-demo/nativeplugins/uni-native-demo

# 撤销软链
rm uniapp-demo/nativeplugins/uni-native-demo

Windows 请用目录联接：mklink /J uniapp-demo\nativeplugins\uni-native-demo native\plugins\uni-native-demo。

二、版本号只有一个来源 ​

插件版本号必须只有一处可写，其他位置都是派生值：

位置用途写入方式
plugins/*/package.json 的 version唯一来源人工或发布脚本修改
Android build.gradle 的 versionName打进 aar构建时从环境变量注入
iOS Info.plist / MARKETING_VERSION打进 framework从 .xcconfig 注入
宿主 manifest.json记录当前插件版本发布脚本同步

Android 侧用 Gradle 属性接收，不在仓库里硬编码：

groovy
// android/build.gradle（片段）
android {
    defaultConfig {
        minSdk 21
        targetSdk 34
        versionCode Integer.parseInt(System.getenv('PLUGIN_VERSION_CODE') ?: '1')
        versionName System.getenv('PLUGIN_VERSION_NAME') ?: '0.0.0-dev'
    }
}

iOS 侧用 xcconfig 接收：

text
// ios/PluginVersions.xcconfig（片段）
MARKETING_VERSION = 1.0.0
CURRENT_PROJECT_VERSION = 1

发布时由脚本或 CI 覆盖：

bash
# 以真实插件目录为例
PLUGIN_VERSION_NAME=1.4.2 \
PLUGIN_VERSION_CODE=10402 \
./gradlew assembleRelease

# iOS：把版本写进 xcconfig 后再构建
sed -i '' "s/^MARKETING_VERSION = .*/MARKETING_VERSION = 1.4.2/" ios/PluginVersions.xcconfig
xcodebuild -project UniNativeDemo.xcodeproj -scheme UniNativeDemo \
  -configuration Release -sdk iphoneos build

三条纪律：

  1. 禁止在 package.json、build.gradle、Info.plist 三处手填不同版本。
  2. 每次发布只改 package.json，其余由构建注入。
  3. 产物文件名带版本号，例如 UniNativeDemo-1.4.2.aar，便于对账。

三、插件声明：双端必须一一对应 ​

package.json 里的 _dp_nativeplugin 是 HBuilderX 识别插件的依据。以仓库内示例为例：

jsonc
// uniapp-demo/nativeplugins/UniNativeDemo/package.json
{
  "id": "UniNativeDemo",
  "name": "原生能力演示插件",
  "version": "1.0.0",
  "_dp_type": "nativeplugin",
  "_dp_nativeplugin": {
    "android": {
      "plugins": [
        { "type": "module", "name": "UniNativeDemo", "class": "com.example.unidemo.NativeDemoModule" },
        { "type": "component", "name": "NativeDemoView", "class": "com.example.unidemo.NativeDemoView" }
      ],
      "integrateType": "aar",
      "minSdkVersion": 21,
      "abis": ["arm64-v8a", "armeabi-v7a"]
    },
    "ios": {
      "plugins": [
        { "type": "module", "name": "UniNativeDemo", "class": "NativeDemoModule" },
        { "type": "component", "name": "NativeDemoView", "class": "NativeDemoView" }
      ],
      "integrateType": "framework",
      "deploymentTarget": "13.0",
      "validArchitectures": ["arm64"]
    }
  }
}

容易出错的四个点：

点错误示例后果
id 与目录名不一致目录 demo，id 为 UniDemoHBuilderX 勾选后运行时找不到插件
双端 module 名称不一致Android 叫 Demo，iOS 叫 UniDemoJS 端要写两套调用名
class 写错包名Java 类实际在 com.example.demo编译通过，运行时报 ClassNotFound
ABI 只留 armeabi-v7a缺少 arm64-v8a新机型无法加载

这些都不该靠人眼检查。仓库提供 scripts/native-check.mjs 做机器校验：

bash
pnpm native:check
# [native-check] 插件根目录：uniapp-demo/nativeplugins
# ⚠  UniNativeDemo 未找到 android/*.aar（需先执行 ./gradlew assembleRelease）
# ⚠  UniNativeDemo 未找到 ios/*.framework 或 *.xcframework（需先执行 xcodebuild）
# [native-check] SKIP：未发现 aar/framework 产物（本地未编译）。

没有产物时默认 SKIP 且退出码 0；发布流水线使用 pnpm native:check:strict，缺产物直接退出码 2。

四、把「声明」变成可执行契约 ​

除了 native-check，仓库还提供一份静态契约测试 tests/native-contract.test.ts，把双端声明与源码导出方法绑定起来：

bash
pnpm exec vitest run tests/native-contract.test.ts
# ✓ tests/native-contract.test.ts (5 tests)

它检查四件事：

  1. id、_dp_type、version 合法；
  2. Android 与 iOS 的 module/component 集合完全一致；
  3. Android @JSMethod 方法与 iOS WX_EXPORT_METHOD 选择器一一对应；
  4. onNativeClick 事件名双端一致，ABI 与最低系统版本符合要求。

下一步 25.2 会把契约扩展到运行期，并处理宿主 SDK 升级。

五、验收标准 ​

bash
# 1. 元数据检查（无产物时 SKIP，不阻塞本地开发）
pnpm native:check

# 2. 双端契约测试
pnpm exec vitest run tests/native-contract.test.ts

# 3. 类型检查
pnpm typecheck

自查：

  • 新增一个插件时，只改 plugins/<name>/package.json 里的版本号。
  • 任意一个双端声明不一致，native:check 或契约测试必须失败。
  • 宿主 nativeplugins/ 里的插件与 monorepo 源码保持同步（软链或 CI 复制）。
  • 仓库不提交 .aar / .framework，只提交源码与 native-artifacts.json 基线。
