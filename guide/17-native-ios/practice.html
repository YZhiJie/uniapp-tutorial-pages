17.3 实战案例：iOS 插件从编译到上架 ​

iOS 的最后一步不是「代码能跑」，而是「能签名、能归档、能上传、能过审」。这条链路任何一环断了，前面写好的插件都交付不了。

本章以 UniNativeDemo 插件为例，走完 插件 Framework 构建 → 接入 uni-app → 自定义基座 → 证书/描述文件 → Archive → 上传 App Store Connect → TestFlight。

配套源码：

text
uniapp-demo/nativeplugins/UniNativeDemo/
├── package.json
├── ios/
│   ├── NativeDemoModule.h
│   ├── NativeDemoModule.m
│   ├── NativeDemoView.h
│   └── NativeDemoView.m
└── README.md

仓库不提交 .framework / .ipa / .p12 / .mobileprovision。按本章命令在本地构建；证书与私钥必须存放在密钥管理系统，禁止进 Git。

一、交付链路总览 ​

mermaid
flowchart LR
    A[插件源码] --> B[Framework]
    B --> C[nativeplugins/ios]
    C --> D[HBuilderX 自定义基座 / 云打包]
    D --> E[.ipa 或 原生工程]
    E --> F[Archive]
    F --> G[Export]
    G --> H[Transporter]
    H --> I[App Store Connect]
    I --> J[TestFlight]
    J --> K[审核上架]

两条常见路线：

路线适用签名主体
HBuilderX 云打包标准插件、无自定义原生代码DCloud 代打包，证书由你上传
Xcode 离线打包自研插件、需要自定义原生工程你自己在 Xcode Archive

二、构建插件 Framework ​

2.1 前置检查 ​

bash
xcodebuild -version
xcodebuild -list -project UniDemoNative.xcodeproj

确认：

  • Framework target 的 Bundle Identifier 与宿主不同（插件是独立 framework）。
  • Deployment Target 与 package.json 的 deploymentTarget 一致。
  • Build Libraries for Distribution = YES（Swift 混编必开）。
  • Defines Module = YES。

2.2 构建 ​

bash
xcodebuild \
  -project UniDemoNative.xcodeproj \
  -scheme UniDemoNative \
  -configuration Release \
  -sdk iphoneos \
  -derivedDataPath ./build \
  BUILD_LIBRARY_FOR_DISTRIBUTION=YES \
  build

校验：

bash
FRAMEWORK=./build/Build/Products/Release-iphoneos/UniDemoNative.framework
lipo -info "$FRAMEWORK/UniDemoNative"
# 期望：arm64
otool -L "$FRAMEWORK/UniDemoNative" | head

上架包只能包含 arm64。如果为了模拟器调试合并了 x86_64，导出 IPA 前必须剥离，否则 App Store 会拒绝。

2.3 第三方 SDK 依赖 ​

如果插件依赖高德、极光等 SDK：

  • 用 CocoaPods 管理时，Framework 里不要静态打包三方 SDK；在插件的 package.json 的 ios.dependencies 声明 Pod 依赖，让 HBuilderX 在打包时解析。
  • 手动集成 .framework 时，确认三方 SDK 的 Embed & Sign 设置正确，避免 dyld: Library not loaded。
  • 注意三方 SDK 的 PrivacyInfo.xcprivacy，缺隐私清单会触发 ITMS-91053。

三、接入 uni-app ​

package.json（只保留 iOS 关键字段）：

jsonc
{
  "id": "UniNativeDemo",
  "name": "原生能力演示插件",
  "version": "1.0.0",
  "_dp_type": "nativeplugin",
  "_dp_nativeplugin": {
    "ios": {
      "plugins": [
        { "type": "module", "name": "UniNativeDemo", "class": "NativeDemoModule" },
        { "type": "component", "name": "NativeDemoView", "class": "NativeDemoView" }
      ],
      "integrateType": "framework",
      "deploymentTarget": "13.0",
      "validArchitectures": ["arm64"]
    }
  }
}

目录：

text
nativeplugins/UniNativeDemo/
├── package.json
├── ios/
│   └── UniNativeDemo.framework/
└── android/UniNativeDemo.aar

3.1 自定义调试基座 ​

  1. HBuilderX → 运行 → 运行到手机或模拟器 → 制作自定义调试基座。
  2. 勾选 UniNativeDemo。
  3. 选择 iOS，填写 Apple 证书与 Bundle ID。
  4. 基座安装到真机后，用「运行到自定义基座」验证。
js
const plugin = uni.requireNativePlugin('UniNativeDemo')
console.log(Object.keys(plugin))

3.2 云打包 ​

  • HBuilderX → 发行 → 原生 App-云打包。
  • 上传 .p12、.mobileprovision，填写密码与 Bundle ID。
  • 打包完成后从 DCloud 后台下载 .ipa。

云打包的限制：无法执行自定义 Build Phase、无法嵌入未声明的动态库。重定制走 Xcode 离线打包。

四、证书与描述文件 ​

4.1 四个角色 ​

角色在哪创建作用
App IDCertificates, Identifiers & Profiles → Identifiers唯一标识，对应 Bundle ID
CertificateCertificates → +证明签名身份
Provisioning ProfileProfiles → +绑定 App ID + 证书 + 设备/商店
Team IDMembershipCI 与 ExportOptions.plist 使用

4.2 创建证书（ CSR → .cer → .p12） ​

  1. 打开「钥匙串访问」→ 证书助理 → 从证书颁发机构请求证书。
  2. 填写邮箱与常用名，选择「存储到磁盘」，得到 CertificateSigningRequest.certSigningRequest。
  3. 在 Apple Developer → Certificates → + → 选择类型（Apple Distribution / iOS Development）→ 上传 CSR。
  4. 下载 .cer，双击导入钥匙串。
  5. 在钥匙串中选中证书 + 私钥，右键「导出」，生成 .p12 并设置密码。
bash
# 校验 p12 是否包含私钥
openssl pkcs12 -in release.p12 -info -nocerts

4.3 创建描述文件 ​

类型用途设备限制
iOS App Development真机调试需登记 UDID
Ad Hoc内测分发需登记 UDID，最多 100 台/年
App Store上架 / TestFlight无设备限制

创建后下载 .mobileprovision，双击安装到本机。

bash
# 查看描述文件内容
security cms -D -i profile.mobileprovision | plutil -p -

4.4 Xcode 自动签名 ​

  1. Target → Signing & Capabilities。
  2. 勾选 Automatically manage signing。
  3. 选择 Team，填写 Bundle Identifier。
  4. Xcode 会自动创建证书与描述文件。

团队协作建议：

  • 小团队用自动签名。
  • 多人 / CI 用 fastlane match 统一管理证书，避免「每人一套证书、描述文件互相覆盖」。

五、Archive 与导出 IPA ​

5.1 Xcode 图形化 ​

  1. 选择 Any iOS Device (arm64)，不要选模拟器。
  2. Product → Archive。
  3. Organizer → Distribute App → App Store Connect → Upload。
  4. 或选择 Export 导出 .ipa 给测试团队。

5.2 命令行（CI 推荐） ​

bash
# 1. 归档
xcodebuild archive \
  -workspace UniDemoNative.xcworkspace \
  -scheme UniDemoNative \
  -configuration Release \
  -destination 'generic/platform=iOS' \
  -archivePath build/UniDemoNative.xcarchive \
  -allowProvisioningUpdates

# 2. 导出配置
cat > build/ExportOptions.plist <<'PLIST'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>method</key>
  <string>app-store-connect</string>
  <key>teamID</key>
  <string>YOUR_TEAM_ID</string>
  <key>signingStyle</key>
  <string>automatic</string>
  <key>uploadSymbols</key>
  <true/>
  <key>stripSwiftSymbols</key>
  <true/>
</dict>
</plist>
PLIST

# 3. 导出 IPA
xcodebuild -exportArchive \
  -archivePath build/UniDemoNative.xcarchive \
  -exportOptionsPlist build/ExportOptions.plist \
  -exportPath build/ipa \
  -allowProvisioningUpdates

校验 IPA：

bash
unzip -l build/ipa/UniDemoNative.ipa | head
# 检查 Payload/*.app/Frameworks 下是否有 x86_64
lipo -info build/ipa/Payload/UniDemoNative.app/UniDemoNative

5.3 ExportOptions.plist 的 method 取值 ​

值用途
app-store-connect上传 App Store / TestFlight
release-testingAd Hoc 内测
debugging开发调试
enterprise企业内部分发（需企业账号）

六、上传 App Store Connect ​

6.1 创建应用记录 ​

  1. App Store Connect → My Apps → + → New App。
  2. 选择平台 iOS、名称、主语言、Bundle ID、SKU。
  3. 填写隐私政策 URL、类目、年龄分级。

6.2 上传 ​

方式一：Transporter（推荐给非 CI）

  1. Mac App Store 安装 Transporter。
  2. 登录 Apple ID。
  3. 拖入 .ipa → Deliver。

方式二：命令行

bash
xcrun altool --upload-app \
  -f build/ipa/UniDemoNative.ipa \
  -t ios \
  --apiKey "$ASC_API_KEY" \
  --apiIssuer "$ASC_API_ISSUER"

altool 在新版 Xcode 中逐步被 Transporter / App Store Connect API 取代。企业 CI 建议直接用 App Store Connect API + xcrun altool 或 Fastlane deliver。

6.3 TestFlight ​

  • 上传成功后，App Store Connect → TestFlight 等待「处理中」变为「可测试」。
  • 内部测试员最多 100 人，外部测试员最多 10,000 人（需审核）。
  • 每次构建给测试员填写「测试内容」，否则外部测试审核容易被拒。

七、上架前检查清单 ​

7.1 技术项 ​

  • [ ] Bundle ID 与 App ID 一致
  • [ ] 签名证书与描述文件匹配
  • [ ] arm64 架构完整，无 x86_64
  • [ ] Info.plist 权限文案齐全（相机、相册、定位、麦克风）
  • [ ] PrivacyInfo.xcprivacy 已声明数据采集
  • [ ] ITSAppUsesNonExemptEncryption 已填写
  • [ ] 没有使用私有 API
  • [ ] 第三方 SDK 均为最新合规版本

7.2 审核项 ​

  • [ ] 隐私政策链接可访问
  • [ ] 截图覆盖 6.7"/6.5"/5.5" 等必要尺寸
  • [ ] 演示账号 / 审核备注（如需要登录）
  • [ ] 应用内购买使用 IAP（虚拟商品）
  • [ ] 没有引导用户跳转外部支付（除非符合地区政策）

八、常见错误与排查 ​

错误原因处理
ITMS-90035 Invalid Signature证书/描述文件不匹配重新导出 p12，检查 Bundle ID
ITMS-90046 Invalid Code Signing Entitlementscapabilities 与 profile 不一致重新生成 profile
ITMS-90474 Invalid Bundle包含 x86_64 / 不支持架构剥离模拟器架构
ITMS-91053 Missing API declaration缺隐私清单补 PrivacyInfo.xcprivacy
ITMS-90683 Missing purpose string权限文案缺失补 NS*UsageDescription
dyld: Library not loaded动态库未 Embed & Sign设置 Embedded Content
module compiled with Swift 5.xSwift 版本不兼容开 BUILD_LIBRARY_FOR_DISTRIBUTION
上传卡在「处理中」二进制校验失败查 App Store Connect 邮件 / Transporter 日志

九、练习题 ​

  1. 用 xcodebuild 完成一次 Archive + Export，并解释 ExportOptions.plist 每个字段的作用。
  2. 模拟一次 ITMS-90474：把模拟器架构合并进 Framework，观察上传报错，再剥离验证。
  3. 给 NativeDemoModule 增加 getIDFA，并说明为什么必须配置 NSUserTrackingUsageDescription。
