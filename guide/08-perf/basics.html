8.1 基础入门：性能指标与度量方法 ​

性能优化的第一原则：没有度量就没有优化。凭感觉改代码，常见结果是越改越复杂、性能没有变化。

关键指标地图 ​

text
用户点击图标
  │
  ├─ T1 容器/小程序环境初始化（平台相关，App 关注）
  ├─ T2 主包下载与加载（小程序关注，包体积相关）
  ├─ T3 JS 引擎初始化 + 主包代码执行（onLaunch/onLoad）
  ├─ T4 首屏数据请求（网络）
  ├─ T5 首次渲染完成（首帧/首屏）
  └─ T6 可交互（事件可响应、列表可滚动）  ← 用户真实感知
指标含义体验目标（参考）
启动耗时点击图标到首屏小程序 ≤2s（中低端机 ≤3s）
首屏可交互数据展示且能点击≤3s
帧率 FPS滚动/动画流畅度稳定 ≥55fps，避免长时间掉帧
setData 成本单次数据量与频率单帧 payload 小、无连续高频调用
包体积主包/分包大小主包 ≤1.5MB（小程序 2MB 限）
接口耗时首屏关键接口P95 ≤500ms（含网关）

小程序端度量手段 ​

1. 微信开发者工具 ​

  • Performance/调试器 → Trace：录制启动与滚动火焰图，查看 setData、渲染、脚本耗时分布。
  • Audits（体验评分）：给出启动、渲染、资源缓存维度的评分与建议，适合作为提交前自检。
  • Memory：排查长时间使用后的内存增长（图片、长列表是重灾区）。

2. 性能日志（真机） ​

开发版/真机调试可开启性能面板；也可通过 wx.getPerformance()（uni 中条件编译调用）采集：

ts
// #ifdef MP-WEIXIN
const performance = wx.getPerformance()
const observer = performance.createObserver((entryList) => {
  entryList.getEntries().forEach((entry) => {
    if (entry.entryType === 'render' || entry.entryType === 'script') {
      console.log('[perf]', entry.entryType, entry.duration)
    }
  })
})
observer.observe({ entryTypes: ['render', 'script', 'navigation'] })
// #endif

3. 自定义埋点（全端通用） ​

ts
// src/utils/perf.ts
export function now(): number {
  // #ifdef H5
  return performance.now()
  // #endif
  // #ifndef H5
  return Date.now()
  // #endif
}

export class PerfMark {
  private marks = new Map<string, number>()
  mark(name: string) {
    this.marks.set(name, now())
  }
  measure(name: string, start: string, end?: string) {
    const s = this.marks.get(start)
    const e = end ? this.marks.get(end)! : now()
    const duration = Math.round((e - (s ?? e)) * 100) / 100
    if (duration > 300) {
      console.warn(`[perf] ${name} 耗时 ${duration}ms，超过 300ms 阈值`)
    }
    return duration
  }
}

页面中埋点：

ts
const perf = new PerfMark()
onLoad(() => perf.mark('load'))
onReady(() => {
  perf.mark('ready')
  perf.measure('首屏渲染(load→ready)', 'load', 'ready')
})
async function fetchData() {
  perf.mark('req-start')
  await api.list()
  perf.mark('req-end')
  perf.measure('首屏接口', 'req-start', 'req-end')
}

H5 端度量手段 ​

  • Lighthouse：性能、可访问性、SEO 一体评分，CI 可用 lhci autorun。
  • DevTools Performance 面板 + performance.mark/measure。
  • Core Web Vitals：LCP（最大内容绘制）、INP（交互响应）、CLS（布局偏移）。
  • 静态站点可直接接 Web Vitals 采集：本教程站点即为 SSG，首屏仅加载静态资源。

App 端度量手段 ​

  • HBuilderX 真机运行控制台的启动日志、渲染模式说明（webview / nvue 原生渲染）。
  • 弱网模拟（Charles/系统开发者选项）验证首屏数据策略。
  • 中低端 Android 真机是必测设备——模拟器和旗舰机不能代表真实用户。

双线程视角下的“渲染成本” ​

回顾 1.2 的双线程模型，一次数据更新的耗时构成：

text
逻辑层序列化 diff  →  JSBridge 传输  →  视图层反序列化 + 渲染

三个变量决定成本：数据量、调用频率、节点复杂度。度量时分别看：

  • 单次 setData payload 大小（Trace 中可见）。
  • 每秒调用次数（输入框联想、滚动联动尤其要查）。
  • 页面节点总数（长列表可达数万节点）。

建立性能预算（Performance Budget） ​

把目标写进团队规范，例如：

项预算
主包体积≤1.5MB
首屏接口数≤2 个（其余延后/预加载）
单次 setData 数据≤256KB
列表首屏节点≤200 个
图片首屏总量≤500KB（WebP + CDN 裁剪）
路由跳转反馈点击到 loading ≤100ms

超预算即视为缺陷，和功能 bug 同等对待。

常见问题 ​

Q：开发者工具很流畅，真机卡？ 工具的 JSBridge 与渲染成本远低于真机，性能只信真机（尤其是中低端 Android）。

Q：首屏慢，先查什么？ 按概率排序：包体积与启动链路、首屏接口瀑布（请求依赖请求）、图片过大、同步存储读写、首屏节点过多。

Q：FPS 怎么测才准？ 录慢动作滚动（快速甩动列表），看掉帧区间而不是平均值；Trace 中标注业务操作（切 tab、发消息）对齐分析。
