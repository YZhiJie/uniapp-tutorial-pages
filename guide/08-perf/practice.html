8.3 实战案例：性能审计清单与优化演练 ​

本篇是一份可以直接拿到项目里执行的审计 SOP。建议对每个重要版本做一次，并把结果沉淀到性能档案。

审计准备 ​

  1. 固定设备矩阵：中低端 Android 真机（必选）、iPhone（近三年主流款）、开发者工具/H5 Chrome。
  2. 固定网络：WiFi、4G/弱网（用工具模拟 3G/高延迟）各一轮。
  3. 清空缓存冷启动，每个场景测 3 次取中位数。
  4. 录屏 + Trace 留档，便于优化后对比。

一、启动与包体积审计 ​

检查项方法目标结果
主包体积构建产物/开发者工具依赖分析≤1.5MB☐
分包合理性pages.json 审读tabBar 外页面基本在分包☐
预加载策略preloadRule 审读高概率分包 WiFi 预下载☐
onLaunch 阻塞代码审查 + Trace无 await 网络请求☐
同步存储调用搜索 getStorageSync启动路径 ≤5 次☐
按需注入manifest lazyCodeLoadingrequiredComponents☐

优化演练：用构建产物分析找到主包最大的三个模块，分别采用「移入分包 / 按需引入 / 资源上 CDN」处理，记录体积变化。

二、首屏审计 ​

检查项方法目标
首屏接口数量Network 面板≤2 个，无请求瀑布
首屏图片量Network 按体积排序≤500KB，尺寸匹配显示
骨架/缓存策略二次进入实测先渲染缓存，后台刷新
首屏节点数WXML/元素面板≤200 节点
关键数据并行代码审查Promise.all 而非顺序 await

典型改造对比：

ts
// ❌ 串行：两次请求耗时相加
const user = await userApi.profile()
const list = await goodsApi.list({ shopId: user.shopId })

// ✅ 并行：本地已有 shopId 时同时发起
const [user, list] = await Promise.all([
  userApi.profile(),
  goodsApi.list({ shopId: cachedShopId })
])

若第二个请求确实依赖第一个的返回值，考虑把依赖参数前置到路由 query 或本地缓存，消灭瀑布。

三、列表与滚动审计 ​

测试动作：进入列表页 → 快速甩动到底部 → 连续上拉加载 5 页。

检查项目标
FPS无持续低于 45fps 的区间
单页大小20 条左右，不可一次拉全量
节点数（加载 5 页后）普通渲染 ≤1000；超过则上虚拟列表
图片尺寸列表图走缩略图参数
setData 频率滚动监听已节流，无逐帧大对象更新

优化演练：对同一列表分别实现「普通渲染 1000 条」与「虚拟列表 1000 条」，在真机 Trace 中对比渲染耗时与内存（参考 8.2 演练场）。

四、交互响应审计 ​

场景目标
按钮点击到反馈≤100ms 出现 loading/按压态
搜索联想防抖 300ms，请求可取消旧请求
提交按钮防重重复点击不产生重复订单
跳转白屏跳转立即出现目标页骨架而非卡顿
ts
// 可取消的搜索：新请求发出前 abort 旧请求
let lastTask: UniApp.RequestTask | null = null
const search = debounce((kw: string) => {
  lastTask?.abort()
  lastTask = uni.request({ url: '/search', data: { kw }, success: render })
}, 300)

五、内存与稳定性审计 ​

检查项方法
长列表滚动 5 分钟内存曲线开发者工具 Memory 定时采样，无持续陡增
定时器/监听清理onUnload 中清除 interval、off 事件、关闭 Socket
大图浏览预览后释放，图片组件数量受控
页面栈深度长流程改用 redirectTo，栈不超过 10

事件监听清理模板：

ts
import { onLoad, onUnload } from '@dcloudio/uni-app'

onLoad(() => {
  uni.$on('cart:changed', refreshBadge)
})
onUnload(() => {
  uni.$off('cart:changed', refreshBadge) // 必须传同一引用，防止重复监听
})

5.1 采样方法：按端选工具，别只看开发者工具 ​

端工具采样动作判读重点
H5Chrome DevTools → Memory进入页面前拍一次 Heap Snapshot；操作 5 轮后再拍；返回上级页再拍Detached DOM 数量、JSHeapUsed 是否回落到基线
微信小程序开发者工具「性能」面板 + 真机调试真机录制 Trace，连续进出页面 5 次页面返回后内存是否回落、setData 峰值
Android AppAndroid Studio Profiler / LeakCanary Debug 包反复进出目标页，触发 GC 后 Heap DumpActivity / View 是否被静态字段或单例持有
iOS AppXcode → Instruments → Allocations / Leaks真机 Profile，操作前后 Mark Generation两代之间的持续增长、Leaks 红色标记
通用uni.getSystemInfo + 自建内存埋点版本迭代间纵向对比同机型同路径的中位数趋势

采样纪律（否则数据不可比）：

  1. 冷启动后静置 10s 再取基线，排除启动期抖动。
  2. 固定一条操作路径（进入列表 → 滚动 3 屏 → 返回首页），重复 5 次。
  3. 每轮结束手动触发 GC，再记录；回落到基线 ±10% 视为正常。
  4. 连续 3 轮不回落才判定「疑似泄漏」，此时抓两份快照做对比，不要凭感觉下结论。

5.2 三类高频泄漏与修法 ​

① 闭包持有页面大对象。 定时器、事件回调、Promise 链里引用了 items、chart 等大数组，页面卸载后闭包仍存活：

ts
import { onLoad, onUnload } from '@dcloudio/uni-app'

let timer: ReturnType<typeof setInterval> | null = null

onLoad(() => {
  timer = setInterval(() => {
    // 闭包捕获了组件作用域的 list，list 越大泄漏越明显
    renderBadge(list.value.length)
  }, 1000)
})

onUnload(() => {
  if (timer) clearInterval(timer)
  timer = null
  list.value = [] // 主动断开大对象引用，帮助运行时尽早回收
})

② 全局单例持有页面 / Activity。 把页面 this、组件实例、原生回调注册进全局对象或单例 store，页面销毁后仍被根对象引用。规则：全局只存可序列化数据（id、token、计数），不存实例；必须存回调时在 onUnload 移除。

ts
// ❌ 全局保存页面实例
getApp().globalData.currentPage = this

// ✅ 只保存数据；需要通信时用事件并在卸载时注销
getApp().globalData.currentPageId = this.pageId
uni.$on('order:paid', this.onPaid)
onUnload(() => uni.$off('order:paid', this.onPaid))

③ 原生 View / 组件未销毁。 Android 的 WXComponent 在 onActivityDestroy 未 removeView，或 iOS 的自定义 View 未置 nil；plus.nativeObj.View 浮层只 show 不 close，都会让原生对象常驻。

ts
// plus.nativeObj.View 必须成对销毁
const overlay = plus.nativeObj.View.getViewById('loading-mask')
onUnload(() => {
  overlay?.close() // 不是 hide，hide 只隐藏不释放
})
java
// Android WXComponent：宿主销毁时解绑
@Override
public void onActivityDestroy() {
    super.onActivityDestroy();
    if (webView != null) {
        webView.removeAllViews();
        webView = null;
    }
}

5.3 「复现 → 快照 → 修复 → 对比」记录范式 ​

每次泄漏都要留下可复查的证据，而不是一句「已优化」：

text
[LEAK-001] 商品详情页返回后内存不回落
环境：Android 13 / 某中端机 / release 包 / 冷启动后第 3 次进入
复现：首页 → 商详（含 20 张主图）→ 返回首页，重复 5 次
基线：PSS 182MB（GC 后）
复现后：PSS 264MB（GC 后），每轮 +16MB
快照对比（Retained Size Top 3）：
  1. GoodsDetailActivity  → 被 AppModule.sLastActivity 静态字段持有
  2. ImageLoader.cache    → 未设置上限，缓存了原图 Bitmap
  3. OkHttp ResponseBody → 商详接口回调闭包未释放
根因：原生插件单例保存了 Activity 引用（对应 5.2 第 ② 类）
修复：NativeGoodsModule.java:88 改为 WeakReference；ImageLoader 上限 20MB
复测：5 轮后 PSS 191MB（+9MB，在 ±10% 容差内）
回归：加入发版前内存巡检清单，见 23-performance 的「泄漏归因」章节

更完整的性能基线、泄漏归因与体积预算流水线见 23.1 性能工程体系 与 23.2 内存与渲染成本。

综合练习 ​

  1. 选一个现有页面完整执行本清单，输出一张量化表与至少三项改造。
  2. 给 8.1 的 PerfMark 封装加上上报能力：超阈值的 measure 批量 POST 到日志接口（注意采样率，别把性能埋点做成新的性能问题）。
