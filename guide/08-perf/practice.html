8.3 实战案例：性能审计清单与优化演练 ​

本篇是一份可以直接拿到项目里执行的审计 SOP。建议对每个重要版本做一次，并把结果沉淀到性能档案。

审计准备 ​

  1. 固定设备矩阵：中低端 Android 真机（必选）、iPhone（近三年主流款）、开发者工具/H5 Chrome。
  2. 固定网络：WiFi、4G/弱网（用工具模拟 3G/高延迟）各一轮。
  3. 清空缓存冷启动，每个场景测 3 次取中位数。
  4. 录屏 + Trace 留档，便于优化后对比。

一、启动与包体积审计 ​

检查项方法目标结果
主包体积构建产物/开发者工具依赖分析≤1.5MB☐
分包合理性pages.json 审读tabBar 外页面基本在分包☐
预加载策略preloadRule 审读高概率分包 WiFi 预下载☐
onLaunch 阻塞代码审查 + Trace无 await 网络请求☐
同步存储调用搜索 getStorageSync启动路径 ≤5 次☐
按需注入manifest lazyCodeLoadingrequiredComponents☐

优化演练：用构建产物分析找到主包最大的三个模块，分别采用「移入分包 / 按需引入 / 资源上 CDN」处理，记录体积变化。

二、首屏审计 ​

检查项方法目标
首屏接口数量Network 面板≤2 个，无请求瀑布
首屏图片量Network 按体积排序≤500KB，尺寸匹配显示
骨架/缓存策略二次进入实测先渲染缓存，后台刷新
首屏节点数WXML/元素面板≤200 节点
关键数据并行代码审查Promise.all 而非顺序 await

典型改造对比：

ts
// ❌ 串行：两次请求耗时相加
const user = await userApi.profile()
const list = await goodsApi.list({ shopId: user.shopId })

// ✅ 并行：本地已有 shopId 时同时发起
const [user, list] = await Promise.all([
  userApi.profile(),
  goodsApi.list({ shopId: cachedShopId })
])

若第二个请求确实依赖第一个的返回值，考虑把依赖参数前置到路由 query 或本地缓存，消灭瀑布。

三、列表与滚动审计 ​

测试动作：进入列表页 → 快速甩动到底部 → 连续上拉加载 5 页。

检查项目标
FPS无持续低于 45fps 的区间
单页大小20 条左右，不可一次拉全量
节点数（加载 5 页后）普通渲染 ≤1000；超过则上虚拟列表
图片尺寸列表图走缩略图参数
setData 频率滚动监听已节流，无逐帧大对象更新

优化演练：对同一列表分别实现「普通渲染 1000 条」与「虚拟列表 1000 条」，在真机 Trace 中对比渲染耗时与内存（参考 8.2 演练场）。

四、交互响应审计 ​

场景目标
按钮点击到反馈≤100ms 出现 loading/按压态
搜索联想防抖 300ms，请求可取消旧请求
提交按钮防重重复点击不产生重复订单
跳转白屏跳转立即出现目标页骨架而非卡顿
ts
// 可取消的搜索：新请求发出前 abort 旧请求
let lastTask: UniApp.RequestTask | null = null
const search = debounce((kw: string) => {
  lastTask?.abort()
  lastTask = uni.request({ url: '/search', data: { kw }, success: render })
}, 300)

五、内存与稳定性审计 ​

检查项方法
长列表滚动 5 分钟内存曲线开发者工具 Memory 定时采样，无持续陡增
定时器/监听清理onUnload 中清除 interval、off 事件、关闭 Socket
大图浏览预览后释放，图片组件数量受控
页面栈深度长流程改用 redirectTo，栈不超过 10

事件监听清理模板：

ts
import { onLoad, onUnload } from '@dcloudio/uni-app'

onLoad(() => {
  uni.$on('cart:changed', refreshBadge)
})
onUnload(() => {
  uni.$off('cart:changed', refreshBadge) // 必须传同一引用，防止重复监听
})

综合练习 ​

  1. 选一个现有页面完整执行本清单，输出一张量化表与至少三项改造。
  2. 给 8.1 的 PerfMark 封装加上上报能力：超阈值的 measure 批量 POST 到日志接口（注意采样率，别把性能埋点做成新的性能问题）。
  3. 在 CI 中加入产物体积检查：构建脚本解析主包大小，超过 1.5MB 直接失败。
