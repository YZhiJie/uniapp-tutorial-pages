19.3 实战案例：电商工程分层重构与门禁落地 ​

本篇对仓库内的 ecommerce-mini-program/ 做增量分层重构：不推倒重写，只在新需求触达的链路上抽层，并用脚本把规则固化。所有命令都可直接执行。

一、现状盘点：先找「职责泄漏」 ​

重构前先审计三类信号，而不是凭感觉画架构：

bash
cd ecommerce-mini-program

# 1. 页面直接 import 请求内核的位置
grep -rn "from '@/transport" src/pages src/components

# 2. 页面里出现金额计算 / 状态判断
grep -rnE "reduce\(|price \* |status === '" src/pages | head -20

# 3. 工具层反向依赖业务
grep -rn "from '@/api\|from '@/stores'" src/utils

示例工程的真实结论：

信号位置处理方式
页面直接调 apipages/index/index.vue 等允许（表现层可直接用数据层），但复杂编排抽用例
金额计算散落商详、购物车、确认页抽 domain/pricing 纯函数
工具反向依赖 apiutils/track.ts登记豁免，后续迁移到 api/telemetry
跨层类型导入composables/usePagination.ts → transport/types放行（import type 不产生运行时耦合）

不新增 data/，直接用现有 api + transport + providers 作为数据访问层；层名写进 scripts/layers.config.mjs 即可，避免为了「标准目录」制造大面积移动。

三、第一步：把价格规则抽成纯函数 ​

改造前，确认页自己算一遍：

ts
// pages/order/confirm.vue（改造前）
const payable = computed(() =>
  items.value.reduce((sum, i) => sum + i.price * i.quantity, freight.value - discount.value)
)

这段代码有三个问题：浮点误差、优惠不能为负、无法单测。抽到领域层：

ts
// src/domain/pricing/priceOrder.ts
export interface CartLine {
  skuId: string
  price: number
  quantity: number
}

export function priceOrder(lines: CartLine[], freight = 0, discount = 0) {
  const goodsAmount = lines.reduce((sum, line) => sum + line.price * line.quantity, 0)
  const payable = Math.max(0, goodsAmount + freight - discount)
  return {
    goodsAmount: Number(goodsAmount.toFixed(2)),
    freight: Number(freight.toFixed(2)),
    discount: Number(discount.toFixed(2)),
    payable: Number(payable.toFixed(2))
  }
}
ts
// tests/domain/priceOrder.spec.ts
import { describe, expect, it } from 'vitest'
import { priceOrder } from '@/domain/pricing/priceOrder'

describe('priceOrder', () => {
  it('优惠大于商品总额时应付为 0，不出现负数', () => {
    const res = priceOrder([{ skuId: 'a', price: 10, quantity: 1 }], 0, 20)
    expect(res.payable).toBe(0)
    expect(res.goodsAmount).toBe(10)
  })

  it('金额保留两位小数', () => {
    const res = priceOrder([{ skuId: 'a', price: 0.1, quantity: 3 }])
    expect(res.goodsAmount).toBe(0.3)
  })
})

页面改为调用：

ts
// pages/order/confirm.vue（改造后）
import { priceOrder } from '@/domain/pricing/priceOrder'

const price = computed(() => priceOrder(items.value, freight.value, discount.value))

四、第二步：把下单编排收进用例层 ​

改造前，确认页同时负责：校验、创建订单、拉起支付、清购物车、跳结果页。任何一步改动都要动页面。

ts
// src/application/checkout/useCheckout.ts
import { ref } from 'vue'
import { createOrder } from '@/api/order'
import { requestPayment } from '@/providers/payment'
import { useCartStore } from '@/stores/cart'
import { useUserStore } from '@/stores/user'

export function useCheckout(deps = { createOrder, requestPayment }) {
  const submitting = ref(false)

  async function submit(input: {
    lines: Array<{ skuId: string; quantity: number }>
    addressId: string
    couponId?: string
  }) {
    if (submitting.value) return null
    submitting.value = true
    try {
      const order = await deps.createOrder({
        skuList: input.lines,
        addressId: input.addressId,
        couponId: input.couponId
      })

      try {
        await deps.requestPayment(order.payParams)
        useCartStore().removeBySkuIds(input.lines.map((l) => l.skuId))
        return { order, paid: true }
      } catch {
        // 支付失败不抛异常：订单已创建，交由页面引导继续支付
        return { order, paid: false }
      }
    } finally {
      submitting.value = false
    }
  }

  return { submitting, submit }
}

页面只负责「根据结果做跳转与提示」：

ts
// pages/order/confirm.vue（改造后）
import { useCheckout } from '@/application/checkout/useCheckout'

const { submitting, submit } = useCheckout()

async function onSubmit() {
  const result = await submit({
    lines: selectedItems.value.map((i) => ({ skuId: i.skuId, quantity: i.quantity })),
    addressId: address.value?.id ?? '',
    couponId: coupon.value?.id
  })
  if (!result) return
  if (result.paid) uni.redirectTo({ url: `/pages/order/result?id=${result.order.id}` })
  else uni.redirectTo({ url: `/pages/order/detail?id=${result.order.id}` })
}

用例层可测试性来自依赖注入：测试时把 requestPayment 换成 async () => { throw new Error('cancel') }，即可覆盖「支付取消」分支，无需真机。

六、第四步：用 ADR 记录取舍 ​

md
# ADR-002 电商示例采用「渐进分层」而非一次性重写

- 状态：已接受
- 日期：2026-11-04

## 背景
示例工程已有 137 个源文件、12 个测试文件，一次性重写会破坏教程引用的路径。

## 决策
1. 保留 api/transport/stores 现有层名，只新增 application/domain。
2. 只重构下单与算价链路，其余页面「触碰即改」。
3. 用 depcruise 守护新增代码，历史技术债登记豁免并注明迁移计划。

## 后果
- 正面：教程与 demo 路径保持稳定；核心链路获得可测性。
- 负面：短期内存在两套写法，需要 Code Review 明确「新代码必须走用例层」。

达到以下状态才算完成：

  • 确认页不再出现 reduce 与接口调用，只有用例调用与页面跳转。
  • 新增越层导入时 pnpm depcruise 退出码为 1。
  • 价格规则的边界用例（优惠超总额、浮点误差）有自动化测试。
  • ADR 能让新人解释「为什么保留两套层名」。
