19.2 进阶应用：用例层、防腐层与多端 BFF ​

分层不是画目录，而是三件具体的事：业务流程有唯一入口（用例层）、后端变化被挡在边界外（防腐层）、多端首屏不再各自拼接口（BFF）。本篇给出可直接复制的实现。

一、用例层：一个文件只描述一个业务动作 ​

用例（Use Case）是「用户意图」的代码化：登录、加购、结算、退款申请。它负责编排，不负责渲染，也不直接接触页面栈。

ts
// src/application/auth/loginWithWechat.ts
import { authRepository } from '@/data/repositories/authRepository'
import { userStore } from '@/stores/user'

export async function loginWithWechat() {
  const code = await new Promise<string>((resolve, reject) => {
    uni.login({
      provider: 'weixin',
      success: (res) => resolve(res.code),
      fail: (err) => reject(new Error(err.errMsg))
    })
  })

  const session = await authRepository.exchangeCode(code)
  userStore.setSession(session)
  return session
}

用例层的三条纪律：

纪律说明
不做 UI不 showToast、不 navigateTo，失败由表现层决定怎么提示
依赖可替换仓库、时钟、随机数通过参数或模块注入，测试时替换
可重入并发调用要幂等（如登录中再次点击复用同一个 Promise）

并发登录的最小处理：

ts
let pending: Promise<Session> | null = null

export function loginWithWechat() {
  if (pending) return pending
  pending = doLogin().finally(() => {
    pending = null
  })
  return pending
}

二、防腐层（ACL）：后端字段变化止步于此 ​

后端返回 goods_id、sale_price、stock_num，业务代码却希望统一用 id、price、stock。如果让 DTO 直接流进页面，一次后端改名就要改几十个文件。

防腐层只做一件事：DTO ↔ 领域模型的双向转换，并集中处理兼容与兜底。

ts
// src/data/acl/goodsAcl.ts
/** 后端 DTO：字段与接口文档一一对应，允许丑陋 */
interface GoodsDto {
  goods_id: string
  goods_name: string
  sale_price: number       // 单位：分
  stock_num: number
  cover_url?: string
}

/** 领域模型：业务代码只认这一套 */
export interface Goods {
  id: string
  name: string
  price: number            // 单位：元
  stock: number
  cover: string
}

export function goodsFromDto(dto: GoodsDto): Goods {
  return {
    id: dto.goods_id,
    name: dto.goods_name,
    price: dto.sale_price / 100,
    stock: dto.stock_num,
    cover: dto.cover_url ?? '/static/images/placeholder.png'
  }
}

export function goodsListFromDto(list: GoodsDto[]): Goods[] {
  return list.map(goodsFromDto)
}

三个容易遗漏的点：

  1. 金额单位只转换一次。DTO 用分，领域用元，展示层不再做除法。
  2. 缺字段给默认值，不要让 undefined 流到模板里引发渲染错误。
  3. 兼容旧字段放在 ACL 内，例如后端灰度期同时返回 price 与 sale_price：
ts
const rawPrice = dto.sale_price ?? (dto as { price?: number }).price ?? 0

仓库层负责「取数据 + 过 ACL」，向上只暴露领域模型：

ts
// src/data/repositories/goodsRepository.ts
import { goodsApi } from '@/data/api/goods'
import { goodsFromDto, goodsListFromDto } from '@/data/acl/goodsAcl'
import type { Goods } from '@/data/acl/goodsAcl'

export const goodsRepository = {
  async list(page: number, size: number): Promise<{ list: Goods[]; total: number }> {
    const res = await goodsApi.list({ page, size })
    return { list: goodsListFromDto(res.list), total: res.total }
  },
  async detail(id: string): Promise<Goods> {
    return goodsFromDto(await goodsApi.detail(id))
  }
}

三、多端 BFF：首屏一个请求，而不是七个 ​

同一首页在 H5、小程序、App 三端各写一遍聚合逻辑，必然出现「H5 加了新模块，小程序忘了」。BFF（Backend for Frontend）把「按屏幕聚合」下沉到一层服务端适配：

text
GET /bff/home?city=310000&platform=mp-weixin
{
  "banners": [...],
  "categories": [...],
  "feed": { "list": [...], "hasMore": true },
  "cartCount": 3,
  "flags": { "newUser": false }
}

服务端伪代码（Node）示意编排职责：

ts
// server/bff/home.ts
app.get('/bff/home', async (req, res) => {
  const { city, platform } = req.query
  const userId = req.auth?.userId

  const [banners, categories, feed, cartCount] = await Promise.all([
    bannerService.active(city, platform),
    categoryService.topLevel(),
    feedService.recommend({ userId, page: 1, size: 10 }),
    userId ? cartService.count(userId) : 0
  ])

  res.json({ banners, categories, feed, cartCount, flags: { newUser: !userId } })
})

客户端只保留一个接口：

ts
// src/data/api/home.ts
export interface HomePayload {
  banners: Banner[]
  categories: Category[]
  feed: { list: Goods[]; hasMore: boolean }
  cartCount: number
  flags: { newUser: boolean }
}

export const homeApi = {
  load(city: string, platform: string) {
    return http.get<HomePayload>('/bff/home', { data: { city, platform } })
  }
}

BFF 的边界：

应该放在 BFF不应该放在 BFF
多接口聚合、字段裁剪、按端裁剪核心业务规则（价格、库存、风控）
首屏数据编排、灰度开关下发长期持久化的业务状态
把内部微服务协议转成端上友好的结构替代领域服务

四、契约先行：类型从 OpenAPI 生成，而不是手抄 ​

接口文档与前端类型长期不同步，是联调阶段最大的时间黑洞。契约先行的顺序是：先定 OpenAPI → 生成类型 → 前后端按契约写测试。

bash
# 从后端仓库或网关导出契约
curl -s https://api.example.com/openapi.json -o openapi.json

# 生成 TypeScript 类型（只生成类型，不生成运行时 SDK）
pnpm dlx openapi-typescript openapi.json -o src/data/api/schema.d.ts
ts
// src/data/api/goods.ts
import type { paths } from './schema'

type GoodsListResponse =
  paths['/goods']['get']['responses']['200']['content']['application/json']

export const goodsApi = {
  async list(query: { page: number; size: number }) {
    // 返回类型由契约推导，后端改字段时类型检查会报错
    return http.get<GoodsListResponse>('/goods', { data: query })
  }
}

运行期仍要校验关键响应（类型只在编译期存在）：

ts
// src/data/api/validate.ts
import { z } from 'zod'

const goodsSchema = z.object({
  goods_id: z.string(),
  goods_name: z.string(),
  sale_price: z.number().int().nonnegative(),
  stock_num: z.number().int().nonnegative()
})

export function parseGoodsList(input: unknown) {
  return z.array(goodsSchema).parse(input)
}

CI 中加一步契约漂移检查：

bash
curl -s "$API_URL/openapi.json" -o /tmp/openapi.json
pnpm dlx openapi-typescript /tmp/openapi.json -o /tmp/schema.d.ts
diff -u src/data/api/schema.d.ts /tmp/schema.d.ts
# 有 diff 说明契约变了但前端未同步，按需失败或提 PR

五、ADR：把「为什么这样分层」留下来 ​

架构决策记录（ADR）是一页纸：背景、决策、后果。放在 docs/adr/，编号递增，永不删除。

md
# ADR-001 引入用例层与防腐层

- 状态：已接受
- 日期：2026-11-04
- 决策人：前端架构组

## 背景
页面直接调用接口与 store，价格规则重复实现三处，后端字段改名需要全量回归。

## 决策
1. 新增 application/ 用例层，页面只调用用例。
2. 新增 data/acl/ 防腐层，DTO 不越过仓库层。
3. 用 scripts/depcruise.mjs 在 CI 拦截越层依赖。

## 后果
- 正面：业务规则可单测；后端字段变化影响面收敛到 ACL。
- 负面：新增一层文件，简单 CRUD 也要写用例，需在评审中允许「薄用例」。
- 迁移：先在新业务试点，旧模块按触碰即重构，不搞一次性大迁移。

ADR 的判断标准：半年后新人能据此理解取舍，而不是只看到结果。

bash
