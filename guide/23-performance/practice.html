23.3 实战案例：Lighthouse CI 与真机性能矩阵 ​

性能优化的最后一公里是「防止回退」。本篇把实验室审计、体积预算与真机矩阵组合成一套可执行的验收流程。

一、Lighthouse CI：H5 回归门禁 ​

1.1 配置 ​

仓库根目录已提供 lighthouserc.cjs：

js
module.exports = {
  ci: {
    collect: {
      url: ['http://localhost:4173'],
      numberOfRuns: 3,
      settings: { preset: 'desktop', throttling: { rttMs: 150, throughputKbps: 1638, cpuSlowdownMultiplier: 4 } }
    },
    assert: {
      assertions: {
        'first-contentful-paint': ['error', { maxNumericValue: 1800 }],
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'total-blocking-time': ['error', { maxNumericValue: 300 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
        'total-byte-weight': ['error', { maxNumericValue: 2000000 }]
      }
    },
    upload: { target: 'temporary-public-storage' }
  }
}

1.2 本地运行 ​

bash
cd ecommerce-mini-program
pnpm build:h5

# 生产口径预览：与线上一致地启用 Brotli / gzip（裸静态服务器不做压缩会让 FCP 虚高）
cd ..
pnpm preview:h5

# 另一终端：跑 3 次取中位数并断言
pnpm lighthouse:ci

不要用 python3 -m http.server 或未压缩的 serve 跑 Lighthouse：Lantern 按实际 transferSize 计算，未压缩文本会把 FCP 拉高 1 秒以上，测出的不是线上表现。

失败时输出会明确指出哪条断言超限，例如：

text
Assertion failed: largest-contentful-paint
  expected: <= 2500
  found: 3120

1.3 CI 集成 ​

yaml
lighthouse:
  runs-on: ubuntu-latest
  defaults:
    run:
      working-directory: ecommerce-mini-program
  steps:
    - uses: actions/checkout@v4
    - uses: pnpm/action-setup@v4
      with: { version: 10 }
    - uses: actions/setup-node@v4
      with:
        node-version: 22
        cache: pnpm
    - run: pnpm install --frozen-lockfile
    - run: pnpm build:h5
    - name: 启动静态预览
      run: |
        npx serve dist/build/h5 -l 4173 &
        npx wait-on http://localhost:4173
    - name: Lighthouse 断言
      run: pnpm dlx @lhci/cli@0.14.x autorun --config=../../lighthouserc.cjs

注意：Lighthouse 对机器抖动敏感。CI 上固定 numberOfRuns: 3、关闭并行、使用固定 runner 规格；不要用「单次跑分」当发布依据。

2.2 电商工程的趋势预算 ​

bash
cd ecommerce-mini-program
pnpm ci:perf

它不仅检查是否超限，还会把本次结果追加到 dist/perf-history.json，与上一次对比输出趋势。CI 中把历史文件作为 artifact 保留，就能看到「连续三个版本主包都在涨」这类慢性问题。

2.3 预算调整规则 ​

场景处理
新增业务导致体积上涨先优化（拆包/压缩/去重），仍超则走评审上调预算
上调预算PR 中说明原因、评估影响、给出后续优化计划
下调预算优化完成后立即下调，形成棘轮
紧急发布允许临时豁免，但 24 小时内必须补回

2.6 生产包剔除 MSW：现象、根因与修复（2026-11-05） ​

现象

  • check:budget 显示 H5 首测 97 个文件 / 1327.4 KB，其中 assets/mock-msw-browser.*.js 占 287.8 KB，另有 static/mockServiceWorker.js 被原样复制；
  • 但 Lighthouse 的 network-requests 里没有任何 mock-msw-browser 请求——它没有被首屏使用，只是被保留在产物里。

根因（三层）

  1. src/platform/msw.ts 的动态 import('@/mock/msw/browser') 只被 #ifdef H5 包裹，没有构建期常量守卫。Rollup 必须为这个动态入口保留 async chunk，即使运行时永远走不到。
  2. 是否启用 MSW 由 readEnv(import.meta.env.VITE_MOCK_MODE, ...) 的运行时结果决定，Vite 无法折叠为常量，死代码消除失效。
  3. src/static/ 由 uni-app 整目录复制进产物，Service Worker 脚本是否被引用不影响它被写出。

修复（两道闸门）

  • 构建期守卫：src/config/env.ts 增加 MSW_ENABLED = import.meta.env.DEV && MOCK_MODE === 'msw'，transport/index.ts 用它选择 transport；src/platform/msw.ts 首行 if (!import.meta.env.DEV) return false。生产构建中 import.meta.env.DEV 被替换为字面量 false，动态 import 变成不可达代码，Rollup 直接剔除。
  • 产物清理：vite.config.ts 新增 stripMswWorker 插件（apply: 'build' + closeBundle），产物写盘后删除 static/mockServiceWorker.js；开发态不触发。

2.7 实战：入口 JS 拆分 + 图片本地化（2026-11-05） ​

承接 2.5 的失败结论（FCP 4957.5ms / LCP 6535.8ms），本轮不动阈值，只改首屏关键路径。

入口构成分析（拆分前 697.5 KB）

组成体积是否首屏必需处理
Mock 运行时（handlers + 数据 + pinyin-pro）440.3 KB rendered否首次请求时动态 import()
uni-h5 / Vue 运行时 + 首屏页面≈ 236 KB是保留，合并小分块减少请求数
dayjs + 5 个插件21.6 KB仅少数页面拆到 @/utils/time，时钟内核独立为 @/utils/clock

四项改动

  1. Mock 运行时懒加载：src/transport/local.ts 去掉静态 import('@/mock')，改为 mockRuntime ??= import('@/mock')，首次请求才拉取；stripMswWorker 继续保证生产包无 Service Worker。
  2. 移除 pinyin-pro（317.7 KB）：搜索联想只需要商品标题的拼音首字母。改为 src/mock/data/pinyin.ts 中预计算 81 个汉字的 initialsOf()（约 1 KB），行为与 pinyin(item.title, { pattern: 'first' }) 一致，pinyin-pro 从依赖中删除。微信端收益更大：common/vendor.js 从 404.9 KB 降到 97.5 KB。
  3. 拆分 dayjs：@/utils/time 保留 dayjs + 插件供格式化页面按需引用；请求内核、倒计时改用零依赖的 @/utils/clock，避免 dayjs 进入入口包。
  4. H5 合块：仅 H5 开启 experimentalMinChunkSize: 30_000，把 17 个脚本 / 9 个样式表中的小分块合并（56 → 36 chunks），减少 Lantern 关键路径的往返次数；小程序分包不受影响。

图片治理

  • Mock 商品图原先指向 picsum.photos 外链（单张 30~55 KB，首屏多张，且依赖外部 CDN）。
  • 改为本地静态资源：src/static/images/ 下 12 张 JPEG（360~640w，q50~q62）+ 12 张 WebP（q75），src/utils/image.ts 按稳定哈希选图。
  • H5 通过条件编译取 .webp，小程序取 .jpg（避免部分小程序 WebP 兼容问题）；首屏图片合计从约 120 KB 降到约 26 KB。
  • 视觉回归：E2E 的拼团 / 秒杀 / 直播 / 登录 / 商详 / 结算 6 个场景全部通过，图片展示与原来一致。

预览口径修正

python3 -m http.server 不做压缩，Lantern 按未压缩 transferSize 计算，FCP 会虚高。新增 scripts/preview-h5.mjs（Node 内置 zlib，按 Accept-Encoding 返回 Brotli 或 gzip），pnpm preview:h5 起生产口径预览后再跑 pnpm lighthouse:ci。

踩坑记录

  1. pinyin-pro 虽已拆成异步 chunk，但 H5 预算脚本按「非分包目录全部计入主包」统计，317.7 KB 仍计入主包导致 1330.5 / 1280 KB 失败。没有放宽阈值，而是彻底移除依赖、改为预计算首字母表。
  2. 注入 modulepreload 预加载首页 chunk 反而让 FCP 从 1878ms 恶化到 2028ms——预加载与首屏脚本争抢带宽，已回滚。
  3. 只把图片换成 WebP 不够：压缩预览下 FCP 仍 1953ms；合块减少往返、拆分 dayjs、移除 pinyin 后才落到 1729ms。
  4. pnpm 12 默认拦截依赖安装脚本，移除包时因 msw 的 postinstall 报 ERR_PNPM_IGNORED_BUILDS；在 ecommerce-mini-program/pnpm-workspace.yaml 显式 allowBuilds: msw 后恢复，不是用 ignore 绕过安全问题。
  5. 图片扩展名不能用不可达的 if (false) 分支，TS 会报错；改为 let ext = '.jpg' + // #ifdef H5 ext = '.webp'。
