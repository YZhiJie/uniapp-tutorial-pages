23.2 进阶应用：内存快照、setData 成本与泄漏归因 ​

拿到基线后，优化要按「成本从高到低」排序。uni-app 里真正拖慢应用的三件事：setData 数据量过大、长列表渲染节点过多、内存泄漏导致越用越卡。

一、setData 成本：先量化，再优化 ​

小程序架构下，逻辑层到视图层的数据传输是性能瓶颈。经验规则：

数据量典型影响
< 100KB可接受
100–256KB中端机开始掉帧
> 256KB明显卡顿，甚至触发传输限制

1.1 在构造边界估算 payload ​

无法直接拦截框架内部 setData，但可以在「准备传给视图层的数据」处估算：

ts
// src/utils/payload.ts
export function estimateBytes(data: unknown) {
  const json = JSON.stringify(data)
  // 中文按 UTF-8 约 3 字节估算，比 .length 更接近真实传输量
  let bytes = 0
  for (const ch of json) {
    bytes += ch.charCodeAt(0) > 0x7f ? 3 : 1
  }
  return bytes
}
ts
// 列表页：只把视图需要的字段放进去
const viewList = computed(() =>
  list.value.map((item) => ({
    id: item.id,
    name: item.name,
    price: item.price,
    cover: item.cover
    // 不要带 desc、specs、skus 等详情字段
  }))
)
console.log('view payload bytes:', estimateBytes(viewList.value))

1.2 三条降本手法 ​

① 分页 + 窗口化：一次只渲染可视区附近的数据。

ts
// 简化版窗口化：滚动时只保留当前页 ± 1 页
const PAGE_SIZE = 20
const windowStart = ref(0)
const visible = computed(() => list.value.slice(windowStart.value, windowStart.value + PAGE_SIZE * 3))

② 合并更新：同一 tick 内多次修改只触发一次视图更新。

ts
import { nextTick } from 'vue'

async function batchUpdate() {
  // 先改完所有状态，再等一个 tick 让 Vue 统一刷新
  items.value = nextItems
  total.value = nextTotal
  await nextTick()
}

③ 避免把大对象塞进响应式：原始响应只保留一次，视图层用轻量映射。

ts
// ❌ 整个 response.data 进入 ref，深度响应式代理开销大
const detail = ref(response.data)

// ✅ 只保留视图字段
const detail = ref({
  id: response.data.id,
  title: response.data.title,
  price: response.data.price
})

1.3 官方测量入口 ​

  • 微信开发者工具「性能」面板的 setData 视图能看到每次调用的数据量与耗时，这是唯一权威口径；
  • 真机 Trace 中查看 setData 时间片与主线程阻塞；
  • 记录优化前后的「次数 × 单次字节」，而不是只记录总耗时。

二、长列表：节点数比数据量更致命 ​

首屏 200 个节点以内是较安全的范围。超过后滚动帧率明显下降，且 scroll-view 的 scroll-into-view 会变慢。

vue
<!-- 虚拟列表最小实现：只渲染可视区 + 缓冲 -->
<script setup lang="ts">
import { computed, ref } from 'vue'

const props = defineProps<{ items: Array<{ id: string; [k: string]: unknown }>; itemHeight: number }>()

const scrollTop = ref(0)
const viewportHeight = 600
const buffer = 5

const start = computed(() => Math.max(0, Math.floor(scrollTop.value / props.itemHeight) - buffer))
const end = computed(() =>
  Math.min(props.items.length, Math.ceil((scrollTop.value + viewportHeight) / props.itemHeight) + buffer)
)
const visible = computed(() => props.items.slice(start.value, end.value))
const totalHeight = computed(() => props.items.length * props.itemHeight)

function onScroll(e: { detail: { scrollTop: number } }) {
  scrollTop.value = e.detail.scrollTop
}
</script>

<template>
  <scroll-view scroll-y style="height: 600px" @scroll="onScroll">
    <view :style="{ height: totalHeight + 'px', position: 'relative' }">
      <view
        v-for="(item, i) in visible"
        :key="item.id"
        :style="{ position: 'absolute', top: (start + i) * itemHeight + 'px', height: itemHeight + 'px' }"
      >
        <slot :item="item" />
      </view>
    </view>
  </scroll-view>
</template>

三、内存快照与泄漏归因 ​

3.1 H5：三份快照法 ​

text
① 进入页面前 → 拍 Snapshot A
② 操作 5 轮（进入 → 滚动 → 返回）→ 拍 Snapshot B
③ 再操作 5 轮 → 拍 Snapshot C

在 DevTools → Memory → Comparison 中对比 A/B/C：

现象结论
B 比 A 多，C 与 B 持平正常（缓存或框架对象）
C 持续比 B 多泄漏，看 Retained Size 排序
Detached DOM 数量持续增长组件/监听未释放

3.2 三类泄漏的归因代码 ​

闭包：定时器、事件、Promise 链持有大数组。修法是在卸载时清理并断开引用（详见 8.3）。

全局单例：全局对象保存页面实例或 Activity。用引用计数/WeakRef（H5 与 App 可用，小程序不支持）自检：

ts
// 调试期检查全局引用（仅在开发环境启用）
const registry = new Set<object>()

export function trackGlobal(obj: object, name: string) {
  if (process.env.NODE_ENV !== 'development') return
  registry.add(obj)
  // #ifdef H5
  console.log(`[global] ${name} tracked, size=${registry.size}`)
  // #endif
}

export function untrackGlobal(obj: object, name: string) {
  registry.delete(obj)
  // #ifdef H5
  console.log(`[global] ${name} released, size=${registry.size}`)
  // #endif
}

原生 View 未销毁：plus.nativeObj.View 必须 close()；Android WXComponent 在 onActivityDestroy 里 removeAllViews；iOS 自定义 View 置 nil。代码模板见 8.3。

四、渲染与图片成本 ​

项做法验收
图片尺寸CDN 按容器尺寸裁剪（?w=750&q=75）首屏图片总量 ≤ 500KB
图片格式WebP（小程序与 App 均支持）同清晰度体积下降 20–40%
懒加载列表图片进入可视区再加载首屏请求数下降
长任务大数据计算放到分片/空闲执行主线程单任务 ≤ 50ms
动画用 CSS transform，不逐帧 setData帧率 ≥ 50fps

图片懒加载示例：

vue
<image
  v-for="img in images"
  :key="img.id"
  :src="img.visible ? img.url : placeholder"
  lazy-load
  mode="aspectFill"
  @appear="img.visible = true"
/>

五、优化顺序（先做收益最大的） ​

text
1. 减 setData 数据量（去掉无用字段）
2. 减首屏节点数（分页 / 虚拟列表）
3. 压图片体积（裁剪 + WebP + 懒加载）
4. 拆分包（非首屏页面进分包）
5. 修内存泄漏（长会话应用必须做）
6. 微优化（节流、防抖、缓存）

前两步通常能解决 70% 的卡顿；直接上「微优化」往往收效甚微。
