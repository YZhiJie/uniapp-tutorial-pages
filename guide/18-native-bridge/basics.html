18.1 基础入门：UTS 插件开发 ​

前两个模块讲的是「传统原生插件」：Android 写 Java、iOS 写 ObjC/Swift，各自产出一个二进制。它能力强，但成本高：同一能力要写两遍，还要分别维护两套工程。

UTS（uni TypeScript）是 uni-app 给出的另一条路：用 TypeScript 语法写一份代码，编译期分别生成 Kotlin 与 Swift。本章讲清 UTS 能做什么、不能做什么，以及一个 UTS 插件从目录到调用的完整结构。

一、UTS 是什么 ​

mermaid
flowchart LR
    A[UTS 源码<br/>TypeScript 语法] --> B{编译}
    B --> C[Android: Kotlin]
    B --> D[iOS: Swift]
    B --> E[Web: JS]
    C --> F[原生能力]
    D --> F
    E --> G[浏览器能力]

三个关键事实：

  1. UTS 不是 TypeScript 运行时。它没有 JS 引擎，源码在编译期被翻译成目标平台语言。
  2. 类型必须写全。any 在 UTS 里受限，编译期就要确定类型。
  3. 一份逻辑，多个平台实现。跨平台逻辑写在 interface.uts，平台差异写在 app-android/index.uts / app-ios/index.uts。

二、UTS 与 TS 的差异 ​

能力TypeScriptUTS说明
类型系统结构类型名义 + 结构，限制更多不支持复杂映射类型
any允许严格受限用 UTSJSONObject 代替动态对象
undefined / null宽松需要显式处理推荐用可选属性
泛型完整部分支持复杂泛型可能编译失败
装饰器支持不支持用普通函数
npm 包任意不能直接用需 UTS 化或原生依赖
DOM / BOM有无不是浏览器环境
反射 / 动态属性有无编译期确定
异常try/catch支持但跨语言映射有限

2.1 类型写法 ​

ts
// UTS 推荐写法
export type DeviceInfo = {
  brand: string
  model: string
  osVersion: string
}

export type Result<T> = {
  code: number
  message: string
  data?: T
}

不推荐：

ts
// 不要这样写：UTS 对动态索引与 any 支持很差
const obj: any = {}
obj[key] = value

需要处理不确定结构的 JSON 时：

ts
const json = JSON.parse(text) as UTSJSONObject
const name = json.getString('name') ?? ''
const age = json.getNumber('age') ?? 0

三、UTS 插件目录结构 ​

以 uni_modules/uni-uts-demo 为例：

text
uni_modules/uni-uts-demo/
├── package.json                 # uni_modules 插件描述
├── utssdk/
│   ├── interface.uts            # 跨平台类型与 API 声明
│   ├── app-android/
│   │   └── index.uts            # Android 实现（编译为 Kotlin）
│   ├── app-ios/
│   │   └── index.uts            # iOS 实现（编译为 Swift）
│   ├── app-harmony/
│   │   └── index.uts            # HarmonyOS 实现（可选）
│   └── web/
│       └── index.uts            # H5 实现（可选）
└── readme.md

package.json 关键字段：

jsonc
{
  "id": "uni-uts-demo",
  "name": "UTS 插件演示",
  "version": "1.0.0",
  "description": "演示 UTS 类型、双端实现与调用",
  "uni_modules": {
    "dependencies": []
  }
}

目录名、id、调用时的插件名必须一致。UTS 插件通过 uni_modules 自动注册，不需要像传统原生插件那样手动 requireNativePlugin（具体调用方式见下文）。

四、一个最小可编译的 UTS 插件 ​

4.1 interface.uts ​

ts
// 跨平台共用的类型与函数签名
export type AddOptions = {
  a: number
  b: number
}

export type AddResult = {
  value: number
}

/**
 * 两数相加
 * 这里只写声明，不写实现
 */
export function add(options: AddOptions): AddResult

4.2 app-android/index.uts ​

ts
import { AddOptions, AddResult } from '../interface'

export function add(options: AddOptions): AddResult {
  return {
    value: options.a + options.b
  } as AddResult
}

4.3 app-ios/index.uts ​

ts
import { AddOptions, AddResult } from '../interface'

export function add(options: AddOptions): AddResult {
  return {
    value: options.a + options.b
  } as AddResult
}

两端实现相同，是因为这段逻辑本身跨平台。真实项目里，差异通常出现在：

  • Android 用 UTSAndroid.getAppContext() 拿 Context。
  • iOS 用 UTSiOS 命名空间的对应能力。
  • 双端可用的 uni.* API 优先复用，避免各写一遍。

4.4 调用 ​

ts
// 业务代码
import { add } from '@/uni_modules/uni-uts-demo'

const result = add({ a: 1, b: 2 })
console.log(result.value) // 3

UTS 插件也可以导出为 uni.requireNativePlugin 风格（在 package.json 中配置），但对于新项目，优先用 ES import，类型提示更完整。

五、调用原生能力：两条路径 ​

5.1 优先用跨端 API ​

ts
export function getPlatformName(): string {
  const info = uni.getSystemInfoSync()
  return info.platform ?? 'unknown'
}

这类能力各端都有，没必要写两份原生代码。

5.2 必须调用平台原生类时 ​

UTS 支持在平台实现文件里访问原生类，但语法与类名映射随平台和版本变化。下面是结构示意，实际类名与 import 写法以官方 UTS 语法文档为准：

ts
// app-android/index.uts（示意）
export function showNativeToast(text: string): void {
  // UTSAndroid 提供宿主 Context / Activity
  const context = UTSAndroid.getAppContext()
  // 通过 UTS 的原生类导入能力拿到 android.widget.Toast
  // 具体 import 形式以当前 HBuilderX 版本为准
  // Toast.makeText(context, text, Toast.LENGTH_SHORT).show()
}
ts
// app-ios/index.uts（示意）
export function showNativeToast(text: string): void {
  // UTSiOS 提供主线程调度能力
  // 通过 UTS 的原生类导入能力拿到 UIKit
  // 在主线程展示 UIAlertController / 自定义 Toast
}

工程建议：

  • 能在 interface.uts 里用 uni.* 解决的，不要下沉到原生。
  • 必须下沉时，把原生调用封装成一个窄接口（如 showNativeToast(text)），不要把平台细节泄漏给业务层。
  • 每个平台实现都要有降级实现（如 H5 用 uni.showToast）。

六、调试 UTS 插件 ​

手段AndroidiOS
日志console.log → Logcat（tag 含 uts）console.log → Xcode Console
运行HBuilderX 运行到真机 / 自定义基座HBuilderX 运行到真机 / 自定义基座
断点原生层调试需看生成的 Kotlin原生层调试需看生成的 Swift
编译错误HBuilderX 控制台会给出 UTS 行号同上

调试顺序：

  1. 先确认 interface.uts 类型声明通过编译。
  2. 再确认平台实现文件被选中（Android 跑 app-android，iOS 跑 app-ios）。
  3. 日志打不出时，检查是否被条件编译剪掉。
  4. 原生崩溃看原生堆栈，不要只看 JS 报错。

常见编译错误 ​

错误原因处理
Type 'any' is not supported使用了 any改成具体类型或 UTSJSONObject
Cannot find module平台目录缺失补 app-android/index.uts / app-ios/index.uts
Property does not exist类型未声明在 interface.uts 补字段
Not supported syntax用了 TS 高级特性改写为 UTS 支持的写法
运行时报 undefined平台实现未导出检查 export function 与签名

七、UTS 的边界：什么时候不该用 ​

场景推荐
轻量原生能力（设备信息、加密、Toast、权限）✅ UTS
需要复用现有 Java/Swift SDK❌ 传统原生插件
复杂原生 UI（地图、相机预览、视频硬解）❌ WXComponent / 原生插件
团队没有原生经验，但想低成本跨端✅ UTS
需要 npm 生态 / 复杂泛型 / 动态反射❌ 传统原生或 JS 方案
需要上架插件市场✅ UTS（可分发）

一句话判断：逻辑简单、双端都要、没有重 SDK → UTS；重 SDK、重 UI、重定制 → 传统原生插件。

八、UTS vs 传统原生插件 ​

维度UTS 插件传统原生插件（aar/framework）
语言TypeScript 风格Java/Kotlin + ObjC/Swift
代码量一份逻辑两端两份
原生 SDK 复用弱强
调试中等强（原生 IDE）
生态成长中成熟
包体积较小取决于 SDK
适合轻能力、跨端复用重能力、深度定制
