15.1 基础入门：混合开发全景与三条武器 ​

学习目标 ​

读完本章，你应该能独立回答：

  • 什么时候应该「混合开发」，什么时候应该「纯 uni-app 跨端」，什么时候又不得不「原生混编」？
  • uni-app 混合开发的「三条武器」分别是什么，各自的适用边界在哪里？
  • JSBridge 在 iOS / Android / 小程序三端的底层通信机制分别是什么？

一、三个概念的边界：Hybrid vs Cross-platform vs Native ​

很多团队一听到「混合开发」就觉得是「降级方案」。其实它不是。纯跨端（uni-app）、混合（H5 + 原生 + 小程序互操作）、原生混编（Kotlin / Swift + uni-app） 三者的选择，本质上是在回答一个问题：你的业务是「单容器」还是「多容器」？

三者决策表 ​

维度纯跨端（uni-app 全栈）混合开发（Hybrid）原生混编（Native Embedding）
核心诉求一套代码跑三端，快速上线既有独立 H5 站点，又有 App / 小程序壳，三者要互通已有存量原生 App，想引入 uni-app 做新模块
技术栈纯 Vue 3 + uni APIVue 3 / React 独立 H5 + uni-app + 原生桥原生 Kotlin/Swift + uni-app 子工程
开发团队1–3 人前端即可需要 H5 团队 + 小程序/App 团队协同必须有原生 Android + iOS 工程师
上线速度最快（两周出首版）中等（H5 可热更，App/小程序需审核）最慢（要集成进原生工程，编译链更长）
典型场景工具类、内容类、中小型电商大型电商（H5 官网 + App + 小程序三端互通）、企业 SaaS、编辑器类产品银行、证券、大型互联网公司（已有原生 App 不能推倒重来）
性能天花板中等（App 端依赖 HTML5+ 引擎）高（需要原生能力的地方直接桥接 SDK）极高（原生 UI + 跨端模块优势互补）
状态管理复杂度低（Pinia 一套通吃）高（需要设计三端账号互通 + 本地缓存同步）中（原生侧状态 + uni-app 侧状态需要桥接）

什么时候选哪个？ ​

决策要点：

  • 没有独立 H5、没有存量原生 App → 纯跨端最省心，别过度设计。
  • 有独立 H5 且 App/小程序只是壳 → 混合开发，用 web-view 承载 H5。
  • 已有原生 App 但想加新业务模块 → 原生混编，把 uni-app 子工程嵌入。
  • 需要重型原生 SDK（高德地图 3D、微信支付、银行 U盾、AR/VR SDK）→ 必须用 requireNativePlugin 桥接。

二、三条武器清单 ​

uni-app 混合开发的「三条武器」对应三种不同粒度的跨容器通信能力。请把它们和你的业务场景一一对上。

武器一：<web-view> 组件 ​

最浅的一层——把一个 H5 页面直接塞进 uni-app 页面里。

vue
<!-- uni-app App 或小程序里 -->
<template>
  <web-view :src="h5EditorUrl" @message="onMessage"></web-view>
</template>

<script setup>
const h5EditorUrl = 'https://your-cdn.com/editor.html'

function onMessage(e) {
  // H5 通过 postMessage 发过来的数据
  console.log('收到 H5 消息:', e.detail.data)
}
</script>
属性App 端小程序端H5 端
是否支持✅ 原生级 webview✅ 真 web-view 组件❌ 自己就是 H5，套壳无意义
能加载的 URL任意 https必须在小程序后台配置「业务域名」白名单—
与宿主通信plus.webview.currentWebview().evalJS() 或 postMessagewx.miniProgram.postMessage—
性能中（webview 独立进程）中—
适用场景独立 H5 页面嵌入（编辑器、文档、活动页）同 App 端—

⚠️ 小程序端 web-view 有严格限制：只能加载 https 且域名必须在后台配置，不允许加载任何 http 或未备案域名。而且 web-view 页面不能作为小程序首页（2020 年后的新规则）。

武器二：plus.webview.* API（仅 App 端） ​

原生级别的 webview 控制——可以创建、销毁、层级管理、evalJS 双向注入。这是 App 端混合开发的核心。

js
// #ifdef APP-PLUS

// 1. 在当前页面创建一个 webview 子页
const currentWebview = plus.webview.currentWebview()
const h5Webview = plus.webview.create(
  'https://your-h5.com/editor',  // URL
  'h5-editor',                    // webview id
  {                               // 样式
    top: '100px',
    bottom: '0px',
    progress: { color: '#007AFF' }
  },
  {                               // 额外参数（H5 可以通过 plus.webview.getWebviewById 拿到）
    token: 'xxx',
    userId: '123'
  }
)
currentWebview.append(h5Webview)

// 2. 向 H5 注入 JS
h5Webview.evalJS(`
  window.receiveFromNative(${JSON.stringify({ type: 'init', data: { theme: 'dark' } })})
`)

// 3. 从 H5 收消息（H5 侧用 plus.webview.postMessageToUniNView）
plus.webview.addEventListener('customEvent', (msg) => {
  console.log('来自 H5:', msg)
})

// #endif
能力说明
plus.webview.create创建新 webview（比 <web-view> 组件更灵活，可多层叠加）
plus.webview.evalJS向目标 webview 注入并执行一段 JS
plus.webview.currentWebview拿到当前 uni-app 页面的 webview 对象
plus.webview.getWebviewById按 id 找到任意 webview（H5 里也能用）
plus.webview.postMessageToUniNViewH5 向 uni-app 宿主页面发消息（App 端专属）

武器三：uni.requireNativePlugin ​

最深的一层——直接调用原生 SDK。当你需要的能力 JS 世界里根本没有（比如高德地图 3D 引擎、微信支付底层、银行加密 SDK、蓝牙协议栈），就走这条路。

js
// #ifdef APP-PLUS
// 在 manifest.json 勾选插件市场的「高德地图」后
const amap = uni.requireNativePlugin('AMap')

// 调用原生方法
amap.init({
  key: 'your-amap-key',
  mapType: 3  // 3D 地图
}, (res) => {
  if (res.code === 0) {
    amap.showMap({
      lat: 39.9,
      lng: 116.4,
      zoom: 12
    })
  }
})
// #endif
对比维度<web-view>plus.webview.*requireNativePlugin
通信方式postMessage（单向为主）evalJS + postMessage（双向）插件桥接（JS → 原生 → 原生回调 JS）
粒度页面级嵌入webview 级精细控制原生 SDK 级调用
跨端兼容性App / 小程序都能用仅 App 端仅 App 端（小程序用 wx.requirePlugin）
性能中（webview 渲染）中（同 webview）高（直接原生调用）
开发成本低中高（需要原生 SDK 集成）
适合场景嵌入独立 H5 页精细控制 webview 层级 / evalJS调用 JS 世界没有的重型能力

三、JSBridge 基础：三端通信机制 ​

JSBridge 是混合开发的灵魂——让 JS 容器里的代码和原生容器互相说话。不同平台底层机制完全不同。

全景架构 ​

      WK -->|"userContentController didReceiveScriptMessage"| NATIVE_IOS[iOS 原生代码]
      NATIVE_IOS -->|"evaluateJavaScript"| H5_IOS

      NATIVE_AND -->|"evalJS"| H5_AND
    end

      H5_MP[web-view H5] -->|"wx.miniProgram.postMessage"| MP_BRIDGE[微信 JSSDK]
      MP_BRIDGE -->|"消息队列"| MP_HOST[小程序宿主]
      MP_HOST -->|"navigateTo / postMessage"| H5_MP
    end

1. iOS 端：WKWebView MessageHandler ​

iOS 上所有 JSBridge 最终都走 WKWebView 的 userContentController 机制。

H5 侧：

js
// H5 页面里，向 iOS 原生发消息
function callNative(method, params) {
  if (window.webkit?.messageHandlers?.[method]) {
    window.webkit.messageHandlers[method].postMessage(params)
  }
}

// 示例：请求原生打开相机
callNative('openCamera', { source: 'gallery', maxSize: 5 })

// 接收来自 iOS 原生的消息
window.receiveFromNative = function (payload) {
  console.log('iOS 原生说:', payload)
}

iOS 原生侧（Swift 示例，了解原理即可）：

swift
// 原生注册消息处理器
class BridgeHandler: NSObject, WKScriptMessageHandler {
    func userContentController(_ controller: WKUserContentController,
                               didReceive message: WKScriptMessage) {
        guard message.name == "openCamera" else { return }
        let params = message.body as? [String: Any]
        // 执行原生逻辑，然后回传给 H5
        webView.evaluateJavaScript("window.receiveFromNative(\(responseJSON))")
    }
}

2. Android / uni-app App 端：plus.webview.evalJS + postMessage ​

H5 侧（跑在 uni-app App 的 web-view 里）：

js
// 判断自己是否在 uni-app App 里
function isInUniApp() {
  return /uni-app/.test(navigator.userAgent)
}

// 向 uni-app 宿主发消息
function sendToUniApp(data) {
  if (isInUniApp()) {
    // App 端：通过 HTML5+ 桥
    plus.webview.currentWebview().parent().evalJS(
      `onH5Message(${JSON.stringify(data)})`
    )
  }
}

// 接收 uni-app 宿主的消息
window.onUniAppMessage = function (data) {
  console.log('uni-app 说:', data)
}

uni-app 宿主侧：

js
// #ifdef APP-PLUS
// 宿主页面定义好供 H5 调用的函数
window.onH5Message = function (data) {
  uni.showToast({ title: '收到 H5:' + data.type, icon: 'none' })

  // 回消息给 H5
  const h5Webview = plus.webview.getWebviewById('my-h5-page')
  h5Webview?.evalJS(
    `window.onUniAppMessage(${JSON.stringify({ ok: true })})`
  )
}
// #endif

3. 小程序端：wx.miniProgram.postMessage ​

H5 侧（跑在小程序 web-view 里）：

js
// 微信 JSSDK 是小程序 web-view 自动注入的
// 向小程序发消息（小程序在特定时机——后退、组件销毁、分享——才会收到）
wx.miniProgram.postMessage({ data: { type: 'saveDraft', content: '...' } })

// 跳转小程序页面
wx.miniProgram.navigateTo({ url: '/pages/editor/editor' })
wx.miniProgram.postToMiniProgramAppMessage({ hello: 'world' })

// 判断是否在小程序里
function isInMiniProgram() {
  return window.__wxjs_environment === 'miniprogram'
}

小程序宿主侧：

vue
<template>
  <web-view src="https://your-h5.com/editor" @message="onH5Message" />
</template>

<script setup>
function onH5Message(e) {
  // e.detail.data 是 H5 通过 wx.miniProgram.postMessage 发过来的消息数组
  // 注意：小程序端 web-view 的 message 事件只在特定时机触发
  const lastMsg = e.detail.data[e.detail.data.length - 1]
  console.log('来自 H5:', lastMsg)
}
</script>

四、FAQ ​

Q1：混合开发是不是意味着 App 性能一定差？

不一定。性能差的是「纯 H5 壳」——整个 App 只有一个 webview。但 uni-app 的混合开发通常是「原生页面 + web-view 子页面」或「uni-app 页 + H5 组件」。需要高性能的部分走原生，需要快速迭代的部分走 H5。性能可以做到和纯原生接近。

Q2：<web-view> 和 plus.webview.create 选哪个？

  • 新手：先用 <web-view> 组件，声明式用法更简单。
  • 需要精细控制（层级、关闭、动画、多 webview 叠加）：用 plus.webview.create。
  • 一个常见坑：<web-view> 组件在 App 端默认是全屏的，想让它只占半个屏幕，必须用 plus.webview.create + position 参数。

Q3：小程序 web-view 的 postMessage 为什么收不到？

这是微信最容易踩的坑。微信小程序 web-view 的 postMessage 不是实时推送的——它只在小程序后退、组件销毁、分享这三个时机触发 @message 事件。如果你需要 H5 和小程序实时通信，要用另一条路：URL query + wx.miniProgram.navigateTo 携带参数，或者用 wx.openEmbeddedMiniProgram（H5 打开小程序）反向通信。

Q4：JSBridge 消息大小有限制吗？

有。iOS WKWebView 的 postMessage 建议不超过 256KB；Android 端 evalJS 字符串过长会抛异常（>1MB 风险高）；小程序 postMessage 虽然文档没写限制，但超过 100KB 建议分片。
