7.1 基础入门：四端差异全景图 ​

「一套代码」不等于「一套体验完全相同」。跨端工程的核心能力是：知道哪里必然不同，并提前设计隔离层。

差异总矩阵 ​

维度H5微信小程序App（iOS/Android）
运行载体浏览器微信宿主独立安装包
逻辑环境同一 JS 线程独立逻辑层（无 DOM）独立 JS 引擎
路由浏览器 history/hash页面栈 ≤10页面栈同小程序
DOM/BOM✅❌不建议使用
本地存储localStorage 约 5–10MB单 key 约 1MB类小程序 + SQLite/文件
网络fetch/XHRwx.request 并发上限 10原生请求，无跨域限制
图片支持全部 web 格式部分格式受限原生支持
支付H5 支付/跳转微信支付微信/支付宝/苹果内购等
推送❌（Web Push 受限）订阅消息UniPush/厂商通道
分享Web Share/复制链接onShareAppMessageuni.share 原生面板
扫码无原生能力（需自定义）uni.scanCodeuni.scanCode
安装分发URL 即达小程序审核/包体 2MB+分包应用商店审核
热更新天然版本发布wgt 资源热更（合规前提下）

生命周期差异 ​

应用级（App.vue）：

ts
import { onLaunch, onShow, onHide } from '@dcloudio/uni-app'

onLaunch((options) => {
  // 启动参数：场景值、扫码进入的 query 等（小程序尤其重要）
  console.log('launch', options)
})
onShow(() => {})
onHide(() => {})

需要注意：

  • 小程序没有「退出 App」概念，onHide 可能只是切后台；不要在 hide 里销毁全局状态。
  • App 端切后台的 JS 执行会被系统挂起，定时器、音频都要按平台规则处理。
  • H5 端的「前后台」对应 visibilitychange，uni 已尽量对齐，但倒计时类功能仍建议以服务器时间校准。

导航与页面容器差异 ​

  • 小程序：导航栏由原生渲染，navigationStyle: custom 后需自绘且要避开胶囊按钮（右上胶囊位置用 uni.getMenuButtonBoundingClientRect() 计算）。
  • H5：无原生导航栏，Vite/H5 容器提供浏览器式标题栏，自定义导航实现成本最低。
  • App：原生导航栏支持更多能力（搜索框、实时网络标题等），但 webview 渲染区域与原生导航的衔接要真机检查。

经验：页面内容区从安全区开始布局，导航相关交互（滚动渐变、沉浸式）在三端分别验收。

样式差异高频点 ​

  1. 单位：rpx 三端通用；App/H5 超宽屏下 rpx 会放大，管理后台类页面可混用 px 或 max-width 约束。
  2. 固定定位：小程序 fixed 相对页面，键盘弹起表现不同；聊天输入框这类场景必须真机测。
  3. CSS 能力：过滤器 filter、mix-blend-mode、部分 grid 特性在小程序低版本基础库不支持。
  4. 字体：小程序需 uni.loadFontFace，字体文件走 HTTPS。
  5. 背景图：小程序不支持本地路径 background-image，改 image 标签/网络地址/base64。
  6. 1px 边框：rpx 方案在各端表现不完全一致，可用 transform: scale(0.5) 伪元素方案统一。
  7. 安全区：刘海屏、底部横条统一用 env(safe-area-inset-*)。

能力差异：以「分享」为例 ​

同一个业务动作「邀请好友」，三端实现完全不同：

ts
async function invite() {
  // #ifdef H5
  await navigator.clipboard?.writeText(window.location.href)
  uni.showToast({ title: '链接已复制，快去分享吧', icon: 'none' })
  // #endif

  // #ifdef MP-WEIXIN
  // 小程序不能主动拉起分享，需要配置 onShareAppMessage，由用户点右上角/按钮触发
  uni.showShareMenu({ withShareTicket: true })
  uni.showToast({ title: '请点右上角 ··· 分享给好友', icon: 'none' })
  // #endif

  // #ifdef APP-PLUS
  uni.share({
    provider: 'weixin',
    scene: 'WXSceneSession',
    type: 0,
    title: '一起来学 uni-app',
    href: 'https://example.com',
    success: () => uni.showToast({ title: '分享成功' })
  })
  // #endif
}

这正是下一篇 7.2 条件编译 要系统化解决的问题。

存储差异与容量规划 ​

存储容量特点
uni.setStorageSync小程序单 key 1MB，总 10MB同步 API、读写快，适合 token/设置/小状态
App SQLite / 文件系统大大量离线数据、聊天记录（11.2）
H5 localStorage约 5MB仅 H5 分支使用
H5 IndexedDB大大量结构化数据，仅 H5

原则：公共层用 uni 存储 API；大数据量走平台专属方案并通过适配层隔离。

支付与登录差异（最容易翻车的两块） ​

  • 登录：小程序有 uni.login 静默 code 换 openid 的独有链路；H5 是账号密码/扫码/OAuth 跳转；App 有一键登录（运营商）与三方 SDK 授权。统一设计：抽象出 loginByPlatform()，内部走条件编译，产出统一的业务 token。
  • 支付：订单在业务服务端创建，各端拿服务端返回的不同支付参数调起对应渠道；永远不要在客户端拼装支付金额。

跨端验收节奏建议 ​

  1. 开发主端（团队最熟的一端，通常是小程序或 H5）。
  2. 每完成一个页面，立刻在第二端跑一次——差异早暴露成本最低。
  3. 提交前清单：导航栏、键盘、滚动、网络失败、权限拒绝、弱网、分享/支付六条链路逐端过。

常见问题 ​

Q：要不要从第一天就追求四端一致？ 不要。追求「业务逻辑一致、体验各端原生」。平台惯例本身就是体验的一部分（如小程序分享必须用户触发）。

Q：条件分支会越来越多怎么治理？ 把分支收敛到 src/platforms/ 的适配模块，页面只调用统一接口，不写散落的 ifdef。下两篇正是这个方法。
