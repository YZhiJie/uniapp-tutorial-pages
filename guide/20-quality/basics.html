20.1 基础入门：可测性设计与测试金字塔 ​

「写测试」不难，「让代码可测」才难。大量 uni-app 项目的测试写不下去，根因不是团队不愿意写，而是业务逻辑和 uni.*、页面栈、全局 store 缠在一起，离开真机就 import 失败。

本篇先解决可测性，再谈测试分层。

一、uni-app 的测试金字塔 ​

层级占比测什么运行环境速度
纯逻辑单测~70%价格、状态机、校验、格式化Node毫秒
Store / Composable~20%状态迁移、副作用编排、缓存Node + Pinia毫秒
组件测试~8%渲染、事件、props/emitsjsdom秒
E2E~2%登录 → 加购 → 下单主链路真机 / 浏览器 / 模拟器分钟

倒金字塔（大量 E2E、几乎没有单测）在 uni-app 里尤其昂贵：小程序 E2E 需要开发者工具与真机，跑一次几十秒，失败原因还难定位。

二、可测性的四个改造手法 ​

2.1 纯函数优先：把 uni 挡在边界外 ​

ts
// ❌ 不可测：函数内部直接读系统信息
export function isTablet() {
  return uni.getSystemInfoSync().deviceType === 'pad'
}

// ✅ 可测：值从参数进来
export function isTablet(deviceType?: string) {
  return deviceType === 'pad'
}

// 运行时适配放在薄薄一层
export function isTabletRuntime() {
  return isTablet(uni.getSystemInfoSync().deviceType)
}

2.2 依赖注入：把网络、时间、随机数变成参数 ​

ts
// ❌ 时间与网络写死
export async function createOrder(payload: OrderInput) {
  const createdAt = Date.now()
  const res = await uni.request({ url: '/orders', method: 'POST', data: payload })
  return { ...payload, createdAt, id: res.data.id }
}

// ✅ 依赖可替换
export interface OrderDeps {
  now: () => number
  post: (url: string, data: unknown) => Promise<{ id: string }>
}

export function createOrderService(deps: OrderDeps) {
  return async function createOrder(payload: OrderInput) {
    const createdAt = deps.now()
    const res = await deps.post('/orders', payload)
    return { ...payload, createdAt, id: res.id }
  }
}

测试里传入固定时钟与假 post，断言稳定；生产环境再注入真实实现。

2.3 避免模块顶层副作用 ​

ts
// ❌ import 即执行，测试环境直接崩
const store = useUserStore()
const info = uni.getSystemInfoSync()

// ✅ 延迟到调用时
export function getEnv() {
  return uni.getSystemInfoSync()
}

2.4 用接口隔离平台能力 ​

定位、支付、推送都定义接口，平台实现放 providers/：

ts
export interface PaymentProvider {
  pay(params: Record<string, string>): Promise<void>
}

// providers/payment.ts
export const wxPayment: PaymentProvider = {
  pay(params) {
    return new Promise((resolve, reject) => {
      uni.requestPayment({
        provider: 'wxpay',
        ...params,
        success: () => resolve(),
        fail: (err) => reject(new Error(err.errMsg))
      })
    })
  }
}

用例层只依赖 PaymentProvider 接口，测试传一个内存实现即可。

三、跑通第一个测试 ​

仓库根目录已有 Vitest 配置（vitest.config.ts），新增测试文件即被识别：

ts
// tests/domain/priceOrder.test.ts
import { describe, expect, it } from 'vitest'
import { priceOrder } from '@/domain/pricing/priceOrder'

describe('priceOrder', () => {
  it('空购物车应付为 0', () => {
    expect(priceOrder([], 0, 0).payable).toBe(0)
  })

  it('运费与优惠同时生效', () => {
    const res = priceOrder([{ skuId: 'sku-1', price: 99, quantity: 2 }], 12, 20)
    expect(res.goodsAmount).toBe(198)
    expect(res.payable).toBe(190)
  })
})
bash
pnpm test                 # 全量
pnpm test:watch           # 监听
pnpm vitest run tests/domain/priceOrder.test.ts   # 单文件

四、mock 全局 uni 的正确姿势 ​

确实需要测调用 uni.* 的薄适配层时，用 vi.stubGlobal，并在每个用例后还原：

ts
import { afterEach, beforeEach, describe, expect, it, vi } from 'vitest'

beforeEach(() => {
  vi.stubGlobal('uni', {
    getStorageSync: vi.fn(() => 'token-123'),
    request: vi.fn()
  })
})

afterEach(() => {
  vi.unstubAllGlobals()
})

it('从本地读取 token 注入请求头', () => {
  const header = buildAuthHeader()
  expect(header.Authorization).toBe('Bearer token-123')
  expect(uni.getStorageSync).toHaveBeenCalledWith('token')
})

不要写一个「万能 uni mock」覆盖所有 API——它会让测试通过但行为与真机不符。只 mock 当前用例依赖的方法，其余保持缺失，逼出真实依赖。

五、测试命名与结构 ​

推荐 describe 按「被测单元」，it 按「行为 + 条件」：

ts
describe('orderStatus', () => {
  it('待支付订单可取消', () => {})
  it('已支付订单不可取消', () => {})
  it('退款中订单不可再次申请退款', () => {})
})

反例：it('test1')、it('should work')。测试名是失败时的第一诊断信息，必须能独立读懂。

六、验收标准 ​

bash
pnpm test
# 期望：所有纯逻辑用例在 Node 环境通过，无 uni-app 运行时依赖

pnpm test:coverage
# 期望：达到当前棘轮阈值（lines 70 / branches 85 / functions 88）

自查三问：

  1. 把 uni 全局删掉，领域层测试还能跑吗？
  2. 新增一个价格边界条件，是否 5 分钟内能补一条测试？
  3. 测试失败时，名字是否直接指出「哪个行为在什么条件下不对」？
