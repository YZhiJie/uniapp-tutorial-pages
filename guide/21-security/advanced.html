21.2 进阶应用：防重放、越权检查与插件供应链审计 ​

令牌解决「你是谁」，本篇解决另外三件事：请求不能被篡改重放、用户不能访问别人的数据、引入的插件与依赖不能被投毒。

一、防重放：时间戳 + 随机数 + 签名 ​

重放攻击：攻击者截获一个「转账 100 元」请求，原样发送 10 次。HTTPS 只能防窃听，不能防重放。标准解法是让每个请求携带一次性随机数（nonce）与时间戳，并对关键参数签名。

1.1 客户端：规范化参数后签名 ​

签名密钥不能是长期 appSecret。用当前用户的 access token 作为 HMAC 密钥（可撤销、按用户隔离），或者服务端下发的短期会话密钥。

bash
pnpm add @noble/hashes
ts
// src/services/requestSign.ts
import { hmac } from '@noble/hashes/hmac'
import { sha256 } from '@noble/hashes/sha256'
import { bytesToHex, utf8ToBytes } from '@noble/hashes/utils'

export interface SignedRequest {
  timestamp: number
  nonce: string
  sign: string
}

/**
 * 规范化字符串：参数按 key 字典序拼接，空值不参与，避免「同参数不同顺序」签出不同结果。
 */
export function canonicalize(params: Record<string, unknown>) {
  return Object.keys(params)
    .filter((key) => params[key] !== undefined && params[key] !== null && params[key] !== '')
    .sort()
    .map((key) => `${key}=${String(params[key])}`)
    .join('&')
}

export function signRequest(
  params: Record<string, unknown>,
  path: string,
  token: string
): SignedRequest {
  const timestamp = Date.now()
  // 16 字节随机数，碰撞概率可忽略；同一 nonce 服务端只接受一次
  const nonce = bytesToHex(crypto.getRandomValues(new Uint8Array(16)))
  const canonical = canonicalize(params)
  const message = `${timestamp}\n${nonce}\n${path}\n${canonical}`
  const sign = bytesToHex(hmac(sha256, utf8ToBytes(token), utf8ToBytes(message)))
  return { timestamp, nonce, sign }
}

发送时把三件套放进请求头：

ts
const signed = signRequest(payload, '/api/orders', accessToken)
await request({
  url: '/api/orders',
  method: 'POST',
  data: payload,
  header: {
    Authorization: `Bearer ${accessToken}`,
    'X-Timestamp': String(signed.timestamp),
    'X-Nonce': signed.nonce,
    'X-Sign': signed.sign
  }
})

1.2 服务端：验签 + nonce 去重 + 时间窗 ​

ts
// server/middleware/antiReplay.ts
import { createHmac, timingSafeEqual } from 'node:crypto'

const WINDOW_MS = 5 * 60_000 // 允许 5 分钟时钟偏差

export async function antiReplay(req, res, next) {
  const timestamp = Number(req.headers['x-timestamp'])
  const nonce = String(req.headers['x-nonce'] ?? '')
  const sign = String(req.headers['x-sign'] ?? '')

  if (!timestamp || Math.abs(Date.now() - timestamp) > WINDOW_MS) {
    return res.status(401).json({ code: 'TIMESTAMP_EXPIRED' })
  }
  if (!nonce || nonce.length < 16) {
    return res.status(401).json({ code: 'NONCE_INVALID' })
  }

  // 1. nonce 一次性：Redis SET NX + TTL，窗口内重复直接拒绝
  const fresh = await redis.set(`nonce:${req.auth.userId}:${nonce}`, '1', {
    nx: true,
    px: WINDOW_MS
  })
  if (!fresh) return res.status(409).json({ code: 'REPLAY_DETECTED' })

  // 2. 用同样的 canonicalize 重建签名
  const canonical = canonicalize({ ...req.query, ...req.body })
  const message = `${timestamp}\n${nonce}\n${req.path}\n${canonical}`
  const expected = createHmac('sha256', req.auth.accessToken).update(message).digest('hex')

  const a = Buffer.from(expected, 'hex')
  const b = Buffer.from(sign, 'hex')
  if (a.length !== b.length || !timingSafeEqual(a, b)) {
    return res.status(401).json({ code: 'SIGN_INVALID' })
  }

  next()
}

四个必须注意的点：

点说明
时钟偏差客户端时间可被篡改，窗口不能太严（建议 ±5 分钟），关键操作再叠加服务端时间
nonce 存储必须带 TTL，否则存储无限增长；按用户维度隔离
签名字符串前后端必须使用完全一致的规范化规则与换行符
比较方式使用常数时间比较（timingSafeEqual），避免时序侧信道

防重放的边界：它能防「原样重放」，不能防「攻击者持有合法 token 后自行构造新请求」。后者靠越权检查与风控。

二、越权检查：前端藏入口 ≠ 后端有权限 ​

越权分两类：

  • 水平越权（IDOR）：用户 A 改 URL 里的订单号，看到用户 B 的订单。
  • 垂直越权：普通用户调用管理员接口（如退款审核）。

2.1 错误示范 ​

ts
// ❌ 只凭前端传的 userId 查数据
app.get('/api/orders', async (req, res) => {
  const orders = await db.order.findMany({ where: { userId: req.query.userId } })
  res.json(orders)
})

攻击者把 userId 改成别人的即可。正确做法：用户身份只从服务端会话取，永不信任请求参数。

ts
// ✅ 从鉴权上下文取 userId，并校验资源归属
app.get('/api/orders/:id', async (req, res) => {
  const order = await db.order.findById(req.params.id)
  // 不存在与无权限都返回 404，避免攻击者枚举资源是否存在
  if (!order || order.userId !== req.auth.userId) {
    return res.status(404).json({ code: 'NOT_FOUND' })
  }
  res.json(order)
})

2.2 能力模型：把权限写成可测的声明 ​

ts
// server/auth/abilities.ts
export type Ability =
  | 'order:read'
  | 'order:cancel'
  | 'order:refund'
  | 'admin:refund:approve'

const roleAbilities: Record<string, Ability[]> = {
  customer: ['order:read', 'order:cancel'],
  support: ['order:read', 'order:refund'],
  admin: ['order:read', 'order:cancel', 'order:refund', 'admin:refund:approve']
}

export function can(role: string, ability: Ability) {
  return roleAbilities[role]?.includes(ability) ?? false
}

// 路由守卫
export function requireAbility(ability: Ability) {
  return (req, res, next) => {
    if (!can(req.auth.role, ability)) {
      return res.status(403).json({ code: 'FORBIDDEN' })
    }
    next()
  }
}

app.post('/api/orders/:id/refund', requireAbility('order:refund'), refundHandler)

前端只把能力列表用于隐藏入口，所有写操作仍由服务端 requireAbility + 资源归属双重校验。

三、插件与依赖供应链审计 ​

原生插件、npm 包、SDK 都可能成为投毒入口。审计分四步：

3.1 来源与版本锁定 ​

项要求
npm 依赖提交 pnpm-lock.yaml，CI 使用 --frozen-lockfile
原生插件固定 commit / tag，禁止引用「最新」；记录来源仓库与维护人
aar / framework记录 SHA-256，构建时校验，防止被替换
私有源配置 @scope 指向可信 registry，禁止同名包从公共源解析
bash
# 校验 aar 产物指纹（构建脚本中执行）
shasum -a 256 android/libs/push-sdk.aar
# 与 PLUGIN_LOCK.json 中登记值比对，不一致直接失败
json
{
  "android/libs/push-sdk.aar": "9f2c...e1",
  "ios/Frameworks/PushSDK.framework": "3ab7...90",
  "source": "git@git.example.com:mobile/push-sdk.git#v1.4.2"
}

3.2 权限与能力核对 ​

原生插件常申请大量权限。接入前逐条核对「权限 → 用途 → 触发时机」，拒绝与业务无关的权限（完整三列表见 21.3）。

3.3 依赖漏洞与许可证扫描 ​

bash
pnpm security:scan            # 仓库内密钥 / 危险 API
pnpm security:scan:deps       # pnpm audit：高危/严重依赖
pnpm security:gitleaks        # 需要安装 gitleaks
pnpm security:trivy           # 需要安装 trivy
bash
# 仅生产依赖、只看高危
pnpm audit --prod --audit-level high

3.4 插件初始化与网络行为审查 ​

原生插件接入前做一次「黑盒审查」：

  • 抓包看是否向未知域名上报设备信息；
  • 检查初始化时机（是否在冷启动主线程做耗时操作）；
  • 检查是否注册全局 Activity 生命周期 / 常驻服务；
  • 确认卸载 SDK 后是否可彻底移除（避免死代码与合规风险）。

四、验收标准 ​

bash
pnpm security:scan
# 期望：error 0；危险 API 仅有登记过的警告

pnpm security:scan:deps
# 期望：high/critical 为 0，或有 .trivyignore 记录的豁免原因

接口层验收：

  1. 用 Burp / Charles 重放同一个下单请求，服务端返回 REPLAY_DETECTED。
  2. 把 URL 里的订单 id 换成他人 id，返回 404 而非数据。
  3. 普通用户 token 调管理员接口，返回 403。
  4. 篡改请求体任一字段但不重算签名，返回 SIGN_INVALID。
