21.3 实战案例：隐私清单、权限矩阵与安全扫描流水线 ​

安全与合规最终要落到三份可检查的材料：数据清单（收集了什么）、权限三列表（为什么收集、什么时候收集）、流水线（怎么防止回退）。本篇给出可直接改造的模板与命令。

一、数据清单：先盘点，再谈合规 ​

按「字段 → 用途 → 存储位置 → 保留期 → 是否共享」逐项登记。示例（电商应用）：

数据用途存储保留期共享给第三方
手机号登录、订单通知服务端账号存续期短信服务商
收货地址履约配送服务端订单完成后 180 天物流服务商
设备型号 / OS兼容性适配、崩溃归因埋点平台90 天崩溃监控服务
位置（粗略）附近门店服务端（不落原始坐标）实时使用，不持久化地图服务商
相片 / 相机头像、售后凭证对象存储账号存续期CDN
剪贴板口令解析（可选）不落盘不保留无

三条常见违规：

  1. 收集了但没写进清单（如第三方 SDK 偷偷采集 IMEI）。
  2. 写了用途但实际用于其他目的（如定位用于风控而非门店）。
  3. 保留期缺失（日志里手机号永久留存）。

2.2 Android：Manifest 权限最小化 ​

xml
<!-- android/app/src/main/AndroidManifest.xml -->
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
  <uses-permission android:name="android.permission.INTERNET" />
  <uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
  <!-- 只在门店功能使用，必须配合运行时申请与用途说明 -->
  <uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
  <!-- 明确不需要的权限，用 tools:node="remove" 防止被第三方 SDK 合并进来 -->
  <uses-permission android:name="android.permission.READ_PHONE_STATE" tools:node="remove" />
</manifest>

第三方 SDK 的 manifest 会「权限合并」，必须用 tools:node="remove" 显式剥离不需要的权限，并在构建后核对：

bash
# 查看最终合并的权限列表
./gradlew :app:processReleaseManifest
grep -o 'android.permission.[A-Z_]*' app/build/intermediates/merged_manifest/release/AndroidManifest.xml | sort -u

2.3 微信小程序：隐私协议与授权时机 ​

manifest.json 中声明隐私校验，并在用户触发相关能力前调用授权：

json
{
  "mp-weixin": {
    "__usePrivacyCheck__": true,
    "requiredPrivateInfos": ["getLocation", "chooseLocation"]
  }
}
ts
// 在真正使用位置能力前调用，而不是冷启动就弹
async function chooseStore() {
  // #ifdef MP-WEIXIN
  await new Promise<void>((resolve, reject) => {
    uni.requirePrivacyAuthorize({
      success: () => resolve(),
      fail: () => reject(new Error('用户未同意隐私协议'))
    })
  })
  // #endif
  uni.chooseLocation({ success: (res) => console.log(res.address) })
}

三、权限 - 用途 - 时机三列表 ​

这张表是应用商店审核与内部评审的必交材料，也是代码评审的依据：

权限 / 能力用途（用户可理解）触发时机拒绝后的降级
相机拍摄头像、上传售后凭证点击「拍照」时引导从相册选择
相册选择头像、上传凭证点击「从相册选择」时提供默认头像
位置（粗略）展示附近门店、计算配送范围进入「附近门店」或填写地址时手动选择城市
位置（精确）不申请——
通知订单状态、支付结果首次下单成功后，说明用途再申请站内信兜底
剪贴板识别口令 / 邀请码用户主动点击「粘贴」时手动输入
通讯录不申请——
设备信息（OAID）崩溃归因、反作弊冷启动后异步，且可关闭使用随机安装 ID

写作要求：

  • 「用途」必须让非技术用户看懂，不能写「用于提升服务质量」。
  • 「时机」必须是用户主动触发，禁止冷启动批量申请。
  • 每一行都要有「拒绝后的降级」，否则审核会判定为强制授权。

四、安全扫描流水线 ​

仓库已内置三个可运行脚本，接入根 package.json：

json
{
  "scripts": {
    "depcruise": "node scripts/depcruise.mjs",
    "security:scan": "node scripts/security-scan.mjs",
    "security:scan:strict": "node scripts/security-scan.mjs --strict",
    "security:scan:deps": "node scripts/security-scan.mjs --deps",
    "security:gitleaks": "gitleaks detect --config .gitleaks.toml --redact",
    "security:trivy": "trivy fs --config trivy.yaml --skip-check-update --timeout 10m .",
    "security:trivy:ci": "trivy fs --config trivy.yaml --skip-check-update --timeout 10m --exit-code 1 ."
  }
}
bash
# 日常与 CI 阻断项（离线可跑）
pnpm security:scan

# 严格模式：警告也阻断（发布前）
pnpm security:scan:strict

# 依赖漏洞（需要网络）
pnpm security:scan:deps

# 更全面的开源方案（需自行安装二进制）
pnpm security:gitleaks
pnpm security:trivy

当前扫描结果（本仓库实测）：

text
[security-scan] 扫描 100+ 个文件
⚠️  .vitepress/theme/components/CatalogExplorer.vue:231  [dangerous-html] 直接写入 HTML…
汇总：error 0 / warn 3
✅ 安全基线扫描通过

警告来自搜索高亮组件的 v-html，内容经过 safeHighlight 转义，属于已评审的例外。scripts/security-scan.mjs 支持在行尾加 security-scan:ignore 注释登记例外。

国内网络下执行：

bash
TRIVY_DB_REPOSITORY=docker.m.daocloud.io/aquasec/trivy-db:2 \
TRIVY_JAVA_DB_REPOSITORY=docker.m.daocloud.io/aquasec/trivy-java-db:1 \
pnpm security:trivy

CI 任务：

yaml
security:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0
    - uses: pnpm/action-setup@v4
    - run: pnpm install --frozen-lockfile
    - run: pnpm security:scan
    - run: pnpm security:scan:deps
    - name: gitleaks
      run: pnpm dlx gitleaks detect --config .gitleaks.toml --redact --no-banner
    - name: 安装 Trivy
      run: |
        curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh -s -- -b "$RUNNER_TEMP/bin" v0.69.3
        echo "$RUNNER_TEMP/bin" >> "$GITHUB_PATH"
    # HIGH / CRITICAL 任一命中即阻断合并
    - run: pnpm security:trivy:ci

pnpm-lock.yaml 必须提交；--frozen-lockfile 保证 CI 不会静默升级依赖。

五、泄露事件响应（Runbook） ​

阶段动作时限
发现扫描告警 / 外部报告，确认密钥是否真实有效1 小时
遏制吊销密钥、下线 token、关闭受影响接口2 小时
取证导出调用日志，确认影响范围与数据量24 小时
修复轮换密钥、修复泄漏路径、补扫描规则72 小时
复盘记录根因、影响、改进项，更新权限三列表1 周

关键：先吊销再排查。密钥一旦进入公开仓库，即使 force push 删除，也可能已被缓存/爬取。

六、验收清单 ​

bash
# 1. 密钥与危险 API
pnpm security:scan

# 2. 依赖高危漏洞
pnpm security:scan:deps

# 3. 分层不被安全改造破坏
pnpm depcruise

# 4. 文档与片段门禁
pnpm sync:fm:check && pnpm check:snippets

人工核对：

  • [ ] 权限三列表与代码中的实际申请一一对应，无「申请了但没用途」的权限。
  • [ ] 冷启动不弹任何权限框；每个权限都能指出触发它的用户动作。
  • [ ] PrivacyInfo.xcprivacy 与实际收集的数据类型一致。
  • [ ] Android 合并后的 Manifest 中不存在被 SDK 带入的多余权限。
  • [ ] 泄露演练：随机挑一个 token，能在 10 分钟内完成吊销与日志取证。
