16.3 实战案例：原生插件离线打包、签名与 ABI ​

这一章把前两章的知识收口成一个可交付的产物：一个能装进 uni-app 基座、能上架、能升级的 Android 原生插件。我们以一个「设备信息 + 原生 Toast」插件 UniNativeDemo 为例，走完 编码 → 编译 aar → 接入 uni-app → 打基座 → 签名发版 全链路。

配套源码在示例工程中：

text
uniapp-demo/nativeplugins/UniNativeDemo/
├── package.json
├── android/
│   ├── build.gradle
│   ├── settings.gradle
│   └── src/main/java/com/example/unidemo/NativeDemoModule.java
├── ios/
│   ├── NativeDemoModule.h
│   └── NativeDemoModule.m
└── README.md

仓库只提交源码与构建脚本，不提交二进制 .aar / .framework。原因：二进制体积大、无法审查、且与本地 SDK 版本强绑定。按本节命令在本地构建即可。

一、需求与接口设计 ​

能力JS API返回
读取设备信息getDeviceInfo({}, cb){ code, data: { brand, model, osVersion, abi } }
原生 ToastshowToast({ text }, cb){ code, message }
原生 UI（nvue）<native-demo-view label="..." />点击触发 onNativeClick

接口约定先定死，后面 Java、iOS、JS 三端都按这个契约实现。不要一边写原生一边改字段名，这是联调返工的最大来源。

二、从源码到 aar ​

2.1 工程结构 ​

text
nativeplugins/UniNativeDemo/android/
├── settings.gradle
├── gradle.properties
├── build.gradle
└── src/main/
    ├── AndroidManifest.xml
    └── java/com/example/unidemo/
        ├── NativeDemoModule.java
        └── NativeDemoView.java

settings.gradle：

groovy
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
    }
}
rootProject.name = 'UniNativeDemo'
include ':android'

build.gradle：

groovy
plugins {
    id 'com.android.library' version '8.6.1' apply false
}

android/build.gradle（模块级）：

groovy
plugins {
    id 'com.android.library'
}

android {
    namespace 'com.example.unidemo'
    compileSdk 34

    defaultConfig {
        minSdk 21
        targetSdk 34
        consumerProguardFiles 'consumer-rules.pro'
    }

    buildTypes {
        release {
            minifyEnabled false
            proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
        }
    }

    compileOptions {
        sourceCompatibility JavaVersion.VERSION_17
        targetCompatibility JavaVersion.VERSION_17
    }
}

dependencies {
    // weex / WXModule 由宿主提供，不能让 aar 自带
    compileOnly files('libs/weex_core.jar')
    implementation 'androidx.core:core:1.13.1'
}

libs/weex_core.jar 从你使用的 HBuilderX 离线 SDK 中拷贝。不同版本路径不同，找不到时先确认离线 SDK 是否完整。

2.2 编译 ​

bash
cd nativeplugins/UniNativeDemo/android

# 首次生成 wrapper（如果仓库没带 gradlew）
gradle wrapper --gradle-version 8.9

./gradlew :android:assembleRelease

# 产物
ls android/build/outputs/aar/
# android-release.aar

把产物按 HBuilderX 约定命名并放到插件目录：

bash
cp android/build/outputs/aar/android-release.aar \
   ../android/UniNativeDemo.aar

最终 nativeplugins/UniNativeDemo/ 下应同时存在：

text
package.json
android/UniNativeDemo.aar
ios/NativeDemoModule.h
ios/NativeDemoModule.m

三、接入 uni-app 工程 ​

3.1 页面调用 ​

vue
<!-- uniapp-demo/pages/native/native-plugin.vue -->
<template>
  <view class="page">
    <button type="primary" @click="loadDevice">读取设备信息</button>
    <button @click="toast">原生 Toast</button>
    <view v-if="info" class="card">
      <text>品牌：{{ info.brand }}</text>
      <text>型号：{{ info.model }}</text>
      <text>系统：{{ info.osVersion }}</text>
      <text>ABI：{{ info.abi }}</text>
    </view>
    <view v-else class="tip">当前端未加载原生插件（H5 / 小程序会走降级提示）</view>
  </view>
</template>

<script setup lang="ts">
import { ref } from 'vue'

interface DeviceInfo {
  brand: string
  model: string
  osVersion: string
  abi: string
}

const info = ref<DeviceInfo | null>(null)

function getPlugin() {
  // #ifdef APP-PLUS
  return uni.requireNativePlugin('UniNativeDemo')
  // #endif
  // #ifndef APP-PLUS
  return null
  // #endif
}

function loadDevice() {
  const plugin = getPlugin()
  if (!plugin || typeof plugin.getDeviceInfo !== 'function') {
    uni.showToast({ title: '非 App 端或插件未打入基座', icon: 'none' })
    return
  }
  plugin.getDeviceInfo({}, (res: { code: number; data?: DeviceInfo; message?: string }) => {
    if (res.code === 0 && res.data) {
      info.value = res.data
    } else {
      uni.showToast({ title: res.message || '读取失败', icon: 'none' })
    }
  })
}

function toast() {
  const plugin = getPlugin()
  if (!plugin || typeof plugin.showToast !== 'function') {
    uni.showToast({ title: '非 App 端或插件未打入基座', icon: 'none' })
    return
  }
  plugin.showToast({ text: '来自 Android 原生模块' }, () => {})
}
</script>

<style>
.page { padding: 32rpx; display: flex; flex-direction: column; gap: 24rpx; }
.card { padding: 24rpx; background: #f5f6f7; border-radius: 12rpx; display: flex; flex-direction: column; gap: 8rpx; }
.tip { color: #999; font-size: 26rpx; }
</style>

3.2 manifest 与 pages.json ​

manifest.json 的 app-plus 下增加插件声明：

jsonc
{
  "app-plus": {
    "nativePlugins": {
      "UniNativeDemo": {}
    }
  }
}

pages.json 注册页面：

jsonc
{
  "path": "pages/native/native-plugin",
  "style": { "navigationBarTitleText": "原生插件演示" }
}

本地插件放在 nativeplugins/ 目录即可被 HBuilderX 识别；nativePlugins 声明用于云打包与基座勾选。两处都配置，避免「本地能跑、云打包丢失」。

四、打自定义基座与云打包 ​

4.1 自定义调试基座 ​

  1. HBuilderX → 运行 → 运行到手机或模拟器 → 制作自定义调试基座。
  2. 在插件列表中勾选 UniNativeDemo。
  3. 选择 Android，等待云端返回基座 APK。
  4. 安装基座后，用「运行到自定义基座」启动项目。

验证：

js
const plugin = uni.requireNativePlugin('UniNativeDemo')
console.log(Object.keys(plugin)) // 应包含 getDeviceInfo / showToast

4.2 云打包 ​

  • HBuilderX → 发行 → 原生 App-云打包。
  • 勾选插件、上传 .jks、填写别名与密码。
  • 渠道包按需勾选；首次上传商店建议先打一个正式包做签名校验。

云打包的边界：无法插入未在 nativeplugins/ 声明的任意 .so，也无法在云端执行自定义 Gradle 脚本。重度定制走离线打包。

五、离线打包：把产物放进原生工程 ​

5.1 生成 uni-app 资源 ​

HBuilderX → 发行 → 原生 App-本地打包 → 生成本地打包 App 资源，得到：

text
app/resources/
└── __UNI__XXXXXXX/
    └── www/

5.2 导入 Android 离线 SDK 工程 ​

  1. 下载与 HBuilderX 版本匹配的 Android 离线 SDK。
  2. Android Studio 打开其中的 HBuilder-Integrate-AS 工程。
  3. 把 www/ 拷到 app/src/main/assets/apps/__UNI__XXXXXXX/www/。
  4. 修改 app/src/main/assets/data/dcloud_control.xml 中的 appid。
  5. 把 UniNativeDemo.aar 放进 app/libs/，并在 app/build.gradle 添加：
groovy
dependencies {
    implementation fileTree(dir: 'libs', include: ['*.aar', '*.jar'])
}
  1. 按插件要求补充 AndroidManifest.xml 权限与组件。
  2. Sync Gradle → 运行到真机验证。

不同版本的离线 SDK 对插件注册的文件与字段不同（dcloud_control.xml / dcloud_properties.xml / feature.json）。以你下载的 SDK 内附文档为准，不要跨版本套用教程。

5.3 离线打包的优缺点 ​

维度云打包离线打包
环境只需 HBuilderXAndroid Studio + SDK
自定义 Gradle / 原生代码受限完全自由
构建速度排队，不可控本地增量快
CI/CD弱强（./gradlew assembleRelease）
适合标准插件、快速验证自研插件、企业级发版

六、签名：.jks 与 assembleRelease ​

6.1 生成签名文件 ​

bash
keytool -genkeypair -v \
  -keystore release.jks \
  -alias release \
  -keyalg RSA \
  -keysize 2048 \
  -validity 36500

要点：

  • 有效期设 25 年以上（36500 天），避免几年后被迫换签名导致无法覆盖升级。
  • .jks、别名、密码必须进公司密钥管理（1Password / Vault / CI Secret），不要提交到 Git。
  • 首次上架后签名不可更换；换签名 = 新应用，老用户无法升级。

6.2 Gradle 配置签名 ​

groovy
android {
    signingConfigs {
        release {
            storeFile file(System.getenv("RELEASE_STORE_FILE") ?: "release.jks")
            storePassword System.getenv("RELEASE_STORE_PASSWORD")
            keyAlias System.getenv("RELEASE_KEY_ALIAS")
            keyPassword System.getenv("RELEASE_KEY_PASSWORD")
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
            minifyEnabled true
            shrinkResources true
        }
    }
}
bash
export RELEASE_STORE_FILE=/secure/release.jks
export RELEASE_STORE_PASSWORD=******
export RELEASE_KEY_ALIAS=release
export RELEASE_KEY_PASSWORD=******

./gradlew :app:assembleRelease
# app/build/outputs/apk/release/app-release.apk

6.3 校验产物 ​

bash
# 包名、版本、权限、ABI
aapt dump badging app-release.apk | head -20

# 签名校验（v1/v2/v3）
apksigner verify --verbose app-release.apk

如果使用 Google Play，改打 AAB：

bash
./gradlew :app:bundleRelease

七、ABI 与体积控制 ​

7.1 只打需要的 ABI ​

groovy
android {
    defaultConfig {
        ndk {
            abiFilters 'arm64-v8a', 'armeabi-v7a'
        }
    }
}

7.2 按 ABI 拆包（可选） ​

groovy
android {
    splits {
        abi {
            enable true
            reset()
            include 'arm64-v8a', 'armeabi-v7a'
            universalApk false
        }
    }
}

收益与代价：

  • 收益：单包体积显著下降，下载转化率更高。
  • 代价：商店需要上传多个 APK；国内部分商店对多包支持不完整。
  • 折中：主包只带 arm64-v8a，老设备走单独渠道包。

7.3 体积排查 ​

bash
# 查看 APK 内各文件占比
unzip -l app-release.apk | sort -k1 -n -r | head -20

# 查看 .so 分布
unzip -l app-release.apk | grep 'lib/'

常见大头：未压缩图片、重复的 .so、未开启 shrinkResources、调试符号未剥离。

八、常见坑与排查表 ​

现象根因处理
覆盖安装失败 INSTALL_FAILED_UPDATE_INCOMPATIBLE新旧包签名不同卸载旧包；统一签名
INSTALL_FAILED_NO_MATCHING_ABIS设备 ABI 不在包内补 arm64-v8a / armeabi-v7a
UnsatisfiedLinkError.so 缺失或 ABI 不匹配检查 jniLibs 与 abiFilters
插件方法 undefined类名/包名与 package.json 不一致对齐全限定类名
云打包后插件丢失未勾选插件 / 未声明 nativePlugins基座与 manifest 双检查
混淆后崩溃反射类/回调被混淆consumer-rules.pro 保留插件类
Duplicate class com.taobao.weex...插件自带 weex改 compileOnly
上架被拒「仅 32 位」未打 64 位加 arm64-v8a
targetSdk 过低被拒未跟随商店政策每年更新 targetSdk
