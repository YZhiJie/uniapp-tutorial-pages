一、商品列表：分页 + 搜索 + 取消旧请求 ​

vue
<!-- pages/goods/list.vue -->
<script setup lang="ts">
import { computed, ref } from 'vue'
import { onLoad, onReachBottom, onPullDownRefresh } from '@dcloudio/uni-app'
import { goodsApi, type GoodsListItem, type GoodsQuery } from '@/api/modules/goods'

const list = ref<GoodsListItem[]>([])
const query = ref<GoodsQuery>({ page: 1, size: 20, keyword: '' })
const total = ref(0)
const loading = ref(false)
let task: UniApp.RequestTask | null = null

const finished = computed(() => list.value.length >= total.value && list.value.length > 0)

onLoad((options) => {
  query.value.category = options?.category
  query.value.keyword = options?.keyword
  load(true)
})

onReachBottom(() => load(false))
onPullDownRefresh(async () => {
  await load(true)
  uni.stopPullDownRefresh()
})

async function load(reset: boolean) {
  if (loading.value) return
  if (!reset && finished.value) return
  loading.value = true
  if (reset) query.value.page = 1
  task?.abort()

  try {
    const res = await goodsApi.list(query.value, (t) => (task = t))
    if (reset) list.value = res.list
    else list.value.push(...res.list)
    total.value = res.total
    query.value.page++
  } catch (e) {
    if (!String(e).includes('abort')) uni.showToast({ title: '加载失败', icon: 'none' })
  } finally {
    loading.value = false
  }
}
</script>

二、SKU 规格选择器核心算法 ​

规格选择的难点：根据已选规格判断哪些规格值无货可点，以及拼出选中的 SKU。

ts
// src/utils/sku.ts
import type { Sku, SpecValue } from '@/types/goods'

export function findSku(skus: Sku[], selected: number[]): Sku | undefined {
  if (selected.length === 0) return undefined
  const key = [...selected].sort((a, b) => a - b).join(',')
  return skus.find((sku) => [...sku.specValues].sort((a, b) => a - b).join(',') === key)
}

/**
 * 判断某个规格值在当前选择路径下是否可选：
 * 存在至少一个「包含该值且库存>0」的 SKU，且该 SKU 与已选其他规格不冲突。
 */
export function isSpecValueAvailable(
  skus: Sku[],
  selected: Map<number, number>, // groupId -> valueId
  targetGroupId: number,
  targetValueId: number
): boolean {
  return skus.some((sku) => {
    if (sku.stock <= 0) return false
    const values = new Set(sku.specValues)
    if (!values.has(targetValueId)) return false
    for (const [gid, vid] of selected) {
      if (gid === targetGroupId) continue
      if (!values.has(vid)) return false
    }
    return true
  })
}

    uni.redirectTo({ url: `/pages/order/result?id=${order.id}` })
  } finally {
    submitting.value = false
  }
}

服务端职责：接收支付渠道异步通知、幂等改订单状态、关单回补库存（9.3 练习）。

5.1 支付渠道矩阵：同一业务，不同参数与跳转方式 ​

uni.requestPayment 只是统一入口，各渠道的「下单 → 调起 → 结果」链路完全不同：

渠道端服务端下单 API客户端调起结果可靠来源关键差异
微信 JSAPI微信小程序v3/pay/transactions/jsapiuni.requestPayment({ provider: 'wxpay', ... })微信异步通知 + 主动查单需要 openid，参数含 package/paySign
微信 H5H5（微信内）transactions/h5 或 JSAPIWeixinJSBridge / 跳转 mweb_url异步通知非微信浏览器会降级为扫码
微信 AppApptransactions/appuni.requestPayment({ provider: 'wxpay' })异步通知 + 查单需开放平台绑定应用签名
支付宝小程序支付宝小程序alipay.trade.createuni.requestPayment({ provider: 'alipay' })异步通知参数是 tradeNO，不是签名串
支付宝 H5H5alipay.trade.wap.pay表单跳转 / location.href异步通知 + return_url同步回跳只用于展示，不作为支付成功依据
支付宝 AppAppalipay.trade.app.payuni.requestPayment({ provider: 'alipay' })异步通知需处理未安装支付宝的降级

选型原则：

  1. 能小程序内支付就不要跳 H5，跳转链路会丢失登录态与页面上下文。
  2. App 端必须同时接微信与支付宝，单一渠道的支付成功率通常低 10–20 个百分点。
  3. H5 端微信支付受浏览器限制，非微信环境要提供「扫码支付 + 轮询订单状态」的兜底页。

5.2 客户端轮询 vs 服务端通知：职责必须分清 ​

这是支付最容易出事故的边界。记住一句话：客户端永远不能决定「支付成功」，只能展示服务端认定的结果。

角色做什么不做什么
客户端拉起支付；支付返回后轮询订单状态；展示结果页；失败时提供「继续支付」入口不改订单状态；不把 requestPayment 的 success 当作最终成功；不在本地写「已支付」
服务端验签接收渠道异步通知；幂等落库；更新支付单与订单；处理金额不一致；关单退库存不依赖客户端回传结果
对账任务每日拉取渠道账单，与本地支付单逐笔比对；自动补单/标记差错不直接改业务订单，差错进入人工队列

客户端轮询只解决「体验」：让用户不用反复进出页面。真正的状态以服务端为准，即使轮询接口返回 paid，也应来自服务端已处理的支付单。

5.3 服务端幂等与对账 ​

渠道通知会重试（微信最长重试 24 小时），同一笔支付可能收到多次通知。幂等的关键是事件表唯一约束 + 事务内状态迁移，而不是「先查再写」：

ts
// server/payment/notify.ts（Node + PostgreSQL 示意，可直接改造为你的框架）
app.post('/pay/notify/:channel', async (req, res) => {
  // 1. 必须用原始报文验签，不能用 JSON.parse 后的对象
  const valid = verifySign(req.params.channel, req.rawBody, req.headers)
  if (!valid) return res.status(401).send('invalid sign')

  const event = parseNotify(req.params.channel, req.rawBody)
  // event: { eventId, outTradeNo, amountFen, status, paidAt }

  await db.transaction(async (tx) => {
    // 2. 事件表唯一索引兜底：重复通知直接跳过
    const inserted = await tx.query(
      `INSERT INTO payment_event (event_id, channel) VALUES ($1, $2)
       ON CONFLICT (event_id) DO NOTHING`,
      [event.eventId, req.params.channel]
    )
    if (inserted.rowCount === 0) return

    // 3. 只允许「待支付/支付中」→「已支付」，重复迁移不产生副作用
    await tx.query(
      `UPDATE payment
          SET status = 'paid', paid_at = $2, channel_trade_no = $3
        WHERE out_trade_no = $1 AND status IN ('pending', 'paying')`,
      [event.outTradeNo, event.paidAt, event.eventId]
    )

    // 4. 金额校验：不一致不自动改单，进差错队列
    const { rows } = await tx.query(
      `SELECT amount_fen FROM payment WHERE out_trade_no = $1`,
      [event.outTradeNo]
    )
    if (rows[0]?.amount_fen !== event.amountFen) {
      await tx.query(
        `INSERT INTO payment_anomaly (out_trade_no, expected_fen, actual_fen, reason)
         VALUES ($1, $2, $3, 'amount_mismatch')`,
        [event.outTradeNo, rows[0]?.amount_fen, event.amountFen]
      )
      return
    }

    await tx.query(
      `UPDATE orders SET status = 'paid' WHERE payment_no = $1 AND status = 'pending_payment'`,
      [event.outTradeNo]
    )
  })

  // 5. 必须按渠道要求返回成功标识；抛 500 会触发渠道重试
  res.status(200).send('success')
})

每日对账任务（伪 SQL 思路，真实项目按渠道账单文件解析）：

sql
-- 渠道有、本地无：补单或进差错
SELECT c.out_trade_no, c.amount_fen, 'channel_only' AS diff_type
FROM channel_bill c
LEFT JOIN payment p ON p.out_trade_no = c.out_trade_no
WHERE p.id IS NULL;

-- 金额或状态不一致：进人工队列
SELECT p.out_trade_no, p.amount_fen, c.amount_fen, p.status, c.status
FROM payment p
JOIN channel_bill c ON c.out_trade_no = p.out_trade_no
WHERE p.amount_fen <> c.amount_fen
   OR (p.status = 'paid' AND c.status <> 'SUCCESS');

对账的三个纪律：

  • 对账以渠道账单为准，不以本地订单为准。
  • 差错只记录、不自动改金额；补单动作必须可审计（谁、何时、依据哪条账单）。
  • 关单与退库存放在「确认未支付」之后，避免用户正在支付时库存被回补又被抢走。

5.4 退款与部分退款状态机 ​

退款不是「把订单改成已退款」这么简单。支付单与退款单要分开建模，支持一笔支付多次部分退款：

mermaid
stateDiagram-v2
    [*] --> applying: 用户/客服发起
    applying --> processing: 审核通过，调用渠道退款
    processing --> success: 渠道返回 SUCCESS
    processing --> failed: 渠道返回 FAIL / 余额不足
    failed --> processing: 换渠道或重试
    success --> partial: 累计退款 < 支付金额
    success --> refunded: 累计退款 = 支付金额
    partial --> refunded: 后续退款补齐
    failed --> closed: 人工关闭
    refunded --> [*]
当前状态允许动作幂等要求
applying审核通过 / 驳回同一退款单号只能审核一次
processing查询渠道结果查询不改变状态，只更新渠道流水
success继续部分退款累计退款额不得超过支付额
failed重试 / 关闭重试复用原退款单号
refunded无终态，任何再次退款请求直接拒绝
ts
// 部分退款：用「已退金额 + 本次金额」做乐观锁，防并发超退
const updated = await tx.query(
  `UPDATE refund
      SET refunded_fen = refunded_fen + $2, status = 'processing'
    WHERE refund_no = $1
      AND status IN ('applying', 'failed')
      AND refunded_fen + $2 <= (SELECT amount_fen FROM payment WHERE out_trade_no = $1)`,
  [refundNo, refundFen]
)
if (updated.rowCount === 0) {
  throw new BizError('REFUND_EXCEED', '退款金额超过可退余额或状态不允许')
}

退款结果同样以渠道异步通知 + 主动查询为准。客户端只展示「退款处理中」，到账时间由渠道决定（微信 1–3 个工作日，支付宝通常更快），不要在前端写死「立即到账」。

六、关键体验细节 ​

  1. 库存售罄按钮置灰但保留可点击提示（告诉用户为什么不能买）。
  2. 价格变化（服务端 reconcile 后）在确认页用醒目动画/提示，不静默改价。
  3. 待支付订单显示服务端返回的剩余支付时间，本地每秒倒计时但不用本地时间决定关单。
  4. 支付中断后从订单列表仍可继续支付或取消。
