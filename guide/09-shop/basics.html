9.1 基础入门：电商应用架构与数据模型 ​

从本篇起进入综合实战。电商是最典型的信息流 + 交易型应用，覆盖前面所有知识点：列表分页、状态管理、路由鉴权、支付适配、性能优化。

页面地图 ​

text
pages/
├─ index/index            首页（会场、金刚位、推荐流）
├─ goods/
│  ├─ list                分类/搜索结果列表（分页、筛选）
│  └─ detail              商详（图集、规格选择、店铺、评价）
├─ cart/index             购物车（tabBar）
├─ order/
│  ├─ confirm             确认订单（地址、优惠券、金额明细）
│  ├─ list                订单列表（状态 tab）
│  └─ detail              订单详情/物流
├─ address/
│  ├─ list
│  ├─ edit
│  └─ picker             选择地址（eventChannel 回传）
├─ mine/index             个人中心（tabBar）
└─ login/index            登录（分包也可，但通常在主包）
subPackages:
├─ pages/marketing/       拼团/秒杀/抽奖等活动页
└─ pages/service/         客服、退款售后

分包原则回顾：交易主链路（浏览→购物车→下单→订单）放主包保证跳转速度；营销活动放分包（见 8.2）。

核心领域模型 ​

商品与 SKU ​

ts
// src/types/goods.ts
export interface Spu {
  id: number
  title: string
  subtitle: string
  mainImages: string[]
  detailHtml: string
  shopId: number
  skus: Sku[]
}

export interface Sku {
  id: number
  specValues: number[]      // 规格值 id 组合，如 [黑(1), XL(8)]
  price: number             // 现价（元）
  originPrice?: number      // 划线价
  stock: number
  image?: string
}

export interface SpecGroup {
  id: number
  name: string              // 颜色 / 尺码
  values: SpecValue[]
}
export interface SpecValue {
  id: number
  name: string
  disabled?: boolean        // 组合无库存时禁用
}

关键认知：用户购买的是 SKU 不是 SPU。「黑色 XL」才是一个可定价、可扣库存的实体。

购物车 ​

见 6.3 购物车 store，服务端通常也保存一份购物车（跨设备同步），客户端策略：

  • 未登录：本地 store，购物车数据随登录动作在服务端合并。
  • 已登录：本地操作乐观更新，后台增量同步；以服务端快照校准价格库存（reconcile）。

订单 ​

ts
// src/types/order.ts
export type OrderStatus =
  | 'pending_payment'  // 待付款
  | 'pending_ship'     // 待发货
  | 'shipped'          // 待收货
  | 'completed'        // 已完成
  | 'cancelled'        // 已取消
  | 'refunding'        // 售后中

export interface OrderItem {
  skuId: number
  title: string
  spec: string
  price: number
  quantity: number
  cover: string
}

export interface Order {
  id: string             // 业务订单号（字符串，避免 JS 大整数精度问题）
  status: OrderStatus
  items: OrderItem[]
  amountGoods: number
  amountFreight: number
  amountDiscount: number
  amountPayable: number
  createdAt: string
  expireAt: string       // 待付款超时时间
}

金额：客户端只展示，服务端才裁决 ​

  • 传输与存储金额单位由后端统一（推荐分，用整数避免浮点误差）。
  • 客户端做即时计算（合计、满减预览）提升体验，但下单金额以服务端返回为准。
  • 大 id（订单号/雪花 id）一律字符串传输，JSON.parse 对超过 2^53 的数字会丢精度。

下单链路时序 ​

mermaid
sequenceDiagram
  participant U as 用户
  participant C as 客户端
  participant S as 服务端
  participant P as 支付渠道
  U->>C: 确认订单页提交
  C->>C: 本地校验（勾选/库存/登录）
  C->>S: POST /orders（skuId、quantity、addressId、优惠券）
  S->>S: 服务端锁库存、重算金额
  S-->>C: 返回 orderId + 各端支付参数
  C->>P: 调起支付（条件编译分支）
  P-->>S: 支付结果异步通知
  C->>S: 查询支付状态/轮询补单
  S-->>C: 支付成功 → 跳转结果页

两条铁律：

  1. 支付结果以服务端回调为准，客户端回调只用于交互引导，必须有查询补单。
  2. 锁库存与超时关单在服务端，客户端倒计时只是展示。

前后端接口清单（最小集） ​

域接口
商品列表分页、搜索、详情、SKU 组合查询、评价分页
购物车快照列表、增量同步、合并游客购物车
地址列表、增删改、默认地址
订单创建订单、订单列表、详情、取消、确认收货、倒计时信息
支付创建支付单（返回各端参数）、查询支付状态

状态归属决策 ​

数据放哪里
商品详情（只读、体积大）页面 ref + 接口缓存，不进全局 store
购物车数量/勾选cart store + 持久化
用户 token/资料/默认地址user store
确认订单页临时选择（优惠券、备注）页面状态；跨页用 order store 或 eventChannel
订单列表页面分页状态，不全局缓存（状态实时性要求高）
