9.3 实战案例：订单状态机与性能优化练习 ​

订单系统最容易出 bug 的地方是「什么状态下允许做什么操作」。用状态机显式建模，比散落的 if-else 可靠得多。

一、订单状态机 ​

mermaid
stateDiagram-v2
  [*] --> pending_payment: 下单成功
  pending_payment --> pending_ship: 支付成功
  pending_payment --> cancelled: 超时/用户取消
  pending_ship --> shipped: 商家发货
  shipped --> completed: 确认收货/自动确认
  completed --> refunding: 申请售后
  refunding --> completed: 售后驳回/撤销
  refunding --> cancelled: 退款完成(终态按业务)
  cancelled --> [*]
  completed --> [*]

代码显式表达转移表，非法转移直接拒绝：

ts
// src/constants/order-machine.ts
import type { OrderStatus } from '@/types/order'

export const ORDER_TRANSITIONS: Record<OrderStatus, OrderStatus[]> = {
  pending_payment: ['pending_ship', 'cancelled'],
  pending_ship: ['shipped', 'cancelled'], // 未发货允许退款取消
  shipped: ['completed'],
  completed: ['refunding'],
  refunding: ['completed', 'cancelled'],
  cancelled: [],
}

export function canTransit(from: OrderStatus, to: OrderStatus): boolean {
  return ORDER_TRANSITIONS[from]?.includes(to) ?? false
}

export function assertTransit(from: OrderStatus, to: OrderStatus) {
  if (!canTransit(from, to)) {
    throw new Error(`非法的订单状态流转：${from} → ${to}`)
  }
}

二、状态 → 操作按钮矩阵 ​

订单列表每个 tab 下能展示哪些按钮，用同一张配置驱动：

ts
// src/constants/order-actions.ts
import type { OrderStatus } from '@/types/order'

export type OrderAction = 'pay' | 'cancel' | 'remind_ship' | 'confirm_receipt' | 'review' | 'after_sale' | 'logistics'

export const STATUS_ACTIONS: Record<OrderStatus, OrderAction[]> = {
  pending_payment: ['pay', 'cancel'],
  pending_ship: ['remind_ship', 'cancel', 'logistics'],
  shipped: ['confirm_receipt', 'logistics'],
  completed: ['review', 'after_sale'],
  refunding: ['logistics'],
  cancelled: [],
}

export const ACTION_META: Record<OrderAction, { text: string; type: 'primary' | 'secondary' | 'danger' }> = {
  pay: { text: '立即付款', type: 'primary' },
  cancel: { text: '取消订单', type: 'danger' },
  remind_ship: { text: '提醒发货', type: 'secondary' },
  confirm_receipt: { text: '确认收货', type: 'primary' },
  review: { text: '评价', type: 'secondary' },
  after_sale: { text: '申请售后', type: 'secondary' },
  logistics: { text: '查看物流', type: 'secondary' }
}

列表渲染时直接 map：

vue
<view class="actions">
  <button
    v-for="action in STATUS_ACTIONS[order.status]"
    :key="action"
    :class="`btn-${ACTION_META[action].type}`"
    @tap="dispatch(order, action)"
  >{{ ACTION_META[action].text }}</button>
</view>

操作分发集中处理，避免模板里堆判断：

ts
async function dispatch(order: Order, action: OrderAction) {
  switch (action) {

三、列表 tab 与分页状态隔离 ​

五个状态 tab 共用一个列表组件，但缓存各自的数据（切回 tab 不重新转圈）：

ts
// 简单方案：每个 tab 独立分页状态的 Map
const caches = reactive(new Map<OrderStatus, { list: Order[]; page: number; finished: boolean }>())

function ensureCache(status: OrderStatus) {
  if (!caches.has(status)) caches.set(status, { list: [], page: 1, finished: false })
  return caches.get(status)!
}

注意与性能原则平衡：缓存提升体验，但订单列表实时性强，onShow 时对当前 tab 做静默刷新（stale-while-revalidate）。

四、性能专项练习（对照 8.3 审计清单） ​

练习 A：商详页首屏 ​

现状假设：首屏要依次请求「详情 → SKU 价格 → 店铺信息 → 评价摘要」，白屏 2.8s。

要求：

  1. 重排为并行请求（首屏必要数据 ≤2 个接口）。
  2. 非关键模块（评价、推荐）延后加载，先出主图与购买栏。
  3. 二次进入商详使用本地缓存先渲染，后台拉新（注意价格不可长期缓存）。
  4. 用 PerfMark 输出优化前后的首屏可交互时间。

练习 B：图片治理 ​

  1. 列表图接入 CDN 裁剪参数，宽度按 200rpx × 设备像素比请求。
  2. 统一 WebP（不支持的端走条件编译回退原格式）。
  3. 商详大图全部懒加载，首屏只加载前两张。

练习 C：包体积 ​

  1. 营销页整体移入分包，配置详情页 WiFi 预下载。
  2. 检查是否整包引入了工具库，改为按需导入。
  3. 记录主包体积前后对比，目标 ≤1.5MB。

五、自测清单（上线前过一遍） ​

交易正确性

  • [ ] 取消支付后订单可继续支付
  • [ ] 弱网重复点击提交不会产生重复订单（服务端幂等 + 客户端锁）
  • [ ] 库存临界：最后一件两人同时下单的结果符合预期
  • [ ] 退款/售后流程中订单状态与按钮变化正确
  • [ ] 金额始终与服务端订单详情一致

多端

  • [ ] 微信支付：小程序、H5（支付目录授权）、App 各真机一次
  • [ ] 自定义导航 + 胶囊按钮位置正确（7.2）
  • [ ] 全面屏底部按钮不被横条遮挡

性能

  • [ ] 列表快速滚动无明显掉帧，图片无抖动
  • [ ] 分包在 4G 下首次进入可接受（或已预下载）
  • [ ] 中低端 Android 真机完成一次完整下单

综合大作业 ​

独立完成一个「秒杀频道」：

  • 放分包内，服务端时间校准倒计时（不依赖本地时钟）
  • 防超额：服务端库存为准，客户端按钮状态只做体验
  • 限流：下单排队态、失败重试上限
  • 完成状态机设计与页面跳转栈说明
