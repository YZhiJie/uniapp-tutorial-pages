14.3 实战案例：企业级 App 完整发布流程 ​

一个 uni-app 电商 App 从「能跑」到「上架 8 个渠道 + 崩溃率 < 0.1% + 随时可回滚」，通常要经过 2–3 周的密集打磨。本章把整个流程拆成：多商店上架 → iOS 合规 → 崩溃监控 → 版本升级策略。每一部分都有真实项目踩过的坑。

一、Android 五家应用商店上架 ​

国内 Android 生态是真正的「战国」——华为、小米、OPPO、vivo、三星各占 10–25% 的市场份额，少上一家就等于少覆盖几百万用户。每家商店的审核规则、资料要求、反馈时效都不一样。

多商店 Checklist ​

商店审核周期核心差异容易被拒的点后台地址
华为应用市场1–2 工作日企业资质最严；软著 / ICP / 备案号三证必查截图含其他应用 Logo；隐私协议链接打不开developer.huawei.com
小米应用商店1–3 工作日包名签名与软著名必须一致应用名称含「官方」「第一」等极限词；首次接入需人工复核dev.mi.com
OPPO 软件商店1–2 工作日OPPO 有独立的支付通道备案要求首页 / 登录页跳 H5 需单独报备；应用内下载其他 App 被拒open.oppomobile.com
vivo 应用商店2–4 工作日vivo 是五家里审核最慢的弹窗广告频率过高被拒（每小时 > 3 次）dev.vivo.com.cn
三星应用商店3–5 工作日海外用户基数大，需多语言描述（简体 + 英文）截图分辨率过低；未覆盖平板适配被降级展示seller.samsungapps.com

审核高频雷区（每家都会踩） ​

雷区描述解法
Demo / Test / Beta 字样应用名、截图、启动页上出现任何类似字样全部替换为正式名；启动页只保留 Logo + Slogan
隐私协议不合规首次启动未弹窗授权、协议里没列清收集哪些字段、没有注销入口参考本节后文的 iOS 隐私方案，Android 基本照抄
隐式跳转浏览器 / 其他 App点击后直接打开 H5 或唤起微信，没有显式确认弹窗加一步确认弹窗：「即将打开外部网页」
自更新逻辑App 内部检查新版本并下载 APK 的行为，华为 / OPPO 明确禁止移除 内置自更 APK 逻辑；热更新 wgt 包不在禁令范围
权限申请顺序首次启动一次性申请所有权限（相机 + 位置 + 通讯录）按需申请：用到哪个功能再申请哪个权限

⚠️ 小米商店特别提示：小米会用自动化工具扫描 APK 里是否出现其他商店的 URL / 名字（华为、OPPO、腾讯应用宝）。如果你的 App 内有「应用商店」入口指向应用宝，必须在小米版本里隐藏或替换。

二、iOS App Store 审核 ​

苹果的审核是所有平台里最「玄学」的——同一个 App，两次提交可能一个秒过一个被拒。但核心雷区相对稳定。

iOS 三大高频拒审条款 ​

条款编号触发场景解法
最小功能性Guideline 4.2App 只有一个 WebView 壳，没有独立于网页的功能必须加原生功能模块（比如 App 专属的「消息中心」「离线缓存」「Widget」），纯 H5 壳必拒
隐私合规Guideline 5.1收集了设备 IDFA / 位置 / 通讯录但没在隐私清单里声明本节后文详述
ITC-21.5审核系统提交时选的年龄分级 / 内容描述与实际不符；订阅类 App 价格结构不清晰用 Age Rating 问卷实事求是回答；订阅价格区间写清楚

隐私清单（Privacy Manifest） ​

Apple 要求自 2024 年起所有 App 必须声明「我们收集了哪些数据、用来做什么」。uni-app App 端需要在 manifest.json 里配置，最终生成一份 PrivacyInfo.xcprivacy 文件：

xml
<!-- 由 manifest.json 自动生成，示意 -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>NSPrivacyAccessedAPITypes</key>
  <array>
    <dict>
      <key>NSPrivacyAccessedAPIType</key>
      <string>NSPrivacyAccessedAPICategoryFileTimestamp</string>
      <key>NSPrivacyAccessedAPITypeReasons</key>
      <array>
        <string>C617.1</string>
      </array>
    </dict>
    <dict>
      <key>NSPrivacyAccessedAPIType</key>
      <string>NSPrivacyAccessedAPICategoryUserDefaults</string>
      <key>NSPrivacyAccessedAPITypeReasons</key>
      <array>
        <string>CA92.1</string>
      </array>
    </dict>
  </array>
  <key>NSPrivacyTracking</key>
  <false/>
  <key>NSPrivacyCollectedDataTypes</key>
  <array>
    <dict>
      <key>NSPrivacyDataType</key>
      <string>NSPrivacyDataTypeContactInfo</string>
      <key>NSPrivacyDataUsage</key>
      <string>NSPrivacyDataUsageProductImprovement</string>
    </dict>
  </array>
</dict>
</plist>

关键原则：

  • 收集了才写。没用到的权限（比如通讯录、日历）就别声明，声明了就必须要运行时弹窗。
  • 原因码要对。C617.1 是文件时间戳（uni.storage）、CA92.1 是 UserDefaults。原因码错了会被强制下架。
  • App Store Connect 里也要填。plist 是给审核看的，Connect 后台的隐私问卷是给用户看的，两边内容必须一致。

典型被拒申诉话术（Guideline 4.2） ​

您好，感谢审核团队的反馈。我们仔细检查了 4.2 条款，并在 v2.1.1 版本中新增了三个 App 专属原生模块：① 消息中心（离线推送到达提醒 + 原生列表）② 我的收藏（SQLite 本地存储）③ 今日推荐小组件（WidgetKit）。同时对商详页加入了原生图片预加载。请重新审核，详见 v2.1.1 版本号。

申诉不要硬刚苹果的决定，而是主动提出修复 + 提交新版本。90% 的情况申诉 + 新版本 1–2 天内会被通过。

三、崩溃监控：Bugly / Sentry 接入 ​

上架只是开始——崩溃率 < 0.1% 才是及格线。iOS 崩溃 5% 以上会被 App Store 主动降权，Android 各商店虽然不直接降权，但用户卸载率会指数上升。

Sentry 接入（推荐） ​

ts
// src/services/sentry.ts
// #ifdef APP-PLUS
import * as Sentry from '@sentry/browser'

Sentry.init({
  dsn: 'https://xxx@o0.ingest.sentry.io/123456',
  environment: plus.runtime.versionName.startsWith('2.') ? 'production' : 'staging',
  release: `shop-app@${plus.runtime.versionName}`,
  integrations: [
    new Sentry.Replay({ enabled: true, maskAllText: false }),
  ],
  // App 端特有：加上机型 / 系统版本
  initialScope: {
    tags: {
      platform: uni.getSystemInfoSync().platform,
      model: uni.getSystemInfoSync().model,
      osVersion: uni.getSystemInfoSync().system,
    },
  },
})

// 全局兜底
uni.onError((err) => {
  Sentry.captureException(err)
})
// #endif

Bugly 接入（腾讯系，国内更稳定） ​

ts
// src/services/bugly.ts
// #ifdef APP-PLUS
// 插件市场装「腾讯 Bugly」原生插件后
const bugly = uni.requireNativePlugin('Bugly')

bugly.init({
  androidAppId: 'your-android-appid',
  iosAppId: 'your-ios-appid',
  channel: 'official',
  // 灰度策略：5% 用户上报详细日志，其余只上报堆栈
  debugMode: false,
  autoInit: true,
})

// 手动上报业务异常
export function reportBizError(code: string, msg: string, extra?: any) {
  bugly.postException({
    code, msg, extra,
    type: 'BusinessException',
  })
}

// 记录用户行为轨迹（面包屑）
export function leaveBreadcrumb(message: string, category?: string) {
  bugly.leaveBreadcrumb({ message, category: category ?? 'action' })
}
// #endif

灰度崩溃告警策略 ​

mermaid
flowchart TD
    A[崩溃发生] --> B{灰度?}
    B -->|是| C[Bugly 自动聚合<br/>按 userId 分桶]
    B -->|全量| D[直接告警]
    C --> E{崩溃率 > 阈值?}
    E -->|否| F[静默收集<br/>人工定期查看]
    E -->|是| G[触发告警<br/>飞书群 @值班人员]
    G --> H[判断是否阻塞<br/>核心路径]
    H -->|阻塞| I[热更新回滚 wgt 包]
    H -->|不阻塞| J[继续观察<br/>下一个版本修复]
阈值数值
告警触发阈值该版本 > 0.5%（Sentry 可按 release 维度配置）
立即回滚阈值核心路径崩溃率 > 2% 且 1 小时内
灰度用户比例通常 5%，高风险版本 1%
核心路径定义登录 → 商详 → 支付下单

崩溃治理 Checklist ​

  • [ ] 所有异常捕获：uni.onError + Promise 全局 unhandledrejection + 网络层重试
  • [ ] 上报携带上下文：userId / 订单号 / 页面栈 / 设备型号 / 原生版本号
  • [ ] 符号表上传：iOS 的 .dSYM 和 Android 的 mapping.txt 每次发版必须上传（否则崩溃堆栈是混淆的）
  • [ ] 崩溃告警分级：核心路径 P0（5 分钟响应）、次要路径 P1（4 小时内）
  • [ ] 每周崩溃复盘：Top 5 崩溃、修复优先级、下周 Crash Free 目标

四、版本升级：强更 / 弱更 / 灰度策略 ​

版本升级是 App 运维里最考验「节奏把控」的一环——强更太多用户烦，弱更太快又覆盖不了核心功能修复。

三种升级类型 ​

类型触发条件交互实现
强更服务端有破坏性变更（如 API 签名变更、Token 协议升级）不可跳过的全屏弹窗，按钮「立即更新」见 14.2 热更新 的 force: true
弱更（推荐）新增功能 / 普通 bug 修复可跳过的弹窗，按钮「稍后」或「立即更新」客户端展示后继续后台静默下载，下次启动安装
灰度更新大版本首次发布 / 高风险变更5% → 20% → 50% → 100% 逐步放量服务端按 userId hash 控制 grayRatio

版本号约定 ​

遵循 semver，把版本号拆成三段：原生主版本号.前端热更新版本号.补丁号

原生版本: 2.1.0   ← 发应用商店，每次改 manifest.json versionName
热更新:  2.1.1   ← 用 wgt 包推送，覆盖所有原生 2.x 用户
补丁:    2.1.1.1 ← 紧急热修，只对灰度用户

不要把原生版本号和热更新版本号混成一个。否则会混乱：应用商店用户可能是 2.1.0，但你已经发了 wgt 到 2.1.3，前端代码版本号和原生版本号对不上。

五、上线前终极 Checklist ​

把这份清单交给 QA，一项项打钩。漏一项就是线上事故：

构建与签名

  • [ ] Android keystore 备份在密码库 + 保险柜
  • [ ] iOS .p12 + .mobileprovision 同步给团队 2 人以上
  • [ ] 证书有效期 ≥ 25 年（Android）/ ≥ 1 年（iOS）
  • [ ] 包名 / Bundle ID 生产环境与测试环境区分

多商店素材

  • [ ] 华为：软著 + ICP + 营业执照三证齐全
  • [ ] 小米：证书 MD5 已填后台，无极限词，无其他商店 URL
  • [ ] OPPO/vivo：隐私协议弹窗首启即弹
  • [ ] 三星：英文描述 + 平板截图

iOS 合规

  • [ ] PrivacyInfo.xcprivacy 与 App Store Connect 后台隐私问卷一致
  • [ ] Info.plist 所有 NS*UsageDescription 写清业务用途
  • [ ] Guideline 4.2 确认：App 有 3 个以上独立原生功能（不只是 WebView）
  • [ ] Age Rating 问卷实事求是填写

崩溃与监控

  • [ ] Bugly / Sentry 已接入并验证（主动抛一个异常看上报）
  • [ ] iOS dSYM / Android mapping.txt 已上传
  • [ ] 飞书 / 钉钉告警通道联通，值班同学已设

权限与隐私

  • [ ] 所有权限按需申请（位置 / 相机 / 相册）
  • [ ] 隐私协议链接可访问（404 会被拒）
  • [ ] 账号注销入口可正常使用（Guideline 5.1.1 强制要求）
  • [ ] 不追踪 IDFA（或走 App Tracking Transparency 弹窗）

性能

  • [ ] 启动白屏时间 ≤ 2s（中低端 Android 真机测）
  • [ ] 冷启动后首屏可交互 ≤ 3s
  • [ ] 安装包体积：Android < 50MB（不含高清资源）、iOS < 100MB

回滚预案

  • [ ] 上一个稳定版本的 wgt 包在 CDN 上保留 30 天
  • [ ] 服务端版本接口已配置好 rollbackVersion 字段可以随时填
  • [ ] 运营同学知道「关闭灰度 → 扩回滚」的操作步骤

综合大作业 ​

假设你是一个电商 App 的 App 端负责人，现在有一个版本要发。请独立完成：

  1. 版本规划：原生 2.2.0 + wgt 2.1.2，哪个走应用商店，哪个走热更新，理由是什么。
  2. 灰度方案：灰度比例怎么定、哪些用户在白名单、告警阈值多少。
  3. 商店资料包：按照本章 Checklist 整理一个 release-materials 目录（实际列出所有需要的文件）。
  4. iOS 隐私清单：你的 App 需要定位、相机、相册、推送 4 项权限，请写出完整的 PrivacyInfo.xcprivacy。
  5. 崩溃监控：Bugly 接入代码 + 符号表上传流程 + 值班告警群。
  6. 回滚演练：模拟一个「商详页点击支付崩溃率 5%」场景，写出你的处置 SOP。
